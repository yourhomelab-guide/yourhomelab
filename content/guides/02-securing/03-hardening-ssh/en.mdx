As soon as a server is reachable from the internet, bots try user names and passwords on port 22 around the clock. That's not a targeted attack; it happens to everyone. With key login alone, you're already well protected. But as long as password login is still allowed, a weak password is enough for a break-in.

So this guide turns off two things: password login and direct login as root. After that, only someone with a registered key gets in, and only as a regular user.

<Callout type="warning" title="Before you start">
Key login must work ([Setting up SSH keys](/en/setup/ssh-keys/)), and with a regular user who may use `sudo`. If you've only been logging in as root so far, do [Users & sudo](/en/setup/users-sudo/) first. Otherwise you'll lock yourself out.
</Callout>

<Steps>

<Step title="Keep a second session open">
Open **two** SSH connections to the server and simply leave one of them open until the end of this guide. Existing sessions stay open even when you restart the SSH service. If something goes wrong with the configuration, you can fix it through this session.

```bash
ssh homelab
```

On a rented server, it's also best to know the way to your provider's web console beforehand. At home, a screen on the device helps in an emergency.
</Step>

<Step title="Create your own configuration file">
Leave the main file `/etc/ssh/sshd_config` unchanged. Current Debian and Ubuntu versions also read all files in `/etc/ssh/sshd_config.d/` that end in `.conf`. A file of your own there has two advantages: you see at a glance what you changed, and package updates don't overwrite anything.

Quickly check that the main file includes the folder:

```bash
grep -i '^Include' /etc/ssh/sshd_config
```

The output should contain `Include /etc/ssh/sshd_config.d/*.conf`. Then create the file:

```bash
sudo nano /etc/ssh/sshd_config.d/10-hardening.conf
```

```text
# Only allow key-based logins
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes

# No direct root login
PermitRootLogin no

# Fewer attempts per connection, no graphical forwarding
MaxAuthTries 3
X11Forwarding no
```

Save with Ctrl+O, Enter, and exit with Ctrl+X.

<Callout title="Why 10- in the file name?">
For most options of the SSH server, the first value found wins, not the last. The files in the folder are read alphabetically, before the rest of the main file. On cloud servers, there's often already a `50-cloud-init.conf` with `PasswordAuthentication yes`. A file named `hardening.conf` would come after it and have no effect. With `10-` at the start, your file is read first. `ls /etc/ssh/sshd_config.d/` shows what else is in the folder.
</Callout>
</Step>

<Step title="Test the configuration">
Before you restart the service, check the syntax. Otherwise a typo could prevent the SSH server from starting again.

```bash
sudo sshd -t
```

No output means: everything's fine. Then check which values the server will actually use. `sshd -T` prints the final configuration, with lowercase names:

```bash
sudo sshd -T | grep -Ei '^(passwordauthentication|kbdinteractiveauthentication|permitrootlogin|pubkeyauthentication)'
```

Expected (the order may differ):

```text
permitrootlogin no
pubkeyauthentication yes
passwordauthentication no
kbdinteractiveauthentication no
```

If it still says `yes` anywhere it should say `no`, another file wins. Find it with `sudo grep -ri passwordauthentication /etc/ssh/`.
</Step>

<Step title="Restart the SSH service">
On Debian and Ubuntu, the service is called `ssh`, not `sshd`:

```bash
sudo systemctl restart ssh
```

Your open sessions stay connected.
</Step>

<Step title="Test in a new terminal">
Leave the existing sessions open and open a **new** terminal. The normal login must keep working:

```bash
ssh homelab
```

Then check that passwords really are rejected. This command forbids SSH to use your key:

```bash
ssh -o PubkeyAuthentication=no homelab
```

Expected is `Permission denied (publickey).` without being asked for a password. Finally, check root:

```bash
ssh root@__SERVER_IP__
```

This must be rejected too. Only when all three tests pass do you close the second session.
</Step>

</Steps>

## If something goes wrong

If you can't get in from the new terminal, switch to the session that's still open. There, rename the file and restart the service:

```bash
sudo mv /etc/ssh/sshd_config.d/10-hardening.conf /root/10-hardening.conf.off
sudo systemctl restart ssh
```

Then the old state applies again, and you can look for the cause calmly. The SSH server's log shows why a login fails:

```bash
sudo journalctl -u ssh -n 50
```

## What about the port?

You often read the advice to move SSH to a port other than 22. That keeps the logs quieter, because fewer bots knock. It hardly makes the server more secure, though, because with key login the guessing attempts are hopeless anyway. That's why this guide leaves the port at 22.

If you want to change the port anyway, add a line like `Port 2200` to your file under `/etc/ssh/sshd_config.d/`. Allow the new port in the [firewall](/en/setup/firewall-ufw/) first (`sudo ufw allow 2200/tcp`), otherwise you'll lock yourself out, and don't use 2222, which [Forgejo](/en/services/forgejo/) uses for Git. Check the configuration with `sudo sshd -t` and apply it:

<Os is="debian">

```bash
sudo systemctl restart ssh
```

</Os>

<Os is="ubuntu">

Ubuntu starts SSH through `ssh.socket`. Then systemd decides which port to listen on, and it only reads the port from your configuration after a `daemon-reload`:

```bash
sudo systemctl daemon-reload
sudo systemctl restart ssh.socket
```

</Os>

Test the login with `ssh -p 2200 …` in a new terminal before you close the old session. Only then remove the firewall rule for port 22.

It's even better if SSH isn't reachable from the internet at all. At home, simply don't forward port 22 on the router, and connect to your home network on the go through a [VPN](/en/setup/vpn-wireguard/). In the next step, the [firewall](/en/setup/firewall-ufw/) also restricts who may connect at all. More in [Keeping the attack surface small](/en/wiki/attack-surface/).
