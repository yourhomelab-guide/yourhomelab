On a server, more programs often listen on ports than you're aware of. A firewall makes sure that only what you explicitly allow is reachable from outside. Everything else is dropped, even if a service later starts on another port by accident.

**UFW** ("Uncomplicated Firewall") is a simple front end for the firewall in the Linux kernel. Instead of long iptables or nftables rules, you write sentences like `ufw allow 443/tcp`.

<Steps>

<Step title="Install UFW">
On Ubuntu, UFW is usually installed already; on Debian it isn't.

```bash
sudo apt update
sudo apt install ufw
```

As long as you don't turn UFW on, nothing changes.
</Step>

<Step title="Set the default rules">
The safe baseline is: everything incoming is denied, everything outgoing is allowed. So the server can download updates and fetch certificates, but nobody gets in uninvited.

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
```
</Step>

<Step title="Allow SSH before you turn it on">
This is the most important step. If you turn on UFW without an SSH rule, the firewall cuts you off from the server.

```bash
sudo ufw allow 22/tcp
```

If your server is at home and you only want to allow SSH from your home network, use this rule instead. Adjust the network to yours:

```bash
sudo ufw allow from 192.168.1.0/24 to any port 22 proto tcp
```

When you're out, you then connect to your home network through a [VPN](/en/setup/vpn-wireguard/) and from there to the server over SSH.
</Step>

<Step title="Allow HTTP and HTTPS">
Your reverse proxy (Traefik, Caddy or Nginx Proxy Manager) will later receive all web requests on ports 80 and 443. It also needs port 80 so Let's Encrypt can issue certificates and visitors get redirected to HTTPS.

```bash
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw allow 443/udp
```

`443/udp` is for HTTP/3, which Traefik and Caddy also offer in the templates here. Without this rule, browsers simply fall back to regular HTTPS.
</Step>

<Step title="Turn on the firewall and check it">

```bash
sudo ufw enable
```

UFW warns that existing SSH connections might be interrupted. With the SSH rule from step 3, that won't happen. Confirm with `y`. The firewall is active from now on and also starts after every reboot.

```bash
sudo ufw status verbose
```

You'll see the default rules and what you've allowed. To be safe, open a new terminal and check that `ssh homelab` still works. To remove a rule, run `sudo ufw status numbered` and then `sudo ufw delete <number>`.
</Step>

</Steps>

## Docker bypasses UFW

You need to know this before you install Docker: **ports that a container publishes are reachable from outside, no matter what UFW says.**

The reason lies in how both programs work with the firewall in the kernel. UFW manages the rules for connections meant for the server itself. If you publish a port like `8080:80` in a `compose.yaml`, Docker writes its own iptables rules. They forward requests on port 8080 straight to the container before UFW's rules even apply. From the firewall's point of view, that's forwarded traffic to another network, not traffic to the server.

That's not a mistake in your configuration but known, documented behavior. The [Docker documentation on firewalls](https://docs.docker.com/engine/network/packet-filtering-firewalls/) describes the details.

### What this means for you

Because UFW doesn't protect you here, you protect yourself in the `compose.yaml`:

- **Only the reverse proxy publishes ports**, namely 80 and 443. All other services get no `ports:` entry at all. They sit in the proxy network `__NETWORK__`, and the proxy reaches them there directly. That's exactly how the templates on this site are built.
- **If you do need a port directly**, for testing for example, bind it to `127.0.0.1`. Then it's only reachable on the server itself, not from the network:

```yaml
ports:
  - "127.0.0.1:8080:80"
```

From your own computer you then get there through an SSH tunnel, for example with `ssh -L 8080:localhost:8080 homelab`, and open `http://localhost:8080` in the browser.

- **Without an IP in front** (`"8080:80"`), the port listens on all network interfaces. That's Docker's default and exactly the case UFW doesn't catch.

Strictly speaking, ports 80 and 443 for a proxy in a container therefore wouldn't need a UFW rule at all. But the rules don't hurt and document what's supposed to be open.

<Callout title="Check for yourself">
You only see what's really reachable from outside. On the server, `sudo ss -tlnp` shows all ports something is listening on. From another computer on the network, you can test a port with `nc -zv __SERVER_IP__ 8080`, for example. If a connection succeeds even though UFW doesn't allow the port, a container has published it.

If Docker later reports on startup that a port is already taken, the same command tells you who's using it. More in [Port already in use](/en/wiki/port-in-use/).
</Callout>

There are projects like [ufw-docker](https://github.com/chaifeng/ufw-docker) that bring UFW and Docker together. To start with, though, the simple rule above is more robust: don't publish unnecessary ports. [Keeping the attack surface small](/en/wiki/attack-surface/) explains why that helps so much.

## Don't forget the router

If your server is at home, the first firewall is your router. From outside, only what you forward there with [port forwarding](/en/wiki/port-forwarding/) gets in. Only forward 80 and 443, not SSH. UFW is the second layer, which also covers devices on your own network.
