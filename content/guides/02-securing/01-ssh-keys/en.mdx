A password can be guessed, intercepted or cracked by trial and error. An SSH key can't: it consists of two parts. The **private key** stays on your computer and never leaves it. The **public key** goes onto the server. When you log in, your computer proves that it has the matching private key, without transmitting it.

This guide sets up the key. After [Users & sudo](/en/setup/users-sudo/), you then turn off password login entirely in [Hardening SSH](/en/setup/hardening-ssh/). The background is in [SSH basics](/en/wiki/ssh-basics/).

The commands use the server IP `__SERVER_IP__` and your user `__USER__` from "My setup". If the values aren't right, enter your own there.

<Callout title="Several devices?">
You repeat the security and Docker guides on every device. Before each pass, enter the device's IP in "My setup"; then all commands fit. [Multiple devices: splitting the roles](/en/wiki/multiple-devices/) explains which device takes on which job.
</Callout>

<Steps>

<Step title="Check whether you already have a key">
Maybe you've created a key before, for GitHub for example. You can keep using it. Look in the `.ssh` folder in your home directory.

On macOS and Linux:

```bash
ls -l ~/.ssh
```

On Windows in PowerShell:

```powershell
ls $env:USERPROFILE\.ssh
```

If you see `id_ed25519` and `id_ed25519.pub` there, skip the next step. If there's only `id_rsa`, that's an older RSA key. It works, but a new ed25519 key is shorter and more modern.
</Step>

<Step title="Create a key pair">
Windows 10 and 11, macOS and practically every Linux distribution already include OpenSSH. The command is the same everywhere. On Windows, type it into PowerShell; otherwise into the terminal.

```bash
ssh-keygen -t ed25519 -C "laptop-__USER__"
```

- `-t ed25519` chooses the key type. ed25519 is the current standard: secure, fast and short.
- `-C` is just a comment. It helps you recognize later which device a key comes from.

Confirm the suggested location with Enter. Then `ssh-keygen` asks for a **passphrase**. Use one. It encrypts the private key on your disk. If your laptop gets stolen, nobody can use the key without the passphrase.

You now have two files:

- `id_ed25519` is the private key. Never share it, never copy it to a server.
- `id_ed25519.pub` is the public key. You may put it anywhere.
</Step>

<Step title="Copy the public key to the server">
On the server, the public key goes into your user's `~/.ssh/authorized_keys` file. Every line there is a key that may log in.

On **macOS and Linux**, `ssh-copy-id` does this. It asks for your password on the server one last time:

```bash
ssh-copy-id -i ~/.ssh/id_ed25519.pub __USER__@__SERVER_IP__
```

On **Windows**, there's no `ssh-copy-id`. This one-liner in PowerShell does the same: it sends the key to the server over SSH, creates the folder there and appends the key to `authorized_keys`.

```powershell
type $env:USERPROFILE\.ssh\id_ed25519.pub | ssh __USER__@__SERVER_IP__ "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"
```

The permissions `700` and `600` matter. If anyone other than you can write the files, the SSH server ignores them for security reasons.

<Callout title="Only root on the server?">
On some rented servers, there's only the root user at first. Then copy the key to root for now and create your own user in the guide [Users & sudo](/en/setup/users-sudo/).
</Callout>
</Step>

<Step title="Test logging in with the key">
Log in again:

```bash
ssh __USER__@__SERVER_IP__
```

If you set a passphrase, SSH now asks for **your key's passphrase**, not the server's password. If SSH asks for `__USER__@__SERVER_IP__'s password`, it didn't work. Common causes: the key is stored for the wrong user, or the permissions on the server aren't right. With `ssh -v __USER__@__SERVER_IP__`, you see which keys SSH offers and what the server answers.
</Step>

<Step title="Create a short name in ~/.ssh/config">
Instead of typing user and IP every time, create an entry in `~/.ssh/config` on your computer. On Windows, the file is at `C:\Users\<your name>\.ssh\config` (without a file extension). If it doesn't exist yet, create it.

```text
Host homelab
    HostName __SERVER_IP__
    User __USER__
    IdentityFile ~/.ssh/id_ed25519
    AddKeysToAgent yes
```

From now on, this is enough:

```bash
ssh homelab
```

The short name also works with `scp` and `rsync`, and in editors like VS Code (Remote SSH).
</Step>

<Step title="Don't enter the passphrase every time">
So you don't have to type the passphrase for every connection, the **SSH agent** remembers the unlocked key until you log out. `AddKeysToAgent yes` from the previous step hands the key to the agent automatically on the first connection.

- **Linux:** most desktops start the agent automatically.
- **macOS:** the agent always runs. If macOS should remember the passphrase permanently in the keychain, add the line `UseKeychain yes` to the entry. This option only exists on macOS.
- **Windows:** the service is off by default. Turn it on once in a PowerShell window you open **as administrator**:

```powershell
Get-Service ssh-agent | Set-Service -StartupType Automatic
Start-Service ssh-agent
ssh-add $env:USERPROFILE\.ssh\id_ed25519
```
</Step>

</Steps>

## Several devices

Use a separate key per device instead of copying one private key around. Each gets its own line in `authorized_keys`. If a laptop gets lost, you only delete its line, and all other devices still get in. That's what the `-C` comment is useful for.

Also back up the private key, or add at least a second key from another device. Once password login is off, the key is your only way onto the server, apart from a screen and keyboard directly at the device or your hosting provider's web console.
