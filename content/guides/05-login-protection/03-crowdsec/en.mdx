As soon as a service is publicly reachable, bots come knocking. They try passwords, look for known holes in WordPress or phpMyAdmin and scan for forgotten admin pages. A good login stops them, but they stay in the log and put load on the server. The smaller your [attack surface](/en/wiki/attack-surface/), the better.

CrowdSec detects such patterns and blocks the senders. It consists of two parts:

- The **security engine** reads logs, compares them with scenarios (e.g. "more than X failed logins in a short time") and makes **decisions**, such as "block IP for 4 hours". It doesn't block anything itself.
- A **bouncer** enforces the decisions. That can be a plugin in the reverse proxy or a rule in the firewall.

In addition, CrowdSec shares detected attackers anonymously with the community and in return gets a blocklist of known bad IPs. Details are in the [official docs](https://docs.crowdsec.net/).

<OneWay />

This guide uses the bouncer plugin for Traefik. It blocks requests before they reach a service. Nginx Proxy Manager and Caddy need other bouncers; see the [bouncer overview](https://docs.crowdsec.net/u/bouncers/intro).

<Steps>

<Step title="Turn on Traefik's access logs">
CrowdSec can only detect what's in the log. By default, Traefik doesn't write an access log. Add this under `command` in `__ROOT__/traefik/compose.yaml`:

```yaml
      - --accesslog=true
      - --accesslog.filepath=/var/log/traefik/access.log
```

and under `volumes`:

```yaml
      - __DATA(traefik)__/logs:/var/log/traefik
```

Then restart Traefik and check that lines arrive:

```bash
mkdir -p __DATA(traefik)__/logs
cd __ROOT__/traefik
docker compose up -d
tail -f __DATA(traefik)__/logs/access.log
```

Open one of your services in the browser. The log then shows one line per request.
</Step>

<Step title="Create the CrowdSec stack">
CrowdSec isn't a service from this site's catalog, so you write the files by hand here.

```bash
mkdir -p __ROOT__/crowdsec __DATA(crowdsec)__
cd __ROOT__/crowdsec
```

The `acquis.yaml` file tells CrowdSec which logs to read and which parser fits them:

```yaml
filenames:
  - /var/log/traefik/access.log
labels:
  type: traefik
```

The `compose.yaml`:

```yaml
services:
  crowdsec:
    image: crowdsecurity/crowdsec:v1.8.1
    container_name: crowdsec
    restart: unless-stopped
    environment:
      - TZ=__TZ__
      # Parser and scenarios for Traefik logs, plus known CVE exploits
      - COLLECTIONS=crowdsecurity/traefik crowdsecurity/http-cve
    volumes:
      - __DATA(crowdsec)__/config:/etc/crowdsec
      - __DATA(crowdsec)__/db:/var/lib/crowdsec/data
      - ./acquis.yaml:/etc/crowdsec/acquis.yaml:ro
      # Traefik access logs, read-only
      - __DATA(traefik)__/logs:/var/log/traefik:ro
    networks:
      - __NETWORK__

networks:
  __NETWORK__:
    external: true
```

A few notes on this:

- **Collections** are packages of parsers and scenarios from the [CrowdSec Hub](https://app.crowdsec.net/hub). `crowdsecurity/traefik` understands the Traefik log and brings general web scenarios.
- Both data folders (`config` and `db`) must be persistent, otherwise CrowdSec doesn't start or loses its database.
- CrowdSec sits in the `__NETWORK__` network so Traefik can reach it at `crowdsec:8080` later. The stack publishes no port to the outside.

You'll find new versions on [CrowdSec's releases](https://github.com/crowdsecurity/crowdsec/releases).
</Step>

<Step title="Start and check that logs are read">

```bash
cd __ROOT__/crowdsec
docker compose up -d
docker compose logs -f crowdsec
```

On the first start, CrowdSec downloads the collections. Then use `cscli`, CrowdSec's command-line tool, to check that it reads the Traefik log:

```bash
docker exec crowdsec cscli metrics
```

In the section on data sources (acquisition), `/var/log/traefik/access.log` should show up with read and parsed lines. If there are only "unparsed" lines, the log format doesn't match the parser. `docker exec crowdsec cscli collections list` shows the installed collections.
</Step>

<Step title="Create a bouncer key">
The bouncer logs in to CrowdSec with an API key. You create it with:

```bash
docker exec crowdsec cscli bouncers add traefik-bouncer
```

The key is shown **only once**. Enter it in `__ROOT__/traefik/.env`:

```bash
CROWDSEC_BOUNCER_KEY=DEIN_BOUNCER_KEY
```

Replace the placeholder with your key. Later, `docker exec crowdsec cscli bouncers list` shows whether the bouncer has connected.
</Step>

<Step title="Turn on the bouncer plugin in Traefik">
The [crowdsec-bouncer-traefik-plugin](https://github.com/maxlerebourg/crowdsec-bouncer-traefik-plugin) is maintained by the community and [officially recommended](https://docs.crowdsec.net/u/bouncers/traefik) by CrowdSec. Traefik downloads it by itself on startup.

Add this under `command` in `__ROOT__/traefik/compose.yaml`:

```yaml
      - --experimental.plugins.bouncer.modulename=github.com/maxlerebourg/crowdsec-bouncer-traefik-plugin
      - --experimental.plugins.bouncer.version=v1.7.1
```

The current version is on the plugin's project page.

Under `labels`, define the `crowdsec` middleware:

```yaml
      - traefik.http.middlewares.crowdsec.plugin.bouncer.enabled=true
      - traefik.http.middlewares.crowdsec.plugin.bouncer.crowdseclapikey=${CROWDSEC_BOUNCER_KEY}
      - traefik.http.middlewares.crowdsec.plugin.bouncer.crowdseclapihost=crowdsec:8080
```

So the middleware applies to **all** services, attach it directly to the `websecure` entrypoint. For that, add this under `command`:

```yaml
      - --entrypoints.websecure.http.middlewares=crowdsec@docker
```

If you only want to protect individual services, leave this line out and attach the middleware to individual routers with a label, as in the [Tinyauth guide](/en/setup/tinyauth/), e.g. `traefik.http.routers.uptime-kuma.middlewares=crowdsec@docker`. Separate several middlewares with commas.

Then restart Traefik:

```bash
cd __ROOT__/traefik
docker compose up -d
docker compose logs traefik
```

The log shouldn't show any errors about the plugin. `docker exec crowdsec cscli bouncers list` now shows a timestamp for the last pull.
</Step>

<Step title="Test a block">
The easiest test is a manual decision. Use an IP you're about to access from, e.g. your phone's on the mobile network. The Traefik log shows which IP arrives.

```bash
docker exec crowdsec cscli decisions add --ip 203.0.113.10 --duration 5m --reason "Test"
docker exec crowdsec cscli decisions list
```

Replace `203.0.113.10` with the real IP. If you now open a service, Traefik answers with `403 Forbidden`. Afterwards, lift the block again:

```bash
docker exec crowdsec cscli decisions delete --ip 203.0.113.10
```
</Step>

</Steps>

## Day to day

The most important commands:

| Command | Shows |
| --- | --- |
| `docker exec crowdsec cscli metrics` | Log lines read, scenarios triggered, bouncer queries |
| `docker exec crowdsec cscli decisions list` | IPs currently blocked by your own detections |
| `docker exec crowdsec cscli alerts list` | What CrowdSec detected and why |
| `docker exec crowdsec cscli bouncers list` | Connected bouncers |
| `docker exec crowdsec cscli hub update` | Updates the list of parsers and scenarios |

Traefik's access log keeps growing. Rotate it, e.g. with `logrotate`. Traefik reopens the log file after the `USR1` signal. More in the article [Logs](/en/wiki/logs/).

If you want to know when CrowdSec blocks someone, it can send messages through its notification plugins, for example over HTTP to ntfy. The guide [Notifications](/en/setup/notifications/) shows how to set up ntfy.

<Callout type="warning" title="Behind Cloudflare or another proxy">
If Traefik runs behind a [Cloudflare Tunnel](/en/setup/cloudflare-tunnel/) or another proxy, it doesn't see the visitor's IP but the proxy's. Then CrowdSec might end up blocking the proxy. In that case, Traefik and the plugin have to trust the forwarded headers. The [plugin's docs](https://github.com/maxlerebourg/crowdsec-bouncer-traefik-plugin) describe how.
</Callout>

## Alternative: firewall bouncer on the host

Instead of in the proxy, a bouncer can also block in the server's firewall. That applies to all ports, including services that don't run through Traefik. For this, install the [firewall bouncer](https://docs.crowdsec.net/u/bouncers/firewall) from CrowdSec's package repository directly on the host (package `crowdsec-firewall-bouncer-iptables` or `crowdsec-firewall-bouncer-nftables`).

So it can reach the CrowdSec container, publish its API locally only. Add this to `__ROOT__/crowdsec/compose.yaml`:

```yaml
    ports:
      - "127.0.0.1:8080:8080"
```

Many other services use port 8080 too. If Docker reports that it's taken, [Port already in use](/en/wiki/port-in-use/) helps.

In the bouncer configuration `/etc/crowdsec/bouncers/crowdsec-firewall-bouncer.yaml`, then set `api_url: http://127.0.0.1:8080/` and, as the `api_key`, a key from `docker exec crowdsec cscli bouncers add firewall-bouncer`.

Important with Docker: traffic to containers doesn't go through the firewall's normal input chain. With iptables, you therefore have to add the `DOCKER-USER` chain to `iptables_chains`, otherwise blocked IPs still reach your containers. The docs describe the details.

<Callout title="All secured?">
With CrowdSec, the login protection stage is complete. Use the [security check](/en/tools/security-check/) to see whether you've thought of everything, from SSH and the firewall to the login in front of your services.
</Callout>
