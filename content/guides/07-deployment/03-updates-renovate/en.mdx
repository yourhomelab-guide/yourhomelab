<Callout title="Optional">
You don't strictly need this guide. [Dockhand](/en/setup/portainer-dockhand/) handles container updates more simply: it checks daily, updates automatically within the tag if you like, and can scan new images for vulnerabilities first. Renovate is worth it if you keep your Compose files in Git and want to see every new version, including new major versions, as a pull request. You can combine both: Dockhand for small updates, Renovate for new tags.
</Callout>

Containers don't update themselves. If you use `latest` and run `docker compose pull` now and then, you do get new versions, but you don't know which. If an update brings a bug, there's no easy way back.

**Renovate** solves this differently: it reads the image tags in your `compose.yaml` files in the Git repository, checks the registry for newer versions and opens a **pull request** (PR) for each update. A PR is a proposed change that you can review, accept or reject. That way you see every update before it goes live, and every version is recorded in the Git history.

This guide builds on [Git deployments with Forgejo](/en/setup/git-deployments-forgejo/). So you need the `homelab` repository in Forgejo and the deploy script on the server.

<OneWay />

## How it works

1. Renovate runs once a night as a short-lived container.
2. It finds, for example, `vaultwarden/server:1.37.2` in your repository and sees that `1.37.3` exists.
3. It opens a PR in Forgejo that changes exactly this line, usually with a link to the release notes.
4. You merge the PR, or Renovate does it itself for patch updates.
5. Your deploy script fetches the change with `git pull`, and `docker compose up -d` starts the container with the new version.

## Setting it up

<Steps>

<Step title="Fixed tags instead of latest">
Renovate can only compare versions. From `latest`, `stable` or `lts`, it can't tell which version is running. So switch your images to fixed version tags.

```yaml
# vorher
image: vaultwarden/server:latest
# nachher
image: vaultwarden/server:1.37.3
```

You'll find the available tags on the image's page on Docker Hub or in the GitHub Container Registry. Pick the version that's currently running for you. That way nothing changes when you switch. The container's log or the service's web interface often shows the running version.

Some projects only offer tags for the major version, such as `forgejo:15`. That's fine: within the major version, updates then come through `docker compose pull`, and Renovate tells you about the jump to the next major version.

Commit and push the change as usual.
</Step>

<Step title="Create a bot user in Forgejo">
Renovate gets a user of its own. That way you see right away in Forgejo which changes come from the bot, and you can revoke its access at any time.

1. As admin in Forgejo: **Site Administration** → **User Accounts** → **Create User Account**. Name it `renovate`, for example.
2. Log in as `renovate` and enter a full name and an email address in the profile settings. Renovate needs both for its commits.
3. Back as yourself: repository `homelab` → **Settings** → **Collaborators** → add `renovate` with **write** access.
</Step>

<Step title="Create an access token">
Logged in as `renovate`: **Settings** → **Applications** → **Generate New Token**. Give it these permissions:

| Scope          | Permission         |
| -------------- | ------------------ |
| `repository`   | Read and write     |
| `user`         | Read               |
| `issue`        | Read and write     |
| `organization` | Read               |

Copy the token right away; Forgejo only shows it once. The current list of permissions is in the [Renovate docs for Forgejo](https://docs.renovatebot.com/modules/platform/forgejo/).
</Step>

<Step title="Put renovate.json into the repository">
The configuration for your repository lives as `renovate.json` directly in `__ROOT__`, or in your cloned repository on your computer. If it's already there on the first run, Renovate skips its setup PR ("onboarding") and gets started right away.

```json
{
  "$schema": "https://docs.renovatebot.com/renovate-schema.json",
  "extends": ["config:recommended"],
  "enabledManagers": ["docker-compose"],
  "ignoreTests": true,
  "packageRules": [
    {
      "matchUpdateTypes": ["patch"],
      "automerge": true
    }
  ]
}
```

What the lines mean:

- `config:recommended` is Renovate's recommended base configuration. Among other things, it creates a "Dependency Dashboard" issue that lists all open and planned updates.
- `enabledManagers` limits Renovate to Compose files. The `docker-compose` manager finds `compose.yaml` and `docker-compose.yml` in all subfolders by itself.
- The `packageRules` allow **automatic merging for patch updates only**, for example from `1.37.2` to `1.37.3`. Minor and major updates stay open as PRs until you approve them.
- `ignoreTests` is needed because your repository has no automated tests. Without this line, Renovate waits for passing tests before automerging, and they never come.

Commit the file and push it.
</Step>

<Step title="Set up Renovate as a container">
Renovate isn't a service that runs permanently. It starts, checks all repositories, opens PRs and exits. Create a folder of its own for it:

```bash
mkdir -p __ROOT__/renovate
touch __ROOT__/renovate/.skip
```

The empty `.skip` file makes the deploy script from the Forgejo guide leave this stack out. Renovate should only run on a schedule, not on every deploy.

`__ROOT__/renovate/compose.yaml`:

```yaml
services:
  renovate:
    # Check https://github.com/renovatebot/renovate/releases for the current major version
    image: ghcr.io/renovatebot/renovate:44
    env_file: .env
```

`__ROOT__/renovate/.env`:

```bash
RENOVATE_PLATFORM=forgejo
RENOVATE_ENDPOINT=https://git.__DOMAIN__/api/v1
RENOVATE_TOKEN=dein-token-aus-forgejo
# Work on every repository the renovate user has access to
RENOVATE_AUTODISCOVER=true
```

Replace the `RENOVATE_TOKEN` value with your token. With `RENOVATE_AUTODISCOVER=true`, Renovate works on every repository the bot user has access to. Because it's only a collaborator in `homelab`, that's exactly this one.

Optional: many images come from projects on GitHub. So Renovate can fetch their release notes without running into rate limits, you can also set `RENOVATE_GITHUB_COM_TOKEN` with a GitHub token without special permissions. Without this token, Renovate shows a warning in the log but works.

The `.env` contains the token and, thanks to the `.gitignore`, doesn't end up in the repository. The `compose.yaml` may go into the repository. Renovate then even updates its own image.

Renovate must be able to reach `https://git.__DOMAIN__` from the server. That's the case when the domain points to your reverse proxy.
</Step>

<Step title="Test the first run">
Start Renovate once by hand and watch:

```bash
cd __ROOT__/renovate
docker compose run --rm renovate
```

The first run takes a bit longer because the image gets downloaded. Afterwards, you'll find the first suggestions in Forgejo under **Pull Requests** and the Dependency Dashboard under **Issues**. If there are no updates right now, that's fine too: the dashboard then lists all images it found.

If nothing happens, read the output from top to bottom. Typical causes are a wrong token, missing permissions for the bot user or a wrong `RENOVATE_ENDPOINT` address.
</Step>

<Step title="Run it automatically at night">
One run per night is enough for a homelab. Open your crontab:

```bash
crontab -e
```

and add this line. Renovate then runs every day at 4:17 a.m.:

```bash
17 4 * * * cd __ROOT__/renovate && docker compose run --rm renovate >> $HOME/renovate.log 2>&1
```

Patch updates are then merged by the next run at the latest. Your deploy script fetches them on the next `git pull`, and `docker compose up -d` downloads the new image because it doesn't exist locally yet.
</Step>

<Step title="Review and approve updates">
For minor and major updates, take a look at the PR:

- Renovate links the release notes if it finds them. Read them before merging, especially for **major updates** (the first number changes). They often bring changes that require manual work.
- **Databases** like PostgreSQL or MariaDB usually can't simply be swapped on a major update. The data has to be migrated. Make a backup first and follow the project's instructions. How that works with a dump and restore, and how to get back if it already happened, is covered in [Database won't start after an update](/en/wiki/database-version/).
- If everything fits, merge the PR in Forgejo. The deploy script takes care of the rest.

If something goes wrong, undo the merge commit with `git revert` and push. Then the old version runs again.
</Step>

</Steps>

<Callout title="Automerge with good judgment">
Patch updates are usually pure bug fixes, but not every project sticks to this rule strictly. If a service is especially important to you, your password manager for example, you can exclude it from automerge. The [Renovate docs on automerge](https://docs.renovatebot.com/key-concepts/automerge/) explain how. And don't forget: automatic updates don't replace [backups](/en/setup/backups-borgmatic/).
</Callout>
