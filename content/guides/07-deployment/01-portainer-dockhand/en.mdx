So far you've controlled everything over SSH and `docker compose`. That remains the most reliable way. A web interface is still handy: you see at a glance which containers are running, read logs in the browser and restart a stuck service without opening a terminal. Two tools are common in homelabs: **Portainer CE** and **Dockhand**.

<OneWay />

## The two at a glance

<Cards>
  <Card title="Portainer CE">
    The classic for many years. Manages containers, images, volumes, networks and Compose stacks. Large community, lots of tutorials. The Community Edition (CE) is open source; there's also a paid Business Edition.
  </Card>
  <Card title="Dockhand">
    A younger, lean tool focused on Compose stacks. Comes with a Compose editor, deployments from Git repositories and vulnerability scans for images. License BSL 1.1: free for personal use, but not classic open source.
  </Card>
</Cards>

|                        | Portainer CE                            | Dockhand                                     |
| ---------------------- | --------------------------------------- | -------------------------------------------- |
| **Focus**              | Everything around Docker, very extensive | Compose stacks, tidy interface              |
| **Stacks from Git**    | Yes                                     | Yes, with webhooks and automatic sync        |
| **Multiple servers**   | Yes, through the Portainer Agent        | Yes, through socket, agent or TCP            |
| **Login**              | Own users, admin account at start       | Local users, SSO via OIDC                    |
| **License**            | Open source (zlib)                      | BSL 1.1, free for personal use               |
| **Maturity**           | Very established                        | Young, evolving quickly                      |

In short: if you want something proven with lots of tutorials online, take Portainer. If a more modern interface matters more to you and you mainly work with Compose stacks, try Dockhand. You only need one of the two.

<Callout type="warning" title="Docker socket means root access">
Both tools mount `/var/run/docker.sock`. Whoever controls the Docker socket can start any container, including one that mounts the server's entire file system. That's practically the same as root access to the server. So never expose the interface to the internet unprotected: reachable only through a VPN or from the home network, or additionally behind login protection like [Tinyauth](/en/setup/tinyauth/) or [Pocket ID](/en/setup/pocket-id/).
</Callout>

## Setting it up

<Steps>

<Step title="Create the stack folder">
Like every service, the interface gets its own folder under `__ROOT__`. Only create the folder for the tool you chose.

```bash
# Portainer
mkdir -p __ROOT__/portainer __DATA(portainer)__

# oder Dockhand
mkdir -p __ROOT__/dockhand __DATA(dockhand)__
```
</Step>

<Step title="Write compose.yaml">
The templates are adapted to your setup. With Traefik, the service gets labels and joins the `__NETWORK__` network; without a reverse proxy, the port is published directly.

**Portainer** stores its database, settings and the stacks created in the interface in `__DATA(portainer)__/data`:

<ServiceFiles id="portainer" />

**Dockhand** also stores its database in `__DATA(dockhand)__/data`:

<ServiceFiles id="dockhand" />

Portainer uses the `lts` tag (long-term support), the stable line with less frequent updates. How to keep your containers up to date is covered further down under "Updates with Dockhand".
</Step>

<Step title="Start">
Start the stack and take a quick look at the log to see whether everything comes up.

```bash
cd __ROOT__/portainer    # oder __ROOT__/dockhand
docker compose up -d
docker compose logs -f
```

Press `Ctrl+C` to leave the log view; the container keeps running.
</Step>

<Step title="Create the admin account">
Open the interface in the browser; with a reverse proxy at `https://portainer.__DOMAIN__` or `https://dockhand.__DOMAIN__`.

- **Portainer** asks for a **setup token** on first access, and then for a user name and password for the admin. The token protects a fresh installation from someone else taking it over first. You'll find it in the log:

  ```bash
  docker compose logs portainer | grep setup_token
  ```

  Do the setup right after starting: after five minutes without an admin account, Portainer locks itself for security reasons. Then `docker compose restart` helps, and the log shows a new token. Afterwards, choose the local environment ("Get Started").
- **Dockhand** starts without a login and shows the local Docker environment right away. Add a user under *Settings → Authentication* and then turn on login. Reload the page and check that Dockhand asks for a user name and password. Do this right after starting.

Use a long, random password and save it in your password manager.
</Step>

<Step title="Secure access">
The interface's own login is the first hurdle. Because root access sits behind it, a second one is worth it:

- **Internal only:** For Dockhand, this is already the default. With Traefik or Caddy, the template only lets addresses from the home network through; everyone else gets `403 Forbidden`. With Nginx Proxy Manager, you create an access list for this. In addition, you can have the subdomain resolve only on your home network or through a [VPN](/en/setup/vpn-wireguard/).
- **Login in front:** Attach a middleware like [Tinyauth](/en/setup/tinyauth/) to the router. Then everyone has to log in there first, and you can reach the interface on the go as well. The Tinyauth guide shows how to swap the home network rule for it.

A publicly reachable Portainer or Dockhand interface without extra protection is a rewarding target for attackers.
</Step>

</Steps>

## Updates with Dockhand

Dockhand can also take care of container updates for you. That's the easiest way to keep your services up to date, and our recommendation as long as you don't manage your stacks in Git. It also works for stacks you created with the CLI under `__ROOT__`.

- **Update check:** On a schedule (e.g. daily), Dockhand checks whether there are new images for your containers' tags. Containers with an update get a badge, and Dockhand sends you a notification if you like.
- **Automatic updates:** In a container's settings, you turn on automatic updates with a schedule of their own, e.g. at 3 a.m. Alternatively, this applies to all containers in the environment. Dockhand pulls the new image, recreates the container with an unchanged configuration and starts it.
- **With a security check:** If a vulnerability scanner is active (Grype or Trivy, in the settings), Dockhand first pulls the new image under a temporary name, scans it and only swaps if it meets your criteria, e.g. "no critical vulnerabilities" or "no more vulnerabilities than before". Otherwise the old container keeps running.
- **New versions as suggestions:** Automatic updates always stay within the tag in your `compose.yaml`. With `ghcr.io/pocket-id/pocket-id:v2`, you get all 2.x versions, but not version 3. If there's a newer tag, Dockhand shows it with the release notes. You then change the tag yourself, deliberately.

Here's how to go about it:

1. Let the update check monitor all containers and turn on notifications.
2. Turn on automatic updates for services whose tag only pins a major version (e.g. `:2`, `:v5`, `:lts`). There, updates bring bug fixes and security patches, but no big changes.
3. **Never update databases automatically.** Exclude containers like `postgres` or `mariadb`, most easily with the label `dockhand.update=false` in the `compose.yaml`. The templates on this site already set it for databases. Database updates belong with a fresh backup; see [Database won't start after an update](/en/wiki/database-version/).
4. Do bigger jumps (a new tag) by hand: read the release notes, back up, change the tag, `docker compose up -d`.

<Callout title="And Renovate?">
[Updates with Renovate](/en/setup/updates-renovate/) is **optional**. It's worth it if you keep your Compose files in Git ([Git deployments with Forgejo](/en/setup/git-deployments-forgejo/)): then Renovate suggests every new version as a pull request, and the Git history shows when which version arrived. For most homelabs, Dockhand is enough.
</Callout>

## CLI stacks and UI stacks

The interface also shows the stacks you started earlier with `docker compose` under `__ROOT__`. Docker uses labels to remember which containers belong to which Compose project, and that's exactly what both tools read. So starting, stopping, reading logs and restarting works for all stacks.

There's one difference when **editing**:

- **Stacks you created with the CLI** don't belong to the tool. Portainer shows them as external and doesn't let you change the `compose.yaml` ("Limited"). After all, the file lives in `__ROOT__/<app>/`, not in Portainer.
- **Stacks you create in the interface** are stored by the tool in its own data folder. In Portainer, they live under `__DATA(portainer)__/data/compose/<number>/`, with numbers instead of names. They don't show up in your folder structure under `__ROOT__`.

So don't mix the two worlds wildly. Pick one source of truth:

- **Files under `__ROOT__` stay in charge** (this site's recommendation): you create stacks over SSH or Git and use the interface for looking around, logs and restarts. Your backup of `__ROOT__` contains everything, and you can always carry on without the interface.
- **The interface is in charge:** you create all stacks there. That's convenient but ties you to the tool. Then be sure to back up its data folder too.

Either way, you don't have to start from scratch for new stacks. The [stack builder](/en/tools/stack-builder/) generates the `compose.yaml` for services from the catalog. If you take over someone else's `compose.yaml` from a project's docs, the [Compose explainer](/en/tools/compose-explainer/) tells you first what every line does.

If you want to roll out stacks from Git later, continue with [Git deployments with Forgejo](/en/setup/git-deployments-forgejo/). Dockhand and Portainer can also deploy stacks from a Git repository themselves. The Forgejo guide shows the way without an interface, which works with any tool.
