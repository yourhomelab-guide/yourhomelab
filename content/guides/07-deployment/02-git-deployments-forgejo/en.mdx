As long as you edit your `compose.yaml`files directly on the server, there's no version history. If an update breaks something, you won't know what the file looked like before. With Git, you get three things:

- **History:** Each change is a commit with a date and description. Use a command to go back.
- **A place for the truth:** You edit files on your computer using your editor, not via SSH with `nano`.
- **Automation:** Tools like [Renovate](/en/setup/updates-renovate/) can suggest updates to you as pull requests.

The repository is hosted on **Forgejo**, a lightweight Git platform that you host yourself. This way, your configurations don't end up with a third-party provider.

<OneWay />

## Which folder will be used as the repository?

The repository should contain the Compose files, not the data or the secrets. How this looks depends on your [directory structure](/en/wiki/directory-structure/):

- **Per stack (default):**  `__ROOT__`becomes the repository. You can exclude`.gitignore` the folders  `data/`and the `.env`files using .
- **Central:** Here, configuration and data are already separated. The repository is the `stack` folder`__ROOT__`; the data is stored separately in ```__DATA_ROOT__`. This works particularly well with Git because there are no large files in the repository folder. The `.git/exclude` file then just needs`.gitignore` to exclude the `.` `.env`files.

The commands below work for both versions.

<Callout type="warning" title="No Secrets in the Repository">
These `.env`files contain passwords and tokens. They should never be included in a Git repository—not even a private one. Once something is committed, it remains in the history forever. Instead, commit a file with`.env.example` placeholders so you know which variables a stack needs.
</Callout>

## Set Up

<Steps>

<Step title="Install Forgejo">
Like any other service, Forgejo runs as a stack. Git over SSH uses port 2222 so that it doesn't conflict with the server's SSH access.

```bash
mkdir -p __ROOT__/forgejo __DATA(forgejo)__
```

<ServiceFiles id="forgejo" />

```bash
cd __ROOT__/forgejo
docker compose up -d
```

Then open it`https://git.__DOMAIN__`. The first time you launch it, Forgejo displays the initial configuration:

- Database: **SQLite** is more than enough for a home lab.
- Server domain`git.__DOMAIN__`, base URL`https://git.__DOMAIN__/`, SSH port **2222**.
- **Disable self-registration** in the optional settings. Otherwise, anyone can create an account.
- Create your admin account there as well.

Port 2222 must be accessible on your home network. You don't need to forward this port on your router.
</Step>

<Step title="Create a repository in Forgejo">
In Forgejo, click the **+** icon in the upper-right corner → **New Repository**. Enter a name (for example)`homelab`, set visibility **to private**. Leave the repository empty: no README, no files`.gitignore`, no license. The files will come directly from the server.

In the commands below,  stands `DEIN-NAME`for your Forgejo username.
</Step>

<Step title="Write a .gitignore file">
This file specifies`.gitignore` what Git ignores. It comes right after `__ROOT__`.

```bash
cd __ROOT__
cat > .gitignore <<'EOF'
# Secrets: never commit
.env
*.env

# Persistent data of each stack
data/
EOF
```

`data/` Without a leading slash, this matches any folder with that name—such as `traefik/data/`,  and`vaultwarden/data/` so on. This also excludes Forgejo's own data.

For each stack with , create`.env``.env.example` a : the same variables, but without actual values.
</Step>

<Step title="Create a repository and push">
Set up Git with your name and create the repository. Before making your first commit`git status`, use to verify that neither `.env`nor `data/`folder appears in the list.

```bash
git config --global user.name "Dein Name"
git config --global user.email "__EMAIL__"

cd __ROOT__
git init -b main
git add .
git status
git commit -m "Initial import"
```

To make your first push, use HTTPS and enter your Forgejo username and password:

```bash
git push https://git.__DOMAIN__/DEIN-NAME/homelab.git main
```

After that, you'll see all the Compose files in the Forgejo web interface.
</Step>

<Step title="The server is assigned a deploy key">
From now on, the server should only **have read access**. To that end, it will be assigned its own SSH key, known as a "deploy key." This key is valid only for this one repository.

```bash
ssh-keygen -t ed25519 -f ~/.ssh/forgejo_deploy -N "" -C "homelab-server"
cat ~/.ssh/forgejo_deploy.pub
```

Copy the line that appears. In Forgejo: Repository → **Settings** → **Deploy Keys** → **Add Deploy Key**. Do not check the "Write access" box.

Because Forgejo runs on the same server, the server connects directly via `localhost`. This bypasses DNS and routers. To do this, add`~/.ssh/config` an entry to :

```bash
cat >> ~/.ssh/config <<'EOF'

Host forgejo-local
  HostName localhost
  Port 2222
  User git
  IdentityFile ~/.ssh/forgejo_deploy
EOF
```

Now link the local repository to Forgejo:

```bash
cd __ROOT__
git remote add origin forgejo-local:DEIN-NAME/homelab.git
git fetch origin
git branch --set-upstream-to=origin/main main
git pull
```

The first time you connect, SSH will ask if you trust the host. Reply with `yes`.  It `git pull`should display "Already up to date."
</Step>

<Step title="Clone on your computer">
On your laptop or PC, save your regular public SSH key in Forgejo: top right → **Settings** → **SSH/GPG Keys**. Then clone the repository:

```bash
git clone ssh://git@git.__DOMAIN__:2222/DEIN-NAME/homelab.git
```

From now on, here’s what you do: Make changes here, commit them, and push them. You no longer edit the Compose files directly on the server; otherwise, conflicts will arise the next time you `git pull`. You’ll continue to maintain only the `.env`files on the server. To create a new stack, create a folder for it in the repository. The [Stack Builder](/en/werkzeuge/stack-builder/) will generate`compose.yaml` the appropriate one for you, and the [Compose Explainer](/en/werkzeuge/compose-erklaerer/) will walk you through a third-party one from a project documentation.
</Step>

<Step title="Deployment script on the server">
In the simplest case, the deployment is just  `git pull`and then  `docker compose up -d`in each stack folder.  `up -d`is harmless for stacks that haven't changed: Docker leaves containers whose configuration has remained the same alone and only recreates the ones that have changed.

Create the script outside the repository so that it doesn't overwrite itself while it's running:

```bash
mkdir -p ~/bin
cat > ~/bin/homelab-deploy <<'EOF'
#!/usr/bin/env bash
# Pull the latest compose files and apply them to every stack.
set -euo pipefail

cd __ROOT__
git pull --ff-only

for dir in */; do
  [ -f "$dir/compose.yaml" ] || continue
  # An empty file named .skip keeps a stack out of automatic deploys.
  [ -f "$dir/.skip" ] && continue
  echo "==> $dir"
  (cd "$dir" && docker compose up -d --remove-orphans)
done
EOF
chmod +x ~/bin/homelab-deploy
```

Try it out manually:

```bash
~/bin/homelab-deploy
```

`--ff-only` Ensures that the script aborts instead of merging changes if someone has made direct changes on the server after all.  `--remove-orphans`Removes containers that you have deleted`compose.yaml` from a  . Stacks that are supposed to remain stopped have an empty file  placed in`.skip` their folder.
</Step>

<Step title="Perform regularly">
To avoid having to connect to the server via SSH after a push, set the script to run regularly using cron. Open your crontab:

```bash
crontab -e
```

and add this line. It checks for changes every 15 minutes:

```bash
*/15 * * * * $HOME/bin/homelab-deploy >> $HOME/homelab-deploy.log 2>&1
```

From now on, here's your workflow: edit the file, commit, push, and wait a few minutes. You can see what happened in the log:

```bash
tail -n 50 ~/homelab-deploy.log
```
</Step>

<Step title="Advanced: Deploy Using Forgejo Actions">
Instead of checking every 15 minutes, Forgejo can start the deployment immediately after each push. This is made possible by **Forgejo Actions**, a CI system similar to GitHub Actions. The jobs are executed by a separate program, the **Forgejo Runner**.

The general process:

1. Enable actions for the repository in its settings.
2. Install and register the Forgejo Runner on the server. To deploy on the same server, the Runner needs a label that runs jobs directly on the host instead of in a container (for example `homelab:host`). It will then run as your user, who is`docker` a member of the  group. The steps are outlined in the [Runner documentation](https://forgejo.org/docs/latest/admin/actions/runner-installation/).
3. Add a workflow to the repository that calls the`main` script every time there's a push, for example`.forgejo/workflows/deploy.yaml`:

```yaml
on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: homelab
    steps:
      - run: ~/bin/homelab-deploy
```

After that, you can delete the cron entry.

<Callout type="warning" title="Runner with Host Access">
A runner that runs directly on the host and has permission to control Docker effectively has root privileges. Therefore, register it only for your own repository—not for the entire instance—and do not allow external users to create workflows.
</Callout>
</Step>

</Steps>

## When something goes wrong

- **`git pull` Stops with the message “Not possible to fast-forward”:** A file on the server has been modified that was also modified in the repository. Use  `git status`and  to see`git diff` which file it is. Apply the change to your repository on your computer and revert`git checkout -- <datei>` the file on the server using .
- **An update failed:** `git revert`Undo the commit on your computer using  and push it. The next time the script runs, it will roll back to the old version.
- **New stack won't start:** The `.env`. is probably missing. You'll need to create it manually on the server, for example from the `.env.example`. If that's not the problem, try [troubleshooting: first steps](/en/wiki/first-steps/).
