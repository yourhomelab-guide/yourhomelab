As long as you edit your `compose.yaml` files directly on the server, there's no history. When an update breaks something, you no longer know what the file looked like before. With Git you get three things:

- **History:** every change is a commit with a date and a description. Going back takes one command.
- **One source of truth:** you edit files on your computer in your editor, not with `nano` over SSH.
- **Automation:** optionally, [Renovate](/en/setup/updates-renovate/) suggests new versions to you as pull requests.

The repository lives in **Forgejo**, a lean Git platform you host yourself. That way your configurations don't end up at a third-party provider.

<OneWay />

## Which folder becomes the repository?

The repository holds the Compose files, not the data and not the secrets. What that looks like depends on your [directory structure](/en/wiki/directory-structure/):

- **Per stack (default):** `__ROOT__` becomes the repository. You exclude the `data/` folders and the `.env` files with a `.gitignore`.
- **Central:** here configuration and data are already separate. The repository is the stack folder `__ROOT__`, and the data lives outside it under `__DATA_ROOT__`. That suits Git especially well, because nothing big sits in the repo folder. The `.gitignore` then only has to exclude the `.env` files.

The commands below work for both variants.

<Callout type="warning" title="No secrets in the repository">
The `.env` files contain passwords and tokens. They never belong in a Git repository, not even a private one. Whatever is committed once stays in the history forever. Commit a `.env.example` with placeholders instead, so you know which variables a stack needs.
</Callout>

## Setting it up

<Steps>

<Step title="Install Forgejo">
Forgejo runs as a stack like any other service. Git over SSH uses port 2222 so it doesn't clash with the server's own SSH access.

```bash
mkdir -p __ROOT__/forgejo __DATA(forgejo)__
```

<ServiceFiles id="forgejo" />

```bash
cd __ROOT__/forgejo
docker compose up -d
```

Then open `https://git.__DOMAIN__`. On first access, Forgejo shows the initial configuration:

- Database: **SQLite** is perfectly fine for a homelab.
- Server domain `git.__DOMAIN__`, base URL `https://git.__DOMAIN__/`, SSH port **2222**.
- In the optional settings, **disable self-registration**. Otherwise anyone can create an account.
- Create your admin account there as well.

Do this right after the first start: until then, anyone who can reach the page can complete the installation. Port 2222 must be reachable on your home network. You don't need port forwarding on the router for it.
</Step>

<Step title="Create the repository in Forgejo">
In Forgejo, click **+** → **New Repository** at the top right. Name it `homelab`, for example, with visibility **private**. Leave the repository empty: no README, no `.gitignore`, no license. The files will come from the server in a moment.

In the commands below, `DEIN-NAME` stands for your Forgejo user name.
</Step>

<Step title="Write the .gitignore">
The `.gitignore` defines what Git ignores. It goes directly into `__ROOT__`.

```bash
cd __ROOT__
cat > .gitignore <<'EOF'
# Secrets: never commit
.env
*.env

# Persistent data of each stack
data/
EOF
```

`data/` without a leading slash matches every folder with that name, so `traefik/data/`, `vaultwarden/data/` and so on. That also excludes Forgejo's own data.

For every stack with a `.env`, create a `.env.example`: the same variables, but without real values.
</Step>

<Step title="Create the repository and push">
Set up Git once with your name and create the repository. Before the first commit, check with `git status` that no `.env` and no `data/` folder shows up in the list.

```bash
git config --global user.name "Dein Name"
git config --global user.email "__EMAIL__"

cd __ROOT__
git init -b main
git add .
git status
git commit -m "Initial import"
```

Use your own name in the first line. Do the first push over HTTPS with your Forgejo user name and password:

```bash
git push https://git.__DOMAIN__/DEIN-NAME/homelab.git main
```

Afterwards you'll see all Compose files in Forgejo's web interface.
</Step>

<Step title="Give the server a deploy key">
From now on, the server should only **read**. For that, it gets an SSH key of its own, a so-called deploy key. It only works for this one repository.

```bash
ssh-keygen -t ed25519 -f ~/.ssh/forgejo_deploy -N "" -C "homelab-server"
cat ~/.ssh/forgejo_deploy.pub
```

Copy the printed line. In Forgejo: repository → **Settings** → **Deploy Keys** → **Add Deploy Key**. Don't check write access.

Because Forgejo runs on the same server, the server connects directly through `localhost`. That bypasses DNS and the router. Add an entry to `~/.ssh/config` for it:

```bash
cat >> ~/.ssh/config <<'EOF'

Host forgejo-local
  HostName localhost
  Port 2222
  User git
  IdentityFile ~/.ssh/forgejo_deploy
EOF
```

Now link the local repository with Forgejo:

```bash
cd __ROOT__
git remote add origin forgejo-local:DEIN-NAME/homelab.git
git fetch origin
git branch --set-upstream-to=origin/main main
git pull
```

On the first connection, SSH asks whether you trust the host. Answer `yes`. `git pull` should report "Already up to date".
</Step>

<Step title="Clone on your computer">
On your laptop or PC, add your regular public SSH key in Forgejo: top right → **Settings** → **SSH / GPG Keys**. Then clone the repository:

```bash
git clone ssh://git@git.__DOMAIN__:2222/DEIN-NAME/homelab.git
```

From now on: you make changes here, commit and push them. You no longer edit the Compose files directly on the server, otherwise you'll get conflicts on the next `git pull`. Only the `.env` files are still maintained on the server. You create a new stack as a folder in the repository. The [stack builder](/en/tools/stack-builder/) generates the matching `compose.yaml`, and the [Compose explainer](/en/tools/compose-explainer/) explains someone else's from a project's docs.
</Step>

<Step title="Deploy script on the server">
In the simplest case, the deployment is just `git pull` followed by `docker compose up -d` in every stack folder. `up -d` is harmless for stacks without changes: Docker leaves containers alone whose configuration stayed the same and only recreates changed ones.

Create the script outside the repository so it doesn't overwrite itself while it runs:

```bash
mkdir -p ~/bin
cat > ~/bin/homelab-deploy <<'EOF'
#!/usr/bin/env bash
# Pull the latest compose files and apply them to every stack.
set -euo pipefail

cd __ROOT__
git pull --ff-only

for dir in */; do
  [ -f "$dir/compose.yaml" ] || continue
  # An empty file named .skip keeps a stack out of automatic deploys.
  [ -f "$dir/.skip" ] && continue
  echo "==> $dir"
  (cd "$dir" && docker compose up -d --remove-orphans)
done
EOF
chmod +x ~/bin/homelab-deploy
```

Test it once by hand:

```bash
~/bin/homelab-deploy
```

`--ff-only` makes the script stop instead of mixing changes in case someone changed something directly on the server after all. `--remove-orphans` cleans up containers you deleted from a `compose.yaml`. Stacks that should stay stopped get an empty `.skip` file in their folder.
</Step>

<Step title="Run it regularly">
So you don't have to SSH into the server after every push, let the script run regularly with cron. Open your crontab:

```bash
crontab -e
```

and add this line. It checks for changes every 15 minutes:

```bash
*/15 * * * * $HOME/bin/homelab-deploy >> $HOME/homelab-deploy.log 2>&1
```

From now on, your workflow is: change a file, commit, push, wait a few minutes. The log shows what happened:

```bash
tail -n 50 ~/homelab-deploy.log
```
</Step>

<Step title="Advanced: deploy with Forgejo Actions">
Instead of checking every 15 minutes, Forgejo can start the deployment right after each push. That's what **Forgejo Actions** is for, a CI system in the style of GitHub Actions. The jobs are run by a separate program, the **Forgejo Runner**.

The rough steps:

1. Turn on Actions in the repository's settings.
2. Install and register the Forgejo Runner on the server. For a deployment on the same server, the runner needs a label that runs jobs directly on the host instead of in a container (for example `homelab:host`). It then runs as your user, who is in the `docker` group. The steps are in the [runner documentation](https://forgejo.org/docs/latest/admin/actions/runner-installation/).
3. Put a workflow into the repository that calls the script on every push to `main`, for example `.forgejo/workflows/deploy.yaml`:

```yaml
on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: homelab
    steps:
      - run: ~/bin/homelab-deploy
```

Then you can remove the cron entry.

<Callout type="warning" title="Runner with host access">
A runner that runs directly on the host and may control Docker practically has root rights. So only register it for your own repository, not for the whole instance, and don't let other users create workflows.
</Callout>
</Step>

</Steps>

## When something goes wrong

- **`git pull` stops with "Not possible to fast-forward":** a file was changed on the server that was also changed in the repository. `git status` and `git diff` show you what it is. Take the change over into your repository on your computer and reset the file on the server with `git checkout -- <file>`.
- **An update is broken:** undo the commit on your computer with `git revert` and push. On the next run, the script rolls out the old version again.
- **A new stack doesn't start:** the `.env` is probably missing. You create it by hand on the server, for example from the `.env.example`. If that's not it, [Troubleshooting: first steps](/en/wiki/first-steps/) helps.
