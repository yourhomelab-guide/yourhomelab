[Home Assistant](https://www.home-assistant.io) is the hub of your smart home. It talks to thousands of devices and services, from radiator thermostats to smart plugs to weather stations, and connects them through automations. Most of it runs locally, without a detour through a manufacturer's cloud.

Before you start, there's a decision that doesn't come up with other services: **how** you install Home Assistant.

## Home Assistant OS in a VM, or a container?

Home Assistant comes in two officially supported variants:

- **Home Assistant OS (HAOS)** is a complete, lean operating system just for Home Assistant. It takes care of updates and backups itself and comes with an app store, the **apps** (formerly called "add-ons"). With them, you install things like Zigbee2MQTT, an MQTT broker or a code editor with one click. On a homelab server, HAOS runs in a **virtual machine**, for example under [Proxmox VE](/en/wiki/proxmox-ve/).
- **Home Assistant Container** is just the application as a Docker image. It fits exactly the path this site takes: a `compose.yaml`, data under `__ROOT__`, updates through a new image. In return, there are no apps. Whatever you need, an MQTT broker for example, you run as a separate container next to it.

| | HAOS in a VM | Container |
|---|---|---|
| Updates | with a click in the interface, including the operating system | new image tag, like any stack |
| Apps (add-ons) | yes | no, extra services as separate containers |
| Backup | built in, restorable as a whole | built in for Home Assistant, extra services separately |
| Resources | its own VM, at least 2 GB RAM and 2 CPU cores | runs alongside, usually needs a few hundred MB of RAM |
| Requirement | a hypervisor like Proxmox | Docker, which you already have |
| Some features like Thread or Z-Wave | set up ready-made through apps | set up yourself |

**The honest recommendation:** if your server runs Proxmox or you're just starting out, use **HAOS in a VM**. It's the variant the Home Assistant project recommends. Most tutorials and forum posts assume it, and updates are little work. If, on the other hand, your server is a plain Linux with Docker, as in the guides on this site, and you don't want to run a VM for it, the **container** is a good choice. You give up the apps but gain a uniform way of running all services.

For HAOS under Proxmox, download the `qcow2` image for KVM/Proxmox from the [official instructions](https://www.home-assistant.io/installation/alternative), import it as the disk of a new VM and set the firmware to UEFI (OVMF). Home Assistant only boots with UEFI. From this guide, you then only need the steps on the reverse proxy, the trusted proxies and the USB stick. The proxy then forwards to the VM's IP instead of `host.docker.internal`, the UFW rules on the Docker server don't apply, and as the trusted proxy you enter the IP of the server your reverse proxy runs on.

The following steps describe the **container**.

<Steps>

<Step title="Why host networking?">
Normally, every container sits in its own Docker network, and only published ports are reachable. But Home Assistant often finds devices on your home network by itself, for example through **mDNS** (devices announce themselves by name on the local network) or **SSDP/UPnP**. This discovery works with broadcast and multicast, and those don't get out of a normal Docker network.

That's why Home Assistant runs with `network_mode: host`. The container then shares the network with the server itself. There's no port forwarding; Home Assistant listens directly on the server's port `8123`.

That has two consequences:

- Home Assistant **can't** join your proxy network `__NETWORK__`. A container with host networking can't be in any other network. So the reverse proxy has to reach Home Assistant through the server's address. The step on the reverse proxy shows how.
- Your **firewall** applies to Home Assistant like to any program running directly on the server. Port `8123` is closed until you open it.

For this reason, there's no ready-made template for Home Assistant under services: the templates automatically put every service into the proxy network, which doesn't work with host networking. So you write the `compose.yaml` yourself.
</Step>

<Step title="Create the folder and compose.yaml">
```bash
mkdir -p __ROOT__/home-assistant __DATA(home-assistant)__/config
cd __ROOT__/home-assistant
nano compose.yaml
```

```yaml
services:
  home-assistant:
    image: ghcr.io/home-assistant/home-assistant:2026.9
    container_name: home-assistant
    restart: unless-stopped
    # Required for device discovery (mDNS, SSDP) in your LAN
    network_mode: host
    # Give Home Assistant time to close its database on shutdown
    stop_grace_period: 60s
    environment:
      - TZ=__TZ__
    volumes:
      - __DATA(home-assistant)__/config:/config
      - /etc/localtime:/etc/localtime:ro
      # Only needed for Bluetooth devices
      - /run/dbus:/run/dbus:ro
```

Home Assistant releases a new version every month. The `2026.9` tag only gets that month's bug fixes. For the jump to the next version, you change the tag deliberately, read the notes on breaking changes in the [release blog](https://www.home-assistant.io/blog/categories/release-notes/) first and restart. [Dockhand](/en/setup/portainer-dockhand/) shows you new tags as suggestions. If you keep your Compose files in Git, [Renovate](/en/setup/updates-renovate/) can optionally open a pull request for it.

The official template also sets `privileged: true`. That gives the container almost full access to the server. You don't need it as long as you pass through individual devices specifically, as shown in the step on the USB stick.
</Step>

<Step title="Open the firewall and start">
For the initial setup, open port `8123` for your home network. Adjust the network to yours:

```bash
sudo ufw allow from 192.168.1.0/24 to any port 8123 proto tcp
```

Then start the container:

```bash
docker compose up -d
docker compose logs -f home-assistant
```

In the browser, open `http://__SERVER_IP__:8123`, with your server's IP. A wizard creates your account (do this right away; until then, anyone on the network can create it) and asks for location, time zone and units. Afterwards, Home Assistant already shows the devices it found on the network.
</Step>

<Step title="Connect the reverse proxy">
For HTTPS and a nice address, put Home Assistant behind your reverse proxy. Because it runs in the host network, the proxy needs a way to the server itself. The entry `host.docker.internal:host-gateway` gives you that: it makes the server's address reachable in the proxy container under the name `host.docker.internal`.

**Traefik:** add this to the `traefik` service in `__ROOT__/traefik/compose.yaml`:

```yaml
    extra_hosts:
      - host.docker.internal:host-gateway
```

Then Home Assistant gets labels in its `compose.yaml`, but **no** `networks:`. Traefik detects the host network and forwards to `host.docker.internal`:

```yaml
    labels:
      - traefik.enable=true
      - traefik.http.routers.home-assistant.rule=Host(`home.__DOMAIN__`)
      - traefik.http.routers.home-assistant.entrypoints=websecure
      - traefik.http.routers.home-assistant.tls.certresolver=le
      - traefik.http.services.home-assistant.loadbalancer.server.port=8123
```

**Caddy:** add `extra_hosts` as above in `__ROOT__/caddy/compose.yaml` and forward in the Caddyfile:

```
home.__DOMAIN__ {
  reverse_proxy host.docker.internal:8123
}
```

**Nginx Proxy Manager:** create a proxy host with the domain `home.__DOMAIN__`. As the forward host, enter your server's IP on the home network, here `__SERVER_IP__`, with port `8123`. Turn on **Websockets Support**; without it, the interface doesn't load.

Then restart the proxy (`docker compose up -d` in its folder) so it picks up the change.

The firewall is still missing. The proxy's requests come from the Docker network `__NETWORK__`, not from your home network. Read out this network's address range:

```bash
docker network inspect __NETWORK__ --format '{{range .IPAM.Config}}{{.Subnet}}{{end}}'
```

The output looks something like `172.18.0.0/16`. Allow this range on port `8123`:

```bash
sudo ufw allow from 172.18.0.0/16 to any port 8123 proto tcp
```
</Step>

<Step title="Set trusted proxies in Home Assistant">
If you now open Home Assistant through the domain, you get an error **400: Bad Request**. That's intended: Home Assistant doesn't accept requests from a proxy you haven't explicitly trusted. Otherwise any device could claim to speak on behalf of another.

So open Home Assistant once more directly at `http://__SERVER_IP__:8123` and go to **Settings → System → Network**. In the **HTTP server** section, turn on **Trust X-Forwarded-For** and enter the address range from before under **Trusted proxies**, so something like `172.18.0.0/16`. When you save, Home Assistant restarts. Afterwards you have to confirm the new settings within five minutes, otherwise it reverts them.

The [docs on the HTTP integration](https://www.home-assistant.io/integrations/http/) describe the options in detail.

<Callout title="Older versions: configuration.yaml">
Up to version 2026.7, these settings lived in the `configuration.yaml` file in the `__DATA(home-assistant)__/config` folder. Many tutorials online still show this block:

```yaml
http:
  use_x_forwarded_for: true
  trusted_proxies:
    - 172.18.0.0/16
```

From version 2026.8, Home Assistant takes over an existing block into the interface during the update and asks you under **Settings → System → Repairs** to delete it from the file afterwards.
</Callout>

Home Assistant should now load at `https://home.__DOMAIN__`. If the proxy reports `502 Bad Gateway` instead, it can't reach port `8123`. Usually the firewall rule from before is missing; more under [Bad Gateway and 404 from the proxy](/en/wiki/bad-gateway/). Finally, enter the address as the Home Assistant URL under **Settings → System → Network** and use it in the companion app on your phone too. You can delete the rule for your home network on port `8123` afterwards if you no longer need direct access (`sudo ufw status numbered`, then `sudo ufw delete <number>`).

If Home Assistant should also be reachable on the go, the same considerations apply as for any service: a [VPN](/en/setup/vpn-wireguard/) is the safest way. Login protection like Tinyauth in front of Home Assistant doesn't get along with the companion app.
</Step>

<Step title="Pass through a USB stick for Zigbee (optional)">
Many smart home devices communicate via **Zigbee**, an energy-efficient radio standard. For that, you need a USB stick as the radio receiver, a so-called coordinator. You pass it through to the container specifically.

Ideally, plug the stick in with a short USB extension cable. Directly on the server, noise from USB 3 ports and disks noticeably disturbs the radio. Then look up the stick's stable name:

```bash
ls -l /dev/serial/by-id/
```

Use the path from `/dev/serial/by-id/`, not `/dev/ttyUSB0`. The number can change after a reboot; the name under `by-id` stays the same. Add it to the `compose.yaml` under `home-assistant`; the name here is just an example:

```yaml
    devices:
      - /dev/serial/by-id/usb-Example_Zigbee_Stick_1234-if00-port0:/dev/ttyUSB0
```

After `docker compose up -d`, set up the **Zigbee Home Automation (ZHA)** integration in Home Assistant and enter `/dev/ttyUSB0` as the device. The alternative, Zigbee2MQTT, additionally needs an MQTT broker and then runs as a separate container.

With HAOS in a Proxmox VM, you pass the stick through to the VM in Proxmox instead: in the VM under **Hardware → Add → USB Device**, ideally by vendor and device ID. Home Assistant then usually finds it by itself.
</Step>

<Step title="Backup">
Everything that makes up Home Assistant lives in `__DATA(home-assistant)__/config`: settings, automations, devices and the database with the history. With [borgmatic](/en/setup/backups-borgmatic/), the folder is included automatically because it's under `__ROOT__`.

The database is an SQLite file that's written to constantly. So also set up the built-in automatic backups under **Settings → System → Backups**. Home Assistant stores them in a consistent state in the configuration folder, and borgmatic backs them up along with everything else. Note the key Home Assistant shows you there in your password manager. Without it, the backups can't be restored.
</Step>

</Steps>
