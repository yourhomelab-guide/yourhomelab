Every device constantly asks for addresses: Where is this`example.com`, where is that`ads.irgendwas.net`? A **DNS server** (Domain Name System, the Internet's "phone book"; see [DNS & Domains](/en/wiki/dns-domains/)) answers these questions. Usually, this is your router or your Internet service provider.

[AdGuard Home](https://github.com/AdguardTeam/AdGuardHome) takes on this role in your home network. If a device requests a known advertising or tracking address, AdGuard Home responds with “does not exist.” The ad isn’t even loaded in the first place. This works on all devices, even those where you can’t install an ad blocker, such as on a smart TV or in apps. Plus, you can see which device is making calls, when, and to where.

<Callout title="What AdGuard Home Can't Do">
A DNS blocker only sees domain names, not the content of a page. Ads that come from the same address as the actual content (for example, on YouTube) slip through. That’s why an additional blocker like uBlock Origin is still useful for your browser.
</Callout>

<OneWay />

The best-known alternative is [Pi-hole](https://pi-hole.net). It essentially does the same thing and has a large community. AdGuard Home offers encrypted DNS (DNS-over-HTTPS) and a modern interface without any additional packages, and runs as a single container. Both are good choices; the steps outlined here apply to AdGuard Home.

<Steps>

<Step title="Open Port 53 (Ubuntu only)">
DNS runs on **port 53**, via UDP and TCP. The container must listen on this port on the server so that other devices can reach it. However, on Ubuntu, **systemd-resolved** is already listening on that port: this is the service that resolves names for the server itself. It starts a small local DNS server, the **stub listener**, at the address `127.0.0.53:53`. Docker is then unable to expose port 53 and `address already in use`exits with .

First, check whether the port is in use:

```bash
sudo ss -tulpn | grep ':53 '
```

If no output appears, the port is free, and you can move on to the next step. On Debian, this is usually the case because systemd-resolved isn't installed there in the first place. If you see this`systemd-resolve`, just disable the stub listener. systemd-resolved itself will continue to run.

```bash
sudo mkdir -p /etc/systemd/resolved.conf.d
printf '[Resolve]\nDNSStubListener=no\n' | sudo tee /etc/systemd/resolved.conf.d/no-stub.conf
sudo ln -sf /run/systemd/resolve/resolv.conf /etc/resolv.conf
sudo systemctl restart systemd-resolved
```

What the three commands do:

- The file in  `/etc/systemd/resolved.conf.d/`is set to `DNSStubListener=no`. systemd-resolved will then`127.0.0.53:53` no longer open . It's better to create a separate file in this folder than to modify the main file, because package updates won't overwrite it.
- `/etc/resolv.conf` tells all programs which DNS server to use. On Ubuntu, it points to the stub server by default (`nameserver 127.0.0.53`). Without the stub server, this would be ineffective. The link to  instead directly `/run/systemd/resolve/resolv.conf`enters the actual DNS servers that you specified when [setting up the static IP](/en/setup/static-ip-hostname/)—usually your router.
- The system will apply the setting when it restarts.

Next, verify that port 53 is open and that the server is still resolving names:

```bash
sudo ss -tulpn | grep ':53 '
ping -c1 debian.org
```

So the server itself continues to query your router or a public DNS server—not AdGuard Home. This is by design: even if the container isn't running, the server can still load updates and images. For more information on occupied ports, see "[Port Occupied](/en/wiki/port-in-use/)."
</Step>

<Step title="Run through the setup wizard">
When you launch AdGuard Home for the first time, it displays a setup wizard on port 3000. Open it`https://adguard.__DOMAIN__`. Without a reverse proxy, you can access it using your server's IP address and the port listed in the `compose.yaml`.

The most important point is on the second page:

| Field | Value |
| --- | --- |
| Admin Web Interface: Network Interface | All Interfaces |
| Admin Web Interface: Port | **3,000** (the proposed number is 80) |
| DNS Server: Network Interface | All Interfaces |
| DNS Server: Port | 53 |

Why 3000? The wizard runs on port 3000, and the finished interface runs on port 80 by default. However, your reverse proxy always forwards traffic to port 3000. If the interface stays on port 3000, the same address will work both before and after setup. “All interfaces” refers to the inside of the container. The configuration `compose.yaml`determines which ports are accessible from the outside.

Next, create a username and password. Use a long password from your password manager. The last page explains how to set up devices. You'll do that right away through the router.

If you accidentally selected port 80, the interface will no longer be accessible. In that case, stop the container, change the`http:` line in  `address: 0.0.0.0:80`to  `__DATA(adguard-home)__/conf/AdGuardHome.yaml`under , and`address: 0.0.0.0:3000` restart it:

```bash
cd __ROOT__/adguard-home
docker compose stop
sudo nano __DATA(adguard-home)__/conf/AdGuardHome.yaml
docker compose start
```
</Step>

<Step title="Select Upstream DNS and Blocklists">
AdGuard Home only responds to requests it blocks itself. It forwards all other requests to an **upstream DNS server**. Under “Settings → DNS Settings,” an encrypted server is already listed (DNS-over-HTTPS, identifiable by `https://`). Your internet service provider will then no longer be able to see which domain names you’re resolving. You can leave it as is or enter a different provider. Use “Test Upstreams” to check if it responds.

The **blocklists** do the actual work. Under “Filters → DNS Blocklists,” the “AdGuard DNS filter” list is already active. By selecting “Add Blocklist → Select from List,” you can add additional lists by checking the boxes—for example, one of the HaGeZi lists. AdGuard Home updates them automatically.

More lists doesn't automatically mean better. Every list can sometimes block something you need, such as a link in a newsletter email or an app's login page. Start with one or two lists. If something doesn't work, look up the address in the "Query Log" and unblock it there with a single click. AdGuard Home creates an exception rule for this under “Filters → Custom Filter Rules.”
</Step>

<Step title="Try it now">
Before you reconfigure the entire network, test the server specifically. The tool `dig`queries a specific DNS server. It's included in the package`dnsutils`. Run the commands on the server or on another Linux computer on your home network, substituting your server's IP address:

```bash
sudo apt install dnsutils
dig @192.168.1.10 debian.org +short
dig @192.168.1.10 doubleclick.net +short
```

The first request returns normal IP addresses. The second targets a known advertising domain and should return`0.0.0.0`: It was blocked. You can see both requests in the "Query Log." On Windows, you can do the same with `nslookup doubleclick.net 192.168.1.10`.

If you don't receive a response (`connection timed out`), the container isn't running or port 53 isn't exposed. Check  `docker compose ps`and the logs, as described in [Troubleshooting: First Steps](/en/wiki/first-steps/).
</Step>

<Step title="Set Up the Router as a DNS Server">
To ensure that all devices use AdGuard Home, the router should distribute it. The devices receive their network settings, including the DNS server, from the router via **DHCP**. If you enter your server’s IP address there, all devices will automatically query AdGuard Home. Depending on the router, this setting is called “Local DNS Server,” “DNS Server for DHCP,” or something similar.

On a **FRITZ!Box,** you'll find it roughly here (it may vary slightly depending on the FRITZ!OS version):

- "Home Network → Network → Network Settings → IP Addresses → IPv4 Settings." There, enter your server's IP address under "Local DNS Server."
- In the IPv6 settings next to it, there is a corresponding field for DNSv6. If your network uses IPv6, the FRITZ!Box will otherwise continue to act as a DNS server, and some devices will bypass AdGuard Home through it.

Do **not** configure the DNS server under "Internet → Access Data → DNS Server." If you do, all requests would still be routed through AdGuard Home, but they would always be sent on behalf of the FRITZ!Box. You would then only see a single device in the log.

The devices won't adopt the new DNS server until they refresh their DHCP settings. The quickest way to do this is to briefly turn Wi-Fi off and then back on. After a few minutes, the devices will appear under "Clients" in the dashboard.

Some devices and browsers bypass the router's DNS server—for example, by using a hard-coded, encrypted DNS. These do not appear in the log. This is normal and can only be changed on the device in question.
</Step>

<Step title="Plan for Downtime">
Now your entire home network depends on your server. **If the server is down or the container is stopped, DNS stops working on your home network.** Websites won’t load, and apps report “no connection,” even though the Internet is actually working. This can happen faster than you think: an update that requires a restart, a power outage, or maintenance.

So think about what you want to happen next:

- **Second DNS Server in the Router**: Many routers allow a second entry. If you enter a public DNS server there, your network will continue to work even if AdGuard Home goes down. The catch: Devices use the second server not only in an emergency, but also from time to time. That means ads will get through there.
- **Second AdGuard Home instance**: A second instance on a different device, such as a Raspberry Pi, with the same settings. You'll need to enter both IP addresses in the router. This is the cleanest solution, but it requires more maintenance.
- **Contingency Plan**: Accept that the service may go down, and write down how to reset the DNS entry in your router. Keep this note in a place where someone else in your household can find it (see [documentation](/en/wiki/documentation/)).

For now, the emergency plan is fine. Also, add AdGuard Home to [Uptime Kuma](/en/setup/uptime-kuma/). The "DNS" monitor type regularly queries the server for a name and alerts you if there is no response.
</Step>

</Steps>

## What happens next?

- **Local Addresses**: Under "Filter → DNS Redirects," you can configure the settings to point to`*.__DOMAIN__` your server's internal IP address. Devices on your home network can then access your services directly, without going through the Internet.
- **Naming clients**: Under “Settings → Client Settings,” you can assign names to devices and set different rules for individual devices—such as stricter filters for children’s devices.
- **Dashboard**: The number of blocked requests is displayed right on your [home](/en/setup/dashboard-homepage/) page.
- **Backup**: Your settings are stored in `__DATA(adguard-home)__/conf`. They are [backed](/en/setup/backups-borgmatic/)`__ROOT__`[ up](/en/setup/backups-borgmatic/) along with the rest of .
