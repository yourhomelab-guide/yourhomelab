Every device constantly asks for addresses: where is `example.com`, where is `ads.irgendwas.net`? A **DNS server** answers these questions (Domain Name System, the "phone book" of the internet; see [DNS & domains](/en/wiki/dns-domains/)). Usually that's your router or your internet provider.

[AdGuard Home](https://github.com/AdguardTeam/AdGuardHome) takes over this role on your home network. When a device asks for a known ad or tracking address, AdGuard Home answers "doesn't exist". The ad is never even loaded. This works on all devices, including those where you can't install an ad blocker, like the smart TV or inside apps. On the side, you see which device calls home where and when.

<Callout title="What AdGuard Home can't do">
A DNS blocker only sees domain names, not the content of a page. Ads that come from the same address as the actual content (on YouTube, for example) slip through. So an additional blocker like uBlock Origin in the browser still makes sense.
</Callout>

<OneWay />

The best-known alternative is [Pi-hole](https://pi-hole.net). At its core it does the same and has a large community. AdGuard Home comes with encrypted DNS (DNS-over-HTTPS) and a modern interface without extra packages, and runs as a single container. Both are a good choice; the steps here are for AdGuard Home.

<Steps>

<Step title="Free up port 53 (Ubuntu only)">
DNS runs on **port 53**, over UDP and TCP. The container has to take this port on the server so other devices can reach it. On Ubuntu, though, **systemd-resolved** already listens there: that's the service that resolves names for the server itself. It starts a small local DNS server, the **stub listener**, at the address `127.0.0.53:53`. Docker then can't publish port 53 and fails with `address already in use`.

First check whether the port is taken:

```bash
sudo ss -tulpn | grep ':53 '
```

If there's no output, the port is free and you skip to the next step. On Debian that's the normal case, because systemd-resolved usually isn't installed there at all. If you see `systemd-resolve`, turn off only the stub listener. systemd-resolved itself keeps running.

```bash
sudo mkdir -p /etc/systemd/resolved.conf.d
printf '[Resolve]\nDNSStubListener=no\n' | sudo tee /etc/systemd/resolved.conf.d/no-stub.conf
sudo ln -sf /run/systemd/resolve/resolv.conf /etc/resolv.conf
sudo systemctl restart systemd-resolved
```

What the three commands do:

- The file in `/etc/systemd/resolved.conf.d/` sets `DNSStubListener=no`. systemd-resolved then no longer opens `127.0.0.53:53`. A file of your own in this folder is better than changing the main file, because package updates don't overwrite it.
- `/etc/resolv.conf` tells all programs which DNS server to ask. On Ubuntu it points to the stub by default (`nameserver 127.0.0.53`). Without the stub, that would lead nowhere. The link to `/run/systemd/resolve/resolv.conf` instead enters the real DNS servers directly, the ones you set when [setting up the static IP](/en/setup/static-ip-hostname/), usually your router.
- The restart applies the setting.

Then check that port 53 is free and the server still resolves names:

```bash
sudo ss -tulpn | grep ':53 '
ping -c1 debian.org
```

So the server itself keeps asking your router or a public DNS server, not AdGuard Home. That's on purpose: if the container isn't running at some point, the server can still download updates and images. More on ports that are already taken under [Port already in use](/en/wiki/port-in-use/).
</Step>

<Step title="Start AdGuard Home">
Create the folder and, in it, `compose.yaml` and `.env`:

```bash
mkdir -p __ROOT__/adguard-home
cd __ROOT__/adguard-home
```

<ServiceFiles id="adguard-home" />

The configuration file `AdGuardHome.yaml` ends up in `data/conf`, statistics and the query log in `data/work`. Start the container:

```bash
docker compose up -d
docker compose logs -f adguard-home
```

Press `Ctrl+C` to leave the log view.

Port 53 is now reachable on the whole network, bypassing the firewall (see [Firewall with UFW](/en/setup/firewall-ufw/)). On a home network behind the router, that's intended. But **never forward port 53 on your router**, and don't run AdGuard Home like this on a server with a public IP. An open DNS server on the internet quickly gets abused for attacks on others.
</Step>

<Step title="Go through the setup wizard">
On the first start, AdGuard Home shows a setup wizard on port 3000. Open `https://adguard.__DOMAIN__`. Without a reverse proxy, you reach it at your server's IP and the port from the `compose.yaml`.

Do this right after starting: until then, anyone who can reach the page can set up AdGuard Home. The most important part comes on the second page:

| Field | Value |
| --- | --- |
| Admin web interface: network interface | All interfaces |
| Admin web interface: port | **3000** (80 is suggested) |
| DNS server: network interface | All interfaces |
| DNS server: port | 53 |

Why 3000? The wizard runs on port 3000, the finished interface on port 80 by default. Your reverse proxy, however, always forwards to port 3000. If the interface stays on 3000, the same address works before and after the setup. "All interfaces" refers to the inside of the container. Which ports are reachable from outside is defined by the `compose.yaml`.

Then create a user name and password. Use a long password from your password manager. The last page explains how to set up devices. You'll do that through the router in a moment.

If you picked port 80 by mistake, the interface is no longer reachable. Then stop the container, change the line `address: 0.0.0.0:80` under `http:` in `__DATA(adguard-home)__/conf/AdGuardHome.yaml` to `address: 0.0.0.0:3000` and start it again:

```bash
cd __ROOT__/adguard-home
docker compose stop
sudo nano __DATA(adguard-home)__/conf/AdGuardHome.yaml
docker compose start
```
</Step>

<Step title="Choose upstream DNS and blocklists">
AdGuard Home only answers what it blocks itself. It passes all other requests on to an **upstream DNS server**. Under "Settings → DNS settings", an encrypted server is already entered (DNS-over-HTTPS, recognizable by `https://`). Your internet provider then no longer sees which names you resolve. You can leave it as is or enter another provider. "Test upstreams" checks whether it answers.

The actual work is done by the **blocklists**. Under "Filters → DNS blocklists", the "AdGuard DNS filter" list is already active. With "Add blocklist → Choose from the list", you can add more lists with a checkbox, for example one of the HaGeZi lists. AdGuard Home updates them automatically.

More lists don't automatically mean better. Every list sometimes blocks something you need, like a link in a newsletter email or an app's login. Start with one or two lists. If something doesn't work, look up the address in the "Query Log" and unblock it there with a click. AdGuard Home creates an exception rule under "Filters → Custom filtering rules" for it.
</Step>

<Step title="Test directly">
Before you switch the whole network, test the server specifically. The `dig` tool asks a particular DNS server. It's in the `bind9-dnsutils` package. Run the commands on the server or on another Linux computer on your home network, with your server's IP:

```bash
sudo apt install bind9-dnsutils
dig @__SERVER_IP__ debian.org +short
dig @__SERVER_IP__ doubleclick.net +short
```

The first query returns normal IP addresses. The second targets a known ad domain and should return `0.0.0.0`: it was blocked. You'll see both requests in the "Query Log". On Windows, the same works with `nslookup doubleclick.net __SERVER_IP__`.

If you get no answer (`connection timed out`), the container isn't running or port 53 isn't published. Check `docker compose ps` and the logs as described in [Troubleshooting: first steps](/en/wiki/first-steps/).
</Step>

<Step title="Let the router hand out the DNS server">
So that all devices use AdGuard Home, the router should hand it out. Devices get their network settings from the router via **DHCP**, including the DNS server. If you enter your server's IP there, all devices automatically ask AdGuard Home. Depending on the router, the setting is called "Local DNS server", "DNS server for DHCP" or similar.

On a **FRITZ!Box**, you'll find it roughly here (slightly different depending on the FRITZ!OS version and language):

- "Home Network → Network → Network Settings → IP Addresses → IPv4 Settings". Enter your server's IP under "Local DNS server" there.
- The IPv6 settings next to it have a matching field for DNSv6. If your network uses IPv6, the FRITZ!Box otherwise keeps handing out itself as the DNS server, and some devices bypass AdGuard Home that way.

**Don't** set the DNS server under "Internet → Account Information → DNS Server". Then all requests would still land at AdGuard Home, but always on behalf of the FRITZ!Box. You'd only see a single device in the log.

Devices only pick up the new DNS server when they renew their DHCP settings. The quickest way is to turn Wi-Fi off and on again briefly. After a few minutes, the devices show up under "Clients" in the dashboard.

Some devices and browsers bypass the router's DNS server, for example with encrypted DNS set up permanently. They then don't show up in the log. That's normal and can only be changed on the device itself.
</Step>

<Step title="Plan for outages">
Now your whole home network depends on your server. **If the server is off or the container stopped, DNS stops working on your home network.** Websites don't load, apps report "no connection" even though the internet is actually up. That happens faster than you'd think: an update with a reboot, a power outage, maintenance.

So think ahead about what should happen then:

- **Second DNS server in the router**: many routers allow a second entry. If you enter a public DNS server there, the network keeps working when AdGuard Home fails. The catch: devices don't only use the second server in an emergency, but also now and then. Ads get through then.
- **Second AdGuard Home instance**: a second instance on another device, a Raspberry Pi for example, with the same settings. You enter both IPs in the router. That's the cleanest solution, but more maintenance. More on splitting things up in [Multiple devices: splitting the roles](/en/wiki/multiple-devices/).
- **Emergency plan**: you accept the outage and write down how to reset the DNS entry in the router. Keep this note where someone else in your household can find it too (see [Documentation](/en/wiki/documentation/)).

To start with, the emergency plan is fine. Also add AdGuard Home to [Uptime Kuma](/en/setup/uptime-kuma/). The "DNS" monitor type regularly asks the server for a name and alerts you when no answer comes.
</Step>

</Steps>

## What's next?

- **Local addresses**: under "Filters → DNS rewrites", you can point `*.__DOMAIN__` to your server's internal IP. Devices on your home network then reach your services directly, without a detour through the internet.
- **Naming clients**: under "Settings → Client settings", you give devices names and can set different rules for individual devices, like stricter filters for children's devices.
- **Dashboard**: [Homepage](/en/setup/dashboard-homepage/) shows the number of blocked requests right on your start page.
- **Backup**: your settings live in `__DATA(adguard-home)__/conf`. They're [backed up](/en/setup/backups-borgmatic/) with the rest of `__ROOT__`.
