---
title: "Uptime Kuma"
description: "Uptime Kuma checks every minute whether your services are reachable and notifies you by push, Telegram or email as soon as something goes down. You also get a status page where you and the people who share your services can see the state of all of them."
level: 1
minutes: 15
requires: [Docker Compose, Reverse proxy]
services: [uptime-kuma]
---

[Beszel](/en/setup/monitoring-beszel/) looks inside the server: CPU, RAM, disk. [Uptime Kuma](https://uptime.kuma.pet) looks at it from outside and asks the question that matters in the end: does the page load in the browser? For that, it calls your services regularly, just like a visitor. If DNS fails, a certificate expires or the reverse proxy hangs, Uptime Kuma notices, even if all containers seem to be running.

<Callout type="warning" title="Who watches the watcher?">
If Uptime Kuma runs on the same server as your services, it goes down with it and can no longer warn you. Ideally, use a **different device**: a Raspberry Pi at home that checks your cloud server, or a small VPS that checks your homelab from outside. To start with, the same server is fine. But then add an external check (last step) that monitors Uptime Kuma itself.
</Callout>

<Steps>

<Step title="Start Uptime Kuma">
Uptime Kuma gets its own folder under `__ROOT__`. Monitors, settings and measurements end up in `data/`.

```bash
mkdir -p __ROOT__/uptime-kuma
cd __ROOT__/uptime-kuma
```

Create `compose.yaml` and `.env` there:

<ServiceFiles id="uptime-kuma" />

```bash
docker compose up -d
docker compose logs -f uptime-kuma
```

Press `Ctrl+C` to leave the log view. If you use Nginx Proxy Manager, turn on "Websockets Support" for the proxy host. Uptime Kuma's interface needs WebSockets for its live view. Traefik and Caddy forward them automatically.
</Step>

<Step title="Choose the database and create the account">
Open `https://status.__DOMAIN__`. On the first start, Uptime Kuma 2 asks which database you want to use. Choose **SQLite**. That's a single file in the `data` folder, ideal for a homelab and easy to back up. The built-in MariaDB only pays off with a very large number of monitors.

Then create your administrator account. Do this right after starting, because until then, anyone who can reach the page can create it. Use a long, random password from your password manager. Later you can also turn on two-factor login under "Settings → Security".
</Step>

<Step title="Set up notifications">
First set up the channel Uptime Kuma reaches you through. Then you can assign it to every new monitor right away. Open "Settings → Notifications → Setup Notification" and choose a type. Three popular ways:

| Type | What you need |
| --- | --- |
| ntfy | The ntfy app on your phone and a topic name. Server URL `https://ntfy.sh` or your own ntfy server. |
| Telegram | A bot you create with BotFather, and your chat ID. Uptime Kuma helps you read out the ID in the dialog. |
| Email (SMTP) | Your mail provider's SMTP details: server, port, user, password. |

On the public ntfy server, anyone who knows the topic name can read along. So choose it long and random. The guide [Notifications](/en/setup/notifications/) shows how to run your own ntfy server with access control instead.

Check "Default enabled" and "Apply on all existing monitors". Click "Test": if the message arrives, save. Many more services are in the [list of notification methods](https://github.com/louislam/uptime-kuma/wiki/Notification-Methods).
</Step>

<Step title="Create your first HTTP monitor">
Click "Add New Monitor" and fill in:

| Field | Value |
| --- | --- |
| Monitor type | HTTP(s) |
| Friendly name | Vaultwarden |
| URL | `https://vault.__DOMAIN__` |
| Heartbeat interval | 60 seconds |
| Retries | 2 |

With the public address, you check the whole chain: DNS, reverse proxy, certificate and service. The **retries** prevent false alarms: only when several checks in a row fail is the service considered down and you get a message.

In the advanced options, turn on the "Certificate expiry notification". Then Uptime Kuma warns you if the automatic renewal ever gets stuck, before visitors see an error message.

Create a monitor for every important service the same way. Besides HTTP, there are other types, such as **keyword** (the page must contain a specific text), **TCP port** and **ping** for devices without a web interface.

Because Uptime Kuma sits in the `__NETWORK__` network, you can also check services internally by their container name, such as `http://vaultwarden:80`. That shows you whether the container itself is running, independently of the proxy.
</Step>

<Step title="Monitor backups">
Some things Uptime Kuma can't query; they report in themselves. That's what the **push** monitor type is for: Uptime Kuma shows you a push URL and waits for it to be called regularly. If the call doesn't come, it raises the alarm.

Ideal for your nightly backup: create a push monitor "Backup" with a heartbeat interval of `90000` seconds (25 hours, a bit of buffer for one day). You enter the push URL in your borgmatic configuration, as described in [Backups with borgmatic](/en/setup/backups-borgmatic/).
</Step>

<Step title="Create a status page">
A **status page** shows at a glance which services are running, without anyone having to log in. Handy when family or friends use your services too: instead of asking "Does Nextcloud work for you?", they check themselves.

Open "Status Pages → New Status Page", enter a name and a short name (slug), for example `homelab`. In the editor, add groups and monitors and save. The page is then reachable at `https://status.__DOMAIN__/status/homelab`.

The status page is public. Only include monitors whose names you want to show, and no internal addresses.
</Step>

<Step title="Monitor Uptime Kuma itself">
Finally, the question from the beginning: who notices when the whole server fails? For that, you need a check that does **not** run on this server. Two simple ways:

- **A second Uptime Kuma instance** on another device or a small VPS. It only checks `https://status.__DOMAIN__` and one or two important services. Ideally at another location, so a failure of your internet line gets noticed too.
- **An external monitoring service**: many providers check a few addresses from outside for free. You enter `https://status.__DOMAIN__` there as an HTTP check and get an email when it stops answering.

That gives you two layers: Uptime Kuma knows all the details, and the external check tells you when Uptime Kuma itself goes silent.
</Step>

</Steps>
