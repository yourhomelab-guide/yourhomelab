<OneWay />

Disks die, updates go wrong, and sometimes you simply delete the wrong folder. That's why a backup is the most important service in your homelab. It only has to do three things: run regularly, live outside the server and be restorable.

For this, you use two programs that belong together:

- **[BorgBackup](https://www.borgbackup.org)** (Borg for short) does the actual work. It **deduplicates** (stores identical data blocks only once), **compresses** and **encrypts** everything before it leaves the server. In Borg, the target is called a **repository**, and every backup state in it is an **archive**.
- **[borgmatic](https://torsion.org/borgmatic/)** wraps a configuration file and automation around Borg. A single call creates the backup, cleans up old archives according to your rules and checks the repository. With **hooks**, it runs your own commands before and after, such as database dumps, and reports the result to your monitoring.

Because everything in this guide lives under `__ROOT__`, a single path is essentially enough. You'll find background on the 3-2-1 rule and retention times under [Backup strategies](/en/wiki/backup-strategies/).

<Steps>

<Step title="Install Borg and borgmatic">
Borg comes from the Debian and Ubuntu package sources. Along with it, install **pipx**, a tool that installs Python programs into a separate, isolated environment:

```bash
sudo apt update
sudo apt install borgbackup pipx
borg --version
```

You install borgmatic itself with pipx, not from apt. The reason: depending on the distribution, the package sources contain very different borgmatic versions, some still from the 1.x series. The configuration file changed considerably between these versions. With pipx, you get the current version, and the configuration in this guide is guaranteed to fit. It's written for **borgmatic 2.x**.

The two variables make pipx install borgmatic system-wide and put the command into `/usr/local/bin`. That way `sudo borgmatic` works directly:

```bash
sudo PIPX_HOME=/opt/pipx PIPX_BIN_DIR=/usr/local/bin pipx install borgmatic
sudo borgmatic --version
```

The output should start with `2.`. Later, you update borgmatic with the same pattern:

```bash
sudo PIPX_HOME=/opt/pipx PIPX_BIN_DIR=/usr/local/bin pipx upgrade borgmatic
```

The [official installation guide](https://torsion.org/borgmatic/how-to/install-borgmatic/) now uses the `uv` tool instead of pipx. The result is the same. Here, pipx has the advantage of being right in the package sources.
</Step>

<Step title="Create the passphrase">
The backup runs as `root`. Only then can Borg also read files that containers created with their own user IDs, such as database folders. That's why the settings go into `/etc/borgmatic`, readable only by root.

Borg encrypts the repository with a **passphrase**. Create a random one and store it in a file only root may read:

```bash
sudo mkdir -p /etc/borgmatic
sudo chmod 700 /etc/borgmatic
openssl rand -base64 32 | sudo tee /etc/borgmatic/passphrase > /dev/null
sudo chmod 600 /etc/borgmatic/passphrase
```

<Callout type="warning" title="Keep the passphrase in two places">
Without this passphrase, all backups are worthless, even to you. There's no way to reset it. Copy it into your password manager right away. It must not exist only on the server you want to back up.

```bash
sudo cat /etc/borgmatic/passphrase
```
</Callout>
</Step>

<Step title="Prepare the backup target">
Borg can back up to a local folder or over SSH to another computer. Choose a target:

- **USB disk**: simple and fast. Mount it permanently, for example at `/mnt/backup` (with an entry in `/etc/fstab`). But it doesn't protect against fire or theft if it sits next to the server. Tip: two disks in rotation, one of them away from home.
- **Another computer over SSH**, such as a NAS or a computer at a friend's place. **Borg must be installed there as well** (`sudo apt install borgbackup`), because Borg talks to itself on both sides. Create a separate user on the target computer, for example `backup`. If you have several devices, they can back each other up; see [Multiple devices: splitting the roles](/en/wiki/multiple-devices/).
- **Storage providers with Borg support**: some hosting providers offer storage that works directly with Borg. The [borgmatic docs](https://torsion.org/borgmatic/how-to/set-up-backups/) name BorgBase, Hetzner and rsync.net, for example. You get an SSH address there and enter it just like for your own computer. The provider only sees encrypted data.

For SSH targets: because the backup runs as root, `root` must be able to log in there with an SSH key. Create a key and show the public part:

```bash
sudo ssh-keygen -t ed25519
sudo cat /root/.ssh/id_ed25519.pub
```

On the target computer, add the output to `~/.ssh/authorized_keys` of the `backup` user (with a provider, in its web interface). Then test the connection. That also confirms the host key and checks that Borg is there on the other side:

```bash
sudo ssh backup@192.168.1.20 borg --version
```

Plan generously for space on the target, at least twice your current data. If it fills up anyway, [Disk full](/en/wiki/disk-full/) helps.
</Step>

<Step title="Write the configuration">
borgmatic reads its settings from `/etc/borgmatic/config.yaml`. Create the file with `sudo nano /etc/borgmatic/config.yaml`. Under `repositories`, choose **one** of the two variants and delete the other or leave it commented out:

<Callout title="Let the tool create the file">
The [borgmatic config](/en/tools/borgmatic-config/) tool builds this file from your answers, with database dumps and an Uptime Kuma report if you like. The explanations below still apply: read them so you know what's in your file.
</Callout>

```yaml
# What to back up
source_directories:
    - __ROOT__

# Where the backups go. Pick ONE of these:
repositories:
    # a) USB disk mounted at /mnt/backup
    - path: /mnt/backup/borg
      label: usb
    # b) Second computer via SSH (Borg must be installed there)
    # - path: ssh://backup@192.168.1.20/./borg
    #   label: remote

# Read the passphrase from the file you created
encryption_passphrase: "{credential file /etc/borgmatic/passphrase}"

compression: zstd

# Keep 7 daily, 4 weekly and 6 monthly archives, delete the rest
keep_daily: 7
keep_weekly: 4
keep_monthly: 6

# Consistency checks and how often they run
checks:
    - name: repository
      frequency: 2 weeks
    - name: archives
      frequency: 2 weeks
    - name: data
      frequency: 3 months
```

What the sections mean:

- **source_directories**: what gets backed up. That's your whole homelab folder with all `compose.yaml` files, `.env` files and data.
- **repositories**: where it gets backed up to. `ssh://backup@192.168.1.20/./borg` means the `borg` folder in the home directory of the `backup` user. The `label` is a short name borgmatic shows in its output.
- **encryption_passphrase**: borgmatic reads the passphrase from the file. So it isn't in the configuration in plain text.
- **compression**: `zstd` compresses well and fast. Without this line, Borg uses the faster but weaker `lz4`.
- **keep_…**: the retention rules. You can go back to any day for a week, any week for a month and any month for half a year. borgmatic deletes older archives automatically.
- **checks**: `repository` and `archives` check the structure of the repository and the archives, here every two weeks. `data` actually reads and decrypts all data. That takes a long time for big backups, so only every three months. borgmatic remembers when a check last ran and skips it until then.

<Callout title="Data lives elsewhere?">
If you chose "central" mode in "My setup", your data lives under `__DATA_ROOT__`. If that folder isn't below `__ROOT__` anyway, add it as a second line under `source_directories`. The same goes for paths outside that you've mounted into stacks, such as a media collection on a second disk.
</Callout>

Watch the indentation: YAML only allows spaces, no tabs. Check the file:

```bash
sudo borgmatic config validate
```

The message `All configuration files are valid` means: everything fits. If needed, you can create a complete example file with all options and comments using `sudo borgmatic config generate --destination /root/borgmatic-beispiel.yaml`. There's also the [configuration reference](https://torsion.org/borgmatic/reference/configuration/) to look things up.
</Step>

<Step title="Create the repository and back up the key">
Now create the repository. You only do this once:

```bash
sudo borgmatic repo-create --encryption repokey
```

`repokey` is the mode the [Borg docs](https://borgbackup.readthedocs.io/en/stable/usage/init.html) recommend as a rule of thumb. If your server has an older CPU, `repokey-blake2` can be faster. The mode can't be changed later.

With `repokey`, the actual key lives **in the repository**, protected by your passphrase. Day to day, you only need the passphrase. But if exactly the key file in the repository gets damaged, everything is lost without a copy of the key. So export it once:

```bash
sudo borgmatic key export
```

The output starts with `BORG_KEY`. Copy all of it as a secure note into your password manager, next to the passphrase. With `--paper`, you get a version for printing.

<Callout type="warning" title="Key and passphrase belong together">
To decrypt, you always need **both**: the key (in the repository or as an export) and the passphrase. Keep both outside the server you're backing up.
</Callout>
</Step>

<Step title="Back up databases first">
Most services store their data as files that Borg can simply copy. With databases like PostgreSQL or MariaDB, that's risky: they write constantly, and a copy taken mid-write can be unusable. That's why you create a **dump** first, a consistent export of the database as a file. Borg then backs up this dump along with everything else.

A **command hook** in borgmatic does this: commands that run before the backup. Since your databases run in containers, you call the dump program in the container with `docker compose exec`. `-T` turns off the terminal so the output lands cleanly in the file. The dump goes into the service's data folder, so into the backed-up area.

Add this block to the configuration. The example backs up the PostgreSQL database of [authentik](/en/services/authentik/) and the MariaDB of [Nextcloud](/en/services/nextcloud/):

```yaml
commands:
    - before: action
      when: [create]
      run:
          # Authentik (PostgreSQL)
          - mkdir -p -m 700 __DATA(authentik)__/db-dump
          - docker compose -f __ROOT__/authentik/compose.yaml exec -T postgresql pg_dump -U authentik -d authentik > __DATA(authentik)__/db-dump/authentik.sql
          # Nextcloud (MariaDB)
          - mkdir -p -m 700 __DATA(nextcloud)__/db-dump
          - docker compose -f __ROOT__/nextcloud/compose.yaml exec -T db sh -c 'mariadb-dump --single-transaction -u root -p"$MARIADB_ROOT_PASSWORD" nextcloud' > __DATA(nextcloud)__/db-dump/nextcloud.sql
```

`before: action` with `when: [create]` means: the commands run right before every backup. If one of them fails, borgmatic stops and reports an error. So it doesn't silently back up a broken state. With MariaDB, the single quotes make sure the variable with the password is only evaluated inside the container.

The dumps stay uncompressed on purpose. Borg compresses by itself and can only recognize unchanged parts of a dump if it wasn't packed beforehand. Container and database names are in each service's `compose.yaml`. If you have no databases, leave the block out. Many projects also describe a backup method of their own in their docs. That one then takes precedence.

By the way, borgmatic also has its own [database hooks](https://torsion.org/borgmatic/how-to/backup-your-databases/) like `postgresql_databases` and `mariadb_databases`. They stream the dump directly into the archive. For databases in containers, though, they need extra settings: either the matching client programs on the server or custom dump commands with `docker exec`, plus the database passwords in the configuration. Going through `docker compose exec` into a file is easier to follow to start with.

**The simple alternative:** you stop the stack briefly, back up and start it again. That's always consistent, but the service isn't reachable during the backup. At night, that usually bothers nobody. An `after` hook also runs if the backup fails. So the stack starts again in any case:

```yaml
commands:
    - before: action
      when: [create]
      run:
          - docker compose -f __ROOT__/nextcloud/compose.yaml stop
    - after: action
      when: [create]
      run:
          - docker compose -f __ROOT__/nextcloud/compose.yaml start
```

There's only one `commands:` block per file. If you use both, all entries go into the same block. Then check the file again with `sudo borgmatic config validate`.
</Step>

<Step title="First backup">
Now back up the complete homelab folder. `--verbosity 1` shows what borgmatic is doing, and `--stats` sums up at the end how much was backed up:

```bash
sudo borgmatic create --verbosity 1 --stats
sudo borgmatic repo-list
```

The first backup takes a while, depending on the amount of data. The following ones are much faster, because Borg only transfers changed blocks. `repo-list` shows you the new archive with host name, date and time.

The `.env` files with your secrets are included in the backup. That's intended, because without them no service starts again. Borg encrypts them before they leave the server.

Day to day, you call borgmatic without an action. Then it does everything in one go: create the backup (`create`), delete old archives according to your rules (`prune`), free up the space (`compact`) and check (`check`, if due). Try it once by hand:

```bash
sudo borgmatic --verbosity 1
```
</Step>

<Step title="Start automatically every night">
A **systemd timer** starts borgmatic at a fixed time. It catches up on a missed run if the server was off at the scheduled time, and writes everything to the system log. The borgmatic project provides [example files](https://torsion.org/borgmatic/how-to/set-up-backups/#systemd) for this. The variant here is deliberately leaner: without extra security settings that can get in the way of Docker commands in hooks, and with the path from the pipx installation. Create two files.

`/etc/systemd/system/borgmatic.service`:

```ini
[Unit]
Description=borgmatic backup
Wants=network-online.target
After=network-online.target docker.service
Documentation=https://torsion.org/borgmatic/

[Service]
Type=oneshot
# Lower CPU and I/O priority so the server stays responsive
Nice=19
IOSchedulingClass=best-effort
IOSchedulingPriority=7
# Don't drop log lines during long runs
LogRateLimitIntervalSec=0
ExecStart=/usr/local/bin/borgmatic --verbosity -2 --syslog-verbosity 1
```

`/etc/systemd/system/borgmatic.timer`:

```ini
[Unit]
Description=Nightly borgmatic backup

[Timer]
OnCalendar=*-*-* 03:00:00
RandomizedDelaySec=15min
Persistent=true

[Install]
WantedBy=timers.target
```

Enable and check:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now borgmatic.timer
systemctl list-timers borgmatic.timer
```

Start a run right away and look at the log:

```bash
sudo systemctl start borgmatic.service
sudo journalctl -u borgmatic.service -e
```

Prefer cron? Then one line in root's crontab (`sudo crontab -e`) is enough:

```bash
0 3 * * * /usr/local/bin/borgmatic --verbosity -1 --syslog-verbosity 1
```
</Step>

<Step title="Get notified about errors">
You only notice a backup that has been failing silently for weeks when you need it. So get notified. borgmatic can report the result directly to a **push monitor** in [Uptime Kuma](/en/setup/uptime-kuma/). If the report doesn't arrive or borgmatic reports an error, Uptime Kuma raises the alarm.

In Uptime Kuma, create a monitor of type "Push". `90000` seconds (25 hours, a bit of buffer for one day) works as the heartbeat interval. Copy the push URL and add it to the configuration. Enter the URL **without** the part from the question mark on; borgmatic appends that itself:

```yaml
uptime_kuma:
    push_url: https://status.__DOMAIN__/api/push/DEIN-PUSH-TOKEN
    states:
        - finish
        - fail
```

Replace `DEIN-PUSH-TOKEN` with the token from your push URL. With `finish` and `fail`, borgmatic reports after every run whether it worked. Check the file with `sudo borgmatic config validate` and start a test run with `sudo systemctl start borgmatic.service`. A green bar should appear in the monitor shortly afterwards. The guide [Notifications](/en/setup/notifications/) shows how the messages get to your phone through your own ntfy server. You'll find other ways, such as ntfy or Healthchecks, in [borgmatic's monitoring docs](https://torsion.org/borgmatic/how-to/monitor-your-backups/).
</Step>

</Steps>
