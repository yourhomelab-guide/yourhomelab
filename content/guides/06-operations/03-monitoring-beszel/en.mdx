---
title: "Monitoring with Beszel"
description: "Beszel shows you CPU, RAM, disks, network and every container on your server, with history, in a lean web interface. In the end, it notifies you when the disk fills up or a server stops responding."
level: 1
minutes: 15
requires: [Docker Compose, Reverse proxy]
services: [beszel]
---

Without monitoring, you only notice problems when something stops working. Yet many failures announce themselves: the disk fills up over weeks, a container slowly eats more and more RAM, the CPU runs too hot in summer. [Beszel](https://beszel.dev) makes such trends visible and is very frugal about it. You'll find the background under [Monitoring](/en/wiki/monitoring/).

Beszel consists of two parts:

- The **hub** is the web interface. It stores the measurements and sends alerts. You only need it once.
- The **agent** runs on every server you want to monitor. It measures the values and sends them to the hub. In this guide, it runs on the same server as the hub.

The agent itself opens an encrypted **WebSocket** connection (a persistent connection over HTTPS) to the hub. That's why you don't need to open a port in the firewall for it.

<Steps>

<Step title="Set up the hub">
Like every service, the hub gets its own folder under `__ROOT__`. Its data ends up in the `data/` subfolder.

```bash
mkdir -p __ROOT__/beszel
cd __ROOT__/beszel
```

Create `compose.yaml` and `.env` there:

<ServiceFiles id="beszel" />

Then start the hub:

```bash
docker compose up -d
```

If you use Nginx Proxy Manager, turn on "Websockets Support" for the proxy host. Otherwise the agent can't connect later. Traefik and Caddy forward WebSockets automatically.

<Callout type="warning" title="Don't put login protection in front">
Beszel has its own login. Don't put Tinyauth or any other forward auth middleware in front of it: the agent connects through the address `/api/beszel/agent-connect` and can't log in interactively there. Instead, Beszel supports OAuth itself, for example with [Pocket ID](/en/setup/pocket-id/) (see the [Beszel docs](https://beszel.dev/guide/oauth)).
</Callout>
</Step>

<Step title="Create the admin account">
Open `https://beszel.__DOMAIN__` in the browser. On first access, you create an account with email and password. Use a long, random password from your password manager. This account is the administrator at the same time.
</Step>

<Step title="Add the system in the hub">
Click "Add System" at the top right. In the dialog, enter:

| Field | Value |
| --- | --- |
| Name | Your server's name, e.g. `homeserver` |
| Host / IP | Your server's IP, here `__SERVER_IP__` |

Below that, the dialog shows two values you'll need for the agent in a moment:

- **Public Key**: the agent uses it to recognize that it's talking to your hub.
- **Token**: the agent uses it to log in to the hub.

Leave the dialog open and switch to the terminal.
</Step>

<Step title="Start the agent">
The agent gets its own stack. It runs with `network_mode: host`, that is directly in the server's network instead of a Docker network. Only that way does it see the real network cards. It reads your containers' statistics through the Docker socket.

```bash
mkdir -p __ROOT__/beszel-agent __DATA(beszel-agent)__
cd __ROOT__/beszel-agent
```

`compose.yaml`:

```yaml
services:
  beszel-agent:
    # Same version as the hub
    image: henrygd/beszel-agent:0.20
    container_name: beszel-agent
    restart: unless-stopped
    network_mode: host
    volumes:
      - __DATA(beszel-agent)__:/var/lib/beszel-agent
      - /var/run/docker.sock:/var/run/docker.sock:ro
    environment:
      - LISTEN=45876
      - HUB_URL=https://beszel.__DOMAIN__
      - KEY=${KEY}
      - TOKEN=${TOKEN}
```

`.env` (copy the values from the open dialog; put the key in quotes because it contains a space):

```bash
KEY="ssh-ed25519 AAAA..."
TOKEN=...
```

```bash
chmod 600 .env
docker compose up -d
docker compose logs -f
```

After a few seconds, the log should say that the WebSocket connection to the hub is up. Press `Ctrl+C` to leave the view.
</Step>

<Step title="Check the system">
Click "Add System" in the dialog. The server appears in the list. When its dot turns green, data is arriving. Click the server to see history for CPU, RAM, disk, network and, if available, temperatures, plus CPU and RAM of every single container.

If the dot stays red, check:

- Is `https://beszel.__DOMAIN__` reachable from the server itself? Test: `curl -I https://beszel.__DOMAIN__`. Some routers don't route requests from inside back to their own public address (missing NAT loopback). A local DNS record that points the domain to the internal IP helps then.
- Are `KEY` and `TOKEN` in the `.env` right? After a change, run `docker compose up -d` again.
- The [common issues](https://beszel.dev/guide/common-issues) in the Beszel docs.
</Step>

<Step title="Set up notifications">
For Beszel to warn you, it needs a channel. Open "Settings → Notifications". Beszel knows two ways:

- **Email**: enter your address. Beszel must be able to send mail for this. You enter your mail provider's SMTP details in the admin settings linked from the user menu.
- **Webhook / push**: Beszel uses [Shoutrrr](https://beszel.dev/guide/notifications/) URLs and so supports ntfy, Telegram, Discord, Gotify and Matrix, among others. For a push message to your phone through the public ntfy server, this is enough, for example:

```bash
ntfy://ntfy.sh/ein-langes-zufaelliges-topic
```

Install the ntfy app and subscribe to the same topic. Anyone who knows the topic name can read along, so choose it long and random, or run your own ntfy server later. The exact URL format for each service is in the [Beszel docs](https://beszel.dev/guide/notifications/). The guide [Notifications](/en/setup/notifications/) shows which channel suits you and how to run ntfy yourself.
</Step>

<Step title="Set the alerts">
You set alerts per system. In the system list, click the bell icon next to your server. Sensible to start with:

| Alert | Suggestion |
| --- | --- |
| Status | on: reports when the server stops responding |
| Disk Usage | from 85 % |
| Memory Usage | from 90 %, for 10 minutes |
| CPU Usage | from 90 %, for 10 minutes |
| Temperature | only if your server reports sensors |

The duration prevents false alarms: a short load spike during an update is normal, ten minutes at full load less so. If the disk alert fires, [Disk full](/en/wiki/disk-full/) helps you find where the space went. Through the "All Systems" tab, you can apply the same values to every new server later.
</Step>

<Step title="Connect more servers">
Every further server only needs an agent. Add a new system in the hub with "Add System" and start the same agent stack on the server with the new key and token. `HUB_URL` stays the same. Because the agent opens the connection, this also works for a VPS in the cloud. [Multiple devices: splitting the roles](/en/wiki/multiple-devices/) explains how to spread tasks over several devices.

Always update the hub and agents together, so the versions match.
</Step>

</Steps>

<Callout title="Beszel complements an outside check, it doesn't replace it">
If the whole server goes down, Beszel goes down with it if it runs there. The status alert then only helps for other servers. Whether your services are reachable from outside is checked by [Uptime Kuma](/en/setup/uptime-kuma/), ideally from a second location.
</Callout>
