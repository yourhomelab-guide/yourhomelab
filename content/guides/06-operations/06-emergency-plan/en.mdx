<OneWay />

Sooner or later it happens: the SSD dies, lightning strikes the line, the server gets stolen, or an update wrecks the system so thoroughly that setting it up again is faster than repairing it. With a backup, that's no drama, just an afternoon of work. Provided you can get to the backup and know what to do.

In practice, that rarely fails because of the backup itself, but because of small things: the passphrase is in the password manager, and that ran on the dead server. Access to the backup machine only worked with the old server's SSH key. The address of the backup target was only in the configuration on the old server.

That's why this guide has two parts. You do the **preparation** now, calmly. You read the **procedure for an emergency** when the time comes. It assumes you've set up [Backups with borgmatic](/en/setup/backups-borgmatic/) and [tested the restore](/en/setup/testing-restores/).

## Preparation: the emergency sheet

The emergency sheet is a short collection of everything you need when your server is gone. The most important rule: **none of it may exist only on the server you're backing up.**

| What | What for |
| --- | --- |
| Borg passphrase | Without it, the backup can't be read, not even by you. |
| Exported Borg key (`sudo borgmatic key export`) | Insurance in case the key file in the repository is damaged. |
| Repository address, e.g. `ssh://backup@192.168.1.20/./borg` | So the new server knows where the backup is. |
| Access to the backup target: login at the provider or on the backup machine | The new server needs an SSH key of its own, which you have to add there. |
| Master password of the password manager and recovery codes for 2FA | Without them, you can't get to any other accounts. |
| Access to the registrar or DNS provider | In case the new server gets a different IP address. |
| Access to the router | To change port forwarding and the fixed IP assignment. |
| Access to the hosting provider, if you use a VPS | To order a new server and adjust the provider's firewall. |
| Overview of your services: subdomains, ports, databases, paths outside `__ROOT__` | So you know everything that has to come back. |
| Copy of `/etc/borgmatic/config.yaml` (optional) | borgmatic puts it into every archive automatically, but a copy saves you a step in an emergency. |

You don't have to write the overview of your services by hand. The [docs export](/en/tools/docs-export/) creates a Markdown file with ports, paths and restore steps from your setup. In an emergency, you can get the borgmatic configuration from the backup or create it again with the [borgmatic config](/en/tools/borgmatic-config/) tool.

<Callout type="warning" title="The chicken-and-egg problem with the password manager">
If your password manager runs in the homelab itself, as [Vaultwarden](/en/services/vaultwarden/) for example, the Borg passphrase and all other credentials are in the backup that you can't open without the passphrase. The Bitwarden apps do keep an encrypted copy of your vault and often still show it without the server. But don't rely on that. Keep at least the Borg passphrase, the key and the master password **outside** as well.
</Callout>

Where you keep the emergency sheet depends on what you want to protect against. What has proven itself:

- **Printed** in a sealed envelope, for example with your important documents. For the Borg key, `sudo borgmatic key export --paper` creates a version for typing back in.
- **A second copy away from home**, with a trusted person for example. Otherwise a fire hits the server, USB backup and paper at the same time.
- **Digitally, somewhere that doesn't depend on your server**, for example in an encrypted export of your password manager on a USB stick.

A sheet of paper with the passphrase is a risk if someone breaks into your home. For most people, that's smaller than the risk of losing all data. Decide deliberately what suits you.

Update the sheet when you change a password, the backup target or a provider. And try it out: the full test from [Testing restores](/en/setup/testing-restores/), with only the emergency sheet in hand, is the best dress rehearsal.

## Setting priorities

In an emergency, you don't want to think about where to start. Decide the order now and write it on the emergency sheet too. A sensible basic order:

| Order | What | Why |
| --- | --- | --- |
| 1 | Password manager | All other access depends on it. |
| 2 | Reverse proxy and login service (e.g. Traefik, Pocket ID) | Without them, hardly any other service is reachable. |
| 3 | Services with important data used daily | Files, photos, calendars, smart home. Other people are often waiting here too. |
| 4 | Everything else | Dashboards, monitoring, media and experiments. |

If someone in your household uses your services too, also think of a plan B for the meantime. For example, that photos stay on the phone until the server is running again.

## Procedure in an emergency

Plan enough time. How long the restore takes mainly depends on the amount of data and the connection to the backup. 500 GB over a 100 Mbit/s line take about eleven hours for the transfer alone. A USB disk on the new server is much faster.

<Steps>

<Step title="Assess the situation and don't rush">
First find out what exactly is broken. If only the power supply is defective, a spare part may be enough. If only the system disk is dead, the data on a second disk may still be intact.

As long as you don't know what's going on:

- **Don't write anything to a disk that might still contain data.** No repair attempts on a hunch.
- **Don't touch the backup repository.** Never run a second `repo-create`, and don't start `borgmatic` without an action on any machine until the restore is done. Otherwise the pruning rules could delete real archives.
- **Check whether the backup itself is affected.** If the server was compromised or files were already damaged before the failure, the newest archive may not be the right one.
</Step>

<Step title="Provide new hardware or a VM">
You need a computer on which your homelab can run again. It doesn't have to be the final solution right away:

- a spare computer or an old laptop,
- a VM on your PC, to get the most important things back quickly,
- a rented VPS, if your backup target is reachable over the internet.

Make sure there's enough storage for all data from the backup, plus a reserve. It's easiest with a computer of the same architecture as the old one, so x86 again or ARM again. The guide [Moving to new hardware](/en/setup/moving-hardware/) explains why.
</Step>

<Step title="Install the operating system and Docker">
Set up the new server like the old one. You already know the guides for this:

1. [Installing the OS](/en/setup/installing-the-os/)
2. [Static IP & hostname](/en/setup/static-ip-hostname/)
3. [Setting up SSH keys](/en/setup/ssh-keys/) and [Users & sudo](/en/setup/users-sudo/)
4. [Hardening SSH](/en/setup/hardening-ssh/) and [Firewall with UFW](/en/setup/firewall-ufw/)
5. [Installing Docker](/en/setup/installing-docker/)

Three things save you work later. Give the server **the same static IP address** as the old one; then port forwarding and local DNS records fit again right away. Give it **the same hostname**, because borgmatic names the archives after it and by default only shows the archives of its own hostname. And create **the same user name**. On Debian and Ubuntu, the first user gets the ID `1000`, as before, and the permissions of the restored files fit.

You can catch up on automatic updates later. Finally, check that Docker is running:

```bash
docker compose version
```
</Step>

<Step title="Install borgmatic and connect it to the backup">
Install Borg and borgmatic exactly as in the [backup guide](/en/setup/backups-borgmatic/):

```bash
sudo apt update
sudo apt install borgbackup pipx
sudo PIPX_HOME=/opt/pipx PIPX_BIN_DIR=/usr/local/bin pipx install borgmatic
```

Enter the passphrase **from the emergency sheet**:

```bash
sudo mkdir -p /etc/borgmatic
sudo chmod 700 /etc/borgmatic
sudo nano /etc/borgmatic/passphrase
sudo chmod 600 /etc/borgmatic/passphrase
```

Then create a minimal version of the configuration with `sudo nano /etc/borgmatic/config.yaml`. For the restore, your repository and the passphrase are enough:

```yaml
repositories:
    - path: ssh://backup@192.168.1.20/./borg
      label: remote

encryption_passphrase: "{credential file /etc/borgmatic/passphrase}"

# Show archives of every host name, not just this server's
match_archives: "*"
```

The last line makes sure you see the archives even if the new server has a different hostname. It only belongs in this restore configuration, not in the real one later.

If the backup is on another machine, root on the new server needs an SSH key of its own. Create it and add the public part at the backup target, that is in `~/.ssh/authorized_keys` of the `backup` user or in your provider's web interface:

```bash
sudo ssh-keygen -t ed25519
sudo cat /root/.ssh/id_ed25519.pub
```

Mount a USB disk at the same path as before. Now the decisive test:

```bash
sudo borgmatic repo-list
```

If you see your archives, the hardest part is done.

By the way, your complete configuration is in the backup: borgmatic automatically puts the configuration files it used into every archive, with their full path. This gets them into a folder for comparison:

```bash
mkdir -p /tmp/bootstrap
P=/etc/borgmatic
sudo borgmatic extract --archive latest --path "${P#/}" --destination /tmp/bootstrap
sudo ls /tmp/bootstrap/etc/borgmatic
```

The passphrase file isn't included; that's intended. Only take over the real `config.yaml` after the restore, together with the timer. The [borgmatic docs](https://torsion.org/borgmatic/how-to/extract-a-backup/) also describe the `config bootstrap` action for this. If Borg reports a key error, import the exported key from the emergency sheet with `sudo borgmatic key import`. The details are in the [borgmatic docs](https://torsion.org/borgmatic/reference/command-line/actions/key-import/).

<Callout type="warning" title="No timer yet">
Only set up the systemd timer once everything is restored. Otherwise a backup of a half-empty server would land next to your real archives, and the pruning rules could delete good states.
</Callout>
</Step>

<Step title="Get the data back">
First choose the archive. `repo-list` shows all states with their dates. Usually the newest is right. If the old server was already acting up before the failure, take an older one.

You get the complete homelab folder back to its original place with a single command. On a fresh server, `--destination /` is exactly right:

```bash
sudo borgmatic extract --archive latest --destination /
```

Instead of `latest`, you can use any name from `repo-list`. Borg also restores owners and permissions.

If you want to go by priority, first get only individual stacks. Borg stores paths without a leading slash, hence the expression after `--path` (more in [Testing restores](/en/setup/testing-restores/)):

```bash
P=__ROOT__/vaultwarden
sudo borgmatic extract --archive latest --path "${P#/}" --destination /
```

In "central" mode, the data lives under `__DATA_ROOT__`. Get it back with a second call, unless the folder is below `__ROOT__` anyway. The same goes for other paths listed in `source_directories`.

Finally, check that everything is there:

```bash
ls -la __ROOT__
```
</Step>

<Step title="Restore the databases">
If your backup stopped the stacks with databases beforehand, the database files are fine. Then skip this step. If the databases were running during the backup, the copied files may not be consistent. The safe way is then the **dump** your backup created beforehand.

The principle: move the old database files aside, start only the database container with an empty data folder and import the dump. The example uses authentik with PostgreSQL from the backup guide:

```bash
cd __ROOT__/authentik
sudo mv __DATA(authentik)__/postgres __DATA(authentik)__/postgres.alt
docker compose up -d postgresql
docker compose exec postgresql pg_isready -U authentik
```

When `pg_isready` reports `accepting connections`, import the dump:

```bash
sudo cat __DATA(authentik)__/db-dump/authentik.sql \
  | docker compose exec -T postgresql psql -U authentik -d authentik
```

With MariaDB, for Nextcloud for example, it looks like this. Here too, move the old data folder aside first and start only the database:

```bash
cd __ROOT__/nextcloud
sudo mv __DATA(nextcloud)__/db __DATA(nextcloud)__/db.alt
docker compose up -d db
sudo cat __DATA(nextcloud)__/db-dump/nextcloud.sql \
  | docker compose exec -T db sh -c 'mariadb -u root -p"$MARIADB_ROOT_PASSWORD" nextcloud'
```

Give the container a few seconds after starting until the database is ready. Services with SQLite, like Vaultwarden in its default setup, usually don't need this step. Only delete the `.alt` folders once the service has run cleanly for a few days.
</Step>

<Step title="Start the stacks in the right order">
First create the proxy network. It belongs to Docker itself and is therefore not in the backup:

```bash
docker network create __NETWORK__
```

Then start the reverse proxy, and after it the services according to your priority list:

```bash
cd __ROOT__/traefik && docker compose up -d
cd __ROOT__/vaultwarden && docker compose up -d
```

Once the most important services are back, start the rest at once. Stacks that are already running stay unchanged:

```bash
for f in __ROOT__/*/compose.yaml; do docker compose -f "$f" up -d; done
```

Docker downloads all images again. If a `compose.yaml` has a fixed tag, you get the same version as before. With `latest`, it may be a newer one. So if there are problems, look at the log first:

```bash
docker compose -f __ROOT__/vaultwarden/compose.yaml logs --tail 50
```

[Troubleshooting: first steps](/en/wiki/first-steps/) shows how to dig further from there. If a database doesn't start because its image now has a newer major version, [Database won't start after an update](/en/wiki/database-version/) helps.
</Step>

<Step title="Check DNS, router and access">
If the new server has the same IP address as the old one, there's usually nothing to do here. Otherwise, go through these points:

- **Router**: switch port forwarding for 80 and 443 (and the WireGuard port, if any) to the new internal IP, and adjust the fixed IP assignment.
- **DNS**: at home, your records point to your connection's public IP. New hardware doesn't change that. If the server runs on a new VPS, change the A and AAAA records at your DNS provider to the new address.
- **Local DNS records**, for example in your router or in Pi-hole, need to point to the new IP.

Then check that the name points to the right address:

```bash
dig +short vault.__DOMAIN__
```

`dig` is in the `bind9-dnsutils` package (`sudo apt install bind9-dnsutils`). Finally, also test your services from outside, for example on your phone over the mobile network instead of Wi-Fi.

Traefik got its certificates back along with its data folder, so it doesn't have to request anything new. If a request does fail at some point, don't restart Traefik in a loop. Let's Encrypt limits how often you may request certificates.
</Step>

<Step title="Follow-up">
Your homelab is running again. So the next emergency goes just as smoothly, a few things are still missing:

1. **Turn the backup back on**: copy the real `config.yaml` from `/tmp/bootstrap` to `/etc/borgmatic`, check the command hooks and monitoring in it, create the systemd timer from the [backup guide](/en/setup/backups-borgmatic/) and start a run by hand. Then delete `/tmp/bootstrap`.
2. **Monitoring**: reinstall agents for [Beszel](/en/setup/monitoring-beszel/) if they ran outside Docker, and check in [Uptime Kuma](/en/setup/uptime-kuma/) that all monitors are green.
3. **Automatic updates** and other settings outside `__ROOT__`: catch up on them.
4. **Update the emergency sheet**: what was missing, what took longer than expected? Write it down now, while you still remember.
5. **Old drives**: wipe or destroy them securely before you dispose of them. Your secrets are on them.
</Step>

</Steps>

## What's next?

An emergency plan is only as good as its last rehearsal. Plan a full restore once a year following [Testing restores](/en/setup/testing-restores/), with only the emergency sheet in hand. The guide [Moving to new hardware](/en/setup/moving-hardware/) shows how to move a working homelab to new hardware without downtime. You'll find tips on documentation under [Documentation](/en/wiki/documentation/).
