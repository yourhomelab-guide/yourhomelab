---
title: "Testing restores"
description: "You get individual files and a complete service back from your borgmatic backup, check a database dump and put the test on your calendar as a fixed date. Afterwards, you know that your backups really work in an emergency."
level: 2
minutes: 40
requires: [Backups with borgmatic, Docker Compose]
---

A backup you've never restored is just a hope. Maybe a folder is missing because it lived outside `__ROOT__`. Maybe the database dump is empty because the command didn't do what you thought. Or the passphrase never made it into the password manager after all. You only find all this out by restoring. Ideally now, calmly, and not when the disk is already dead.

This guide builds on [Backups with borgmatic](/en/setup/backups-borgmatic/). You always restore into a **separate folder** or onto **another computer**, never over the running services.

<Steps>

<Step title="Look at the archives">
First, check that the backups arrive regularly at all:

```bash
sudo borgmatic repo-list
```

You see a list of archives with host name, date and time. Is the date of the newest archive right? Are days missing even though the timer should run every night? Then look at the log first (`sudo journalctl -u borgmatic.service`).

Before you look into an archive, one Borg peculiarity: it stores paths **without a leading slash**. `/srv/homelab` becomes `srv/homelab` in the archive. The borgmatic commands expect the path after `--path` exactly as it is in the archive. In the examples, the shell handles this: you put the usual path into the variable `P`, and the expression after `--path` fills it in without the first slash.

You list the content of the newest archive with `list`. `latest` stands for the newest archive, but you can also use any name from `repo-list`:

```bash
P=__ROOT__/vaultwarden
sudo borgmatic list --archive latest --path "${P#/}"
```

Check here that all stacks, all `.env` files and the database dumps are included. If something is missing, add it to the configuration on the server. The [borgmatic config](/en/tools/borgmatic-config/) tool creates a new version for you if you like.
</Step>

<Step title="Get back a single file">
The most common case day to day: a file is broken or deleted. With `--path`, you get back only this path, and `--destination` sets the target folder. You have to create the folder first:

```bash
mkdir -p /tmp/restore-test
P=__ROOT__/vaultwarden/.env
sudo borgmatic extract --archive latest --path "${P#/}" --destination /tmp/restore-test
```

Borg recreates the full path below the target folder. So the file is at `/tmp/restore-test` plus the original path. Compare it with the original:

```bash
sudo diff /tmp/restore-test__ROOT__/vaultwarden/.env __ROOT__/vaultwarden/.env && echo "identisch"
```

If both are the same, the command prints `identisch`. Watch the output of `extract`: if Borg reports `never matched`, the path doesn't exist in the archive. Usually that's due to a typo in the path, or the file never was in the backed-up area.
</Step>

<Step title="Browse the backup as a folder">
Want to look around before getting something back? `borgmatic mount` mounts an archive as a folder. That needs **FUSE**, a technology that lets programs provide file systems of their own. Depending on the distribution, it's already included with the `borgbackup` package. This command makes sure:

```bash
sudo apt install fuse3 python3-pyfuse3
sudo mkdir -p /mnt/borg
sudo borgmatic mount --archive latest --mount-point /mnt/borg
```

The command returns right away; the archive stays mounted. Look around:

```bash
sudo ls /mnt/borg__ROOT__/
```

You simply copy individual files out with `sudo cp`. Finally, unmount the archive again:

```bash
sudo borgmatic umount --mount-point /mnt/borg
```

For large amounts of data, `extract` is much faster than copying from the mount.
</Step>

<Step title="Import a database dump">
A dump is only good if it can be imported. You test that with a **throwaway container** that only runs for the test. The example uses the authentik dump from the backup guide.

Get the dump from the backup:

```bash
mkdir -p /tmp/restore-test
P=__DATA(authentik)__/db-dump
sudo borgmatic extract --archive latest --path "${P#/}" --destination /tmp/restore-test
sudo ls -lh /tmp/restore-test__DATA(authentik)__/db-dump/
```

If the file is only a few bytes, something is wrong with the dump command in the configuration. Then start an empty database. Use the same image as in the stack (it's in the `compose.yaml`) so the versions match. [Database won't start after an update](/en/wiki/database-version/) explains why that matters:

```bash
docker run -d --name restore-test-db \
  -e POSTGRES_USER=authentik -e POSTGRES_PASSWORD=test -e POSTGRES_DB=authentik \
  postgres:16-alpine
```

Wait a few seconds until the database is ready, then import the dump. The dump folder belongs to root, so `sudo cat` reads the file:

```bash
sudo cat /tmp/restore-test__DATA(authentik)__/db-dump/authentik.sql \
  | docker exec -i restore-test-db psql -U authentik -d authentik
```

Now check whether tables and data are there:

```bash
docker exec restore-test-db psql -U authentik -d authentik -c '\dt'
```

If you see a long list of tables, the dump is fine. Finally, clean up the test container:

```bash
docker rm -f restore-test-db
```

For MariaDB, it works the same way, with the `mariadb` image and the `mariadb` command instead of `psql`.
</Step>

<Step title="Restore a complete service">
The most important test: does a service run again after a total failure? Ideally you check this on **another computer**, for example a VM on your PC or an old laptop. That way you honestly simulate the emergency, and the test doesn't interfere with your real server. On the same server, it's cumbersome, because container names and ports are already taken.

On the test computer, you need Docker, Borg and borgmatic. Install Borg and borgmatic as described in the backup guide. If your repository is on another computer, the test computer must be able to access it with an SSH key too. Then test the connection once with `sudo ssh`, as in the backup guide. A USB disk you simply mount on the test computer, at the same path as on the server.

Then create the passphrase. Copy it **from your password manager**, not from the server. That's exactly what you'll have to do in an emergency too:

```bash
sudo mkdir -p /etc/borgmatic
sudo chmod 700 /etc/borgmatic
sudo nano /etc/borgmatic/passphrase
sudo chmod 600 /etc/borgmatic/passphrase
```

For the restore, a short configuration in `/etc/borgmatic/config.yaml` with only the repository and the passphrase is enough. Enter the same repository as on the server:

```yaml
repositories:
    - path: ssh://backup@192.168.1.20/./borg
      label: remote

encryption_passphrase: "{credential file /etc/borgmatic/passphrase}"

# Show archives of every host name, not just this computer's
match_archives: "*"
```

The last line matters: borgmatic names archives after the host name and by default only shows the archives of its own computer. The test computer has a different name than your server, so without this line, `repo-list` and `--archive latest` would find nothing. It only belongs in this restore configuration, not on the server.

<Callout type="warning" title="No backup from the test computer">
Don't set up a timer on the test computer and don't start `borgmatic` without an action. Otherwise archives from the test environment end up in the same repository, and the pruning rules might delete real states.
</Callout>

Next, check your exported key. With `repokey`, the key lives in the repository, so normally you only need the passphrase. The export is your insurance in case exactly this file in the repository gets damaged. Show the key and compare it with the export in your password manager:

```bash
sudo borgmatic key export
```

Both should match. If you've changed the passphrase since the export, export the key again.

Then restore a service at its usual path, here Vaultwarden:

```bash
P=__ROOT__/vaultwarden
sudo borgmatic extract --archive latest --path "${P#/}" --destination /
```

<Callout title="Data lives elsewhere?">
In "central" mode, the data isn't in the stack folder. Then get it back with a second call, using `P=__DATA(vaultwarden)__` and the same `extract` command.
</Callout>

`--destination /` writes the files to their original path. That's only okay on the test computer, never on your server while the real data lives there. Borg also restores owners and permissions, which is why the command runs with `sudo`. Now start the service:

```bash
docker network create __NETWORK__
cd __ROOT__/vaultwarden
docker compose up -d
docker compose logs -f
```

Does the container start without errors in the log, and does it find its data? To see the web interface, you can temporarily add a port to the `compose.yaml` (for example `ports: ["8080:80"]` for the `vaultwarden` service) and open `http://<test computer IP>:8080`. Log in and check that your entries are there. Without HTTPS, some services refuse the login. Then it's enough for now that the container starts cleanly and finds its database.

To be really thorough, get back the complete homelab folder including the reverse proxy, that is `extract` without `--path`. That's the real emergency.
</Step>

<Step title="Check all data">
The nightly checks from the backup guide only read all data every three months. During the restore test, you can trigger this check right away, on the server or the test computer. `--only data` picks the most thorough check, and `--force` ignores the configured interval:

```bash
sudo borgmatic check --only data --force --progress
```

borgmatic reads and decrypts all archives. With large repositories or a target on the internet, that takes a long time. So start the check when you have time, on the weekend for example.
</Step>

<Step title="Clean up and repeat regularly">
Delete the test data so no copies of your secrets are lying around:

```bash
sudo rm -rf /tmp/restore-test
```

A restore test isn't a one-off. Services get added, paths change, a dump command breaks after an update. So put the test on your calendar:

- **Monthly**: look at `repo-list`, get back a file, check the reports in Uptime Kuma.
- **Every three to six months**: import a database dump and run the data check.
- **Yearly**: start a complete service on the test computer, with only the passphrase and key from your password manager.
- **After every bigger change**: new stack, new database, new backup target.

Put the dates in your calendar. Also briefly write down which steps you needed and what got stuck. In an emergency you're nervous; then ready-made instructions help more than any memory. More under [Documentation](/en/wiki/documentation/).
</Step>

</Steps>
