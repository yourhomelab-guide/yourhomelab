A homelab shouldn't keep you busy every day. But you want to know right away when something's wrong. The nightly backup failed. Vaultwarden stopped answering. The disk is 90 percent full. Without notifications, you only notice such things when you need the service. For backups, that's the worst possible moment.

The tools from the previous guides already detect such problems: [Uptime Kuma](/en/setup/uptime-kuma/) checks reachability, [Beszel](/en/setup/monitoring-beszel/) the server values, [borgmatic](/en/setup/backups-borgmatic/) knows whether the backup worked. What's missing is a shared channel through which they reach you. The background is under [Monitoring](/en/wiki/monitoring/).

## How ntfy works

[ntfy](https://ntfy.sh) (pronounced "notify") sends push messages to your phone and your browser. The principle is simple:

- Messages land in a **topic**, a kind of channel with a name you choose freely, for example `homelab`.
- To send, you make a simple HTTP request to `https://ntfy.__DOMAIN__/homelab`. That works with `curl` from any script.
- The ntfy app on your phone **subscribes** to the topic and shows every new message as a notification.

You can use the public server `ntfy.sh` without an account. But there, anyone who knows the topic name can read along. With your own server, you decide who may read and send.

<Callout type="warning" title="Who reports the server going down?">
If ntfy runs on the same server as your services, it goes down with it. The message "server not responding" then never arrives. For this one case, you need a way that doesn't depend on your server: the external check from the [Uptime Kuma guide](/en/setup/uptime-kuma/) with email notification, or a second Uptime Kuma instance that reports through `ntfy.sh`. All other messages go fine through your own server.
</Callout>

<Steps>

<Step title="Start ntfy">
Create the folder and, in it, `compose.yaml` and `.env`:

```bash
mkdir -p __ROOT__/ntfy
cd __ROOT__/ntfy
```

<ServiceFiles id="ntfy" />

The most important settings are environment variables in the `compose.yaml`:

- `NTFY_AUTH_DEFAULT_ACCESS=deny-all` makes the server private. Without an account, nobody may read or send.
- `NTFY_AUTH_FILE` and `NTFY_CACHE_FILE` put the user database and the message store as SQLite files into `__DATA(ntfy)__`. That way accounts and messages not yet picked up survive a restart.
- `NTFY_BEHIND_PROXY=true` tells ntfy that it runs behind a reverse proxy. Otherwise all visitors would count as one and be rate limited together.
- `NTFY_UPSTREAM_BASE_URL` is needed by the iPhone app for instant messages. Your server only sends a message ID to `ntfy.sh` for this, not the content. If nobody uses an iPhone, you can delete the line.

The [ntfy docs](https://docs.ntfy.sh/config/) explain all options.

```bash
docker compose up -d
docker compose logs -f ntfy
```

Open `https://ntfy.__DOMAIN__`. You see ntfy's web interface, but can't subscribe to anything yet, because there's no account.
</Step>

<Step title="Create users and permissions">
You manage users with the `ntfy` command inside the container. You create two accounts:

- an **admin account** for you. Admins may read and write all topics. You log in to the app with it.
- an account **`server`**, which your services send with. It may only write to the `homelab` topic, not read.

```bash
cd __ROOT__/ntfy
docker compose exec ntfy ntfy user add --role=admin DEINNAME
docker compose exec ntfy ntfy user add server
docker compose exec ntfy ntfy access server homelab write-only
```

Replace `DEINNAME` with your user name. With `user add`, ntfy asks for a password. Use long, random passwords from your password manager. The last line is an entry in the **access control list** (ACL): user `server`, topic `homelab`, write only.

So you don't have to enter the `server` password everywhere, create an **access token**. It's a long string starting with `tk_` that replaces user name and password:

```bash
docker compose exec ntfy ntfy token add --label=homelab server
```

Save the token in your password manager. It has the same rights as the `server` account, so only writing to `homelab`. With `docker compose exec ntfy ntfy access`, you can see all accounts and permissions at any time.
</Step>

<Step title="App on the phone">
Install the ntfy app from the Play Store, F-Droid or the App Store. You'll find links to all versions on [ntfy.sh](https://ntfy.sh).

1. In the app, open the settings and add your admin account under "Users": server `https://ntfy.__DOMAIN__`, plus user name and password.
2. Tap "+" and enter `homelab` as the topic. Choose "Use another server" and enter `https://ntfy.__DOMAIN__`.
3. On Android, turn on **instant delivery** when subscribing. The app then keeps a connection to your server open. Without this option, messages from your own servers only arrive with a delay.

In the browser, it works the same at `https://ntfy.__DOMAIN__`: log in, subscribe to the topic, allow browser notifications.
</Step>

<Step title="Test with curl">
Now send a message from the server. Fill in your token:

```bash
curl \
  -H "Authorization: Bearer tk_DEIN_TOKEN" \
  -H "Title: Test aus dem Homelab" \
  -H "Tags: white_check_mark" \
  -d "Wenn du das liest, funktioniert ntfy." \
  https://ntfy.__DOMAIN__/homelab
```

After a second or two, your phone should ring. With `-H "Priority: high"`, a message becomes more noticeable, and `Tags` adds icons. The [docs on publishing](https://docs.ntfy.sh/publish/) show all options.

Also check the other direction: without a token, the request must fail.

```bash
curl -d "Das darf nicht ankommen" https://ntfy.__DOMAIN__/homelab
```

Instead of a confirmation, you get an error message, and nothing arrives on the phone. That's how it should be.

Any script of your own can report with the same request that it's done or has a problem. The script reads the token from a file only root may read, not from the script itself.
</Step>

<Step title="Connect Uptime Kuma">
In Uptime Kuma, open "Settings → Notifications → Setup Notification" and choose the type **ntfy**:

| Field | Value |
| --- | --- |
| Server URL | `https://ntfy.__DOMAIN__` |
| Topic | `homelab` |
| Priority | 4 or 5, so outages stand out |
| Authentication | Access token, your `tk_…` token |

Check "Default enabled" and "Apply on all existing monitors" and click "Test". From now on, Uptime Kuma reports every outage and every recovery.
</Step>

<Step title="Connect Beszel">
Beszel sends notifications through [Shoutrrr](https://beszel.dev/guide/notifications/ntfy) URLs. Open "Settings → Notifications" and enter under "Webhook / Push notifications":

```text
ntfy://:tk_DEIN_TOKEN@ntfy.__DOMAIN__/homelab
```

The colon before the token belongs there: it stands where user name and password would otherwise go. With "Test URL", you check the connection. If it doesn't work, the Beszel docs name an alternative format.

Then you decide per system with the bell icon which warnings Beszel sends, for example "Status" for an agent that's down and "Disk" from 85 percent usage. Details are in the guide [Monitoring with Beszel](/en/setup/monitoring-beszel/).
</Step>

<Step title="Connect borgmatic">
borgmatic has a hook of its own for ntfy. First put the token into a file only root may read, just like your backup's passphrase:

```bash
printf '%s' 'tk_DEIN_TOKEN' | sudo tee /etc/borgmatic/ntfy-token > /dev/null
sudo chmod 600 /etc/borgmatic/ntfy-token
```

Then add this to `/etc/borgmatic/config.yaml` (`sudo nano /etc/borgmatic/config.yaml`):

```yaml
ntfy:
    topic: homelab
    server: https://ntfy.__DOMAIN__
    access_token: "{credential file /etc/borgmatic/ntfy-token}"
    fail:
        title: Backup fehlgeschlagen
        message: borgmatic meldet einen Fehler. Details im Log.
        priority: high
        tags: warning
    states:
        - fail
```

Feel free to write title and message in your own language. Without `states`, borgmatic also only reports errors; the line makes that visible. If you also want a message on success, add a `finish` block with `priority: low` and `- finish` under `states`. In the long run, though, daily success messages get annoying and you'll start to overlook them.

ntfy doesn't report whether the backup ran at all. That's what the push monitor in Uptime Kuma from the [backup guide](/en/setup/backups-borgmatic/) is for. Together, both cases are covered: borgmatic reports errors right away through ntfy, and Uptime Kuma reports a missing backup, again through ntfy.

```bash
sudo borgmatic config validate
```

To test, temporarily set `- start` under `states` and add a `start` block with a `title`. Then start a run with `sudo systemctl start borgmatic.service`. If the message arrives, remove both again. All options are in the [configuration reference](https://torsion.org/borgmatic/reference/configuration/) under `ntfy`.
</Step>

</Steps>

## Alternative: email

Push messages are fast and stand out. But some people prefer email, for example because they check their inbox anyway. Uptime Kuma and Beszel can both send mail. For that, you enter a mail account's **SMTP details**: server, port, user, password.

- Don't use your main account for this. Many providers allow a separate **app password** that's only for sending and can be revoked individually.
- Alternatively, use an **SMTP relay service** that delivers mail on behalf of your server. Many have a free quota that's enough for a homelab.
- Running a mail server of your own isn't worth it for this. Mail from private servers often lands in spam or gets rejected.

A good compromise: everyday messages through ntfy, and the external check that detects the whole server going down by email.
