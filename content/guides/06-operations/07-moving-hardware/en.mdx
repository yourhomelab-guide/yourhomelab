---
title: "Moving to new hardware"
description: "You move your complete homelab with all stacks, data and certificates to a new server. In the end, all services run on the new hardware, and the old server stays around as a fallback until everything works reliably."
level: 2
minutes: 60
requires: [Linux server, Docker Compose, SSH access to both servers]
---

<OneWay />

Sooner or later, the old mini PC is too slow, too loud or too power-hungry. Or you're upgrading from a Raspberry Pi to a proper server. The move sounds like a lot of work. With this site's folder structure, though, it's manageable: everything that belongs to your services lives in a single folder, `__ROOT__`. You copy it to the new server, start the stacks, and you're done.

There are still a few things to watch: the services must be stopped while copying, file permissions must be kept, and databases move most safely as a dump. That's exactly what this guide shows.

<Steps>

<Step title="Take stock on the old server">
First get an overview. Which stacks are running right now?

```bash
docker ps --format '{{.Names}}\t{{.Image}}'
ls __ROOT__
```

Also check what lives **outside** `__ROOT__` and has to move along:

- **Named volumes**: data in volumes managed by Docker itself lives under `/var/lib/docker/volumes` and isn't copied along. `docker volume ls` shows them. Stacks following this site's templates use bind mounts; then the list is empty or only contains leftovers.
- **Data folder in "central" mode** under `__DATA_ROOT__`, if it isn't below `__ROOT__` anyway, and other mounted paths, such as a media collection on a second disk.
- **System settings**: `/etc/borgmatic`, timers and crontabs, entries in `/etc/fstab`, your UFW rules (`sudo ufw status`).
- **Agents outside Docker**, for example the Beszel agent, if you installed it as a system service.

Write the list down. It's also a good start for your [documentation](/en/wiki/documentation/).

Finally, check the architecture of both computers:

```bash
uname -m
```

`x86_64` stands for regular PCs and mini PCs, `aarch64` for ARM, such as a Raspberry Pi. If both servers show the same, everything is simple. If not, read the box at the end of this guide before you continue.
</Step>

<Step title="Prepare the new server">
Set up the new server just like the old one. You know the guides for this:

1. [Installing the OS](/en/setup/installing-the-os/) and [Static IP & hostname](/en/setup/static-ip-hostname/). For the transition, use a different IP address than the old server.
2. [SSH keys](/en/setup/ssh-keys/), [Users & sudo](/en/setup/users-sudo/), [Hardening SSH](/en/setup/hardening-ssh/), [Firewall with UFW](/en/setup/firewall-ufw/) and [Automatic updates](/en/setup/automatic-updates/)
3. [Installing Docker](/en/setup/installing-docker/)

Create the same user name as on the old server and check the user ID on both computers:

```bash
id
```

If both sides show `uid=1000`, the copied files belong to you again on the new server. On Debian and Ubuntu, that's the normal case for the first user.

Then create the homelab folder and install rsync, the copying tool. rsync must be installed on **both** servers:

```bash
sudo mkdir -p __ROOT__
sudo chown $USER:$USER __ROOT__
sudo apt install rsync
```
</Step>

<Step title="Set up access between the servers">
So that owners, groups and permissions of all files are kept, rsync has to run as root on both sides. But you rightly turned off direct root login over SSH when [hardening](/en/setup/hardening-ssh/). That's why you take a small detour: you fetch the data from the new server, log in to the old one as a regular user and start rsync there with `sudo`.

On the **new** server, root gets an SSH key. If you already created one there, for borgmatic for example, skip the first command:

```bash
sudo ssh-keygen -t ed25519
sudo cat /root/.ssh/id_ed25519.pub
```

On the **old** server, add this public key for your user. Also allow your user temporarily to start rsync with sudo without a password:

```bash
nano ~/.ssh/authorized_keys
echo "$USER ALL=(root) NOPASSWD: /usr/bin/rsync" | sudo tee /etc/sudoers.d/umzug
sudo chmod 440 /etc/sudoers.d/umzug
sudo visudo -c
```

In the editor, paste the key as a new line. `visudo -c` checks the sudo configuration and should report `parsed OK` for all files. Now test from the **new** server whether everything works. Replace `benutzer` and `192.168.1.10` with your user name and the old server's IP address:

```bash
sudo ssh benutzer@192.168.1.10 sudo rsync --version
```

The first time, SSH asks whether you trust the server. Confirm with `yes`. If you then see rsync's version, access is ready.
</Step>

<Step title="Dump databases and stop the stacks">
Databases move most safely as a **dump**, an export into a file. A dump works independently of architecture and storage format. Copied database files usually run too, but only if the image version and architecture stay the same. The dump is your insurance.

If you've set up [Backups with borgmatic](/en/setup/backups-borgmatic/), the matching commands are already in your configuration. Run them by hand now, for example for authentik:

```bash
sudo mkdir -p __DATA(authentik)__/db-dump
docker compose -f __ROOT__/authentik/compose.yaml exec -T postgresql pg_dump -U authentik -d authentik \
  | sudo tee __DATA(authentik)__/db-dump/authentik.sql > /dev/null
sudo ls -lh __DATA(authentik)__/db-dump/
```

If the file is only a few bytes, something went wrong. Then check the command before you continue.

Now stop all stacks so nothing changes while copying. The loop goes through every stack folder:

```bash
for f in __ROOT__/*/compose.yaml; do docker compose -f "$f" down; done
docker ps
```

`docker ps` should now be empty. `down` only removes the containers; the data in the stack folder stays. Also turn off the nightly backup on the old server so it doesn't start in the middle of the move:

```bash
sudo systemctl disable --now borgmatic.timer
```
</Step>

<Step title="Copy the data with rsync">
Now copy the complete homelab folder. The command runs on the **new** server and fetches the data from the old one:

```bash
sudo rsync -aHAX --numeric-ids --info=progress2 \
  --rsync-path="sudo rsync" \
  benutzer@192.168.1.10:__ROOT__/ __ROOT__/
```

What the options mean:

- `-a` (archive) copies recursively and keeps permissions, owners, timestamps and symbolic links.
- `-H`, `-A` and `-X` also keep hard links, ACLs (extended permissions) and extended file attributes.
- `--numeric-ids` transfers owners as numbers instead of names. That's important because containers often use user IDs that don't exist as names on the host at all, such as the database's ID inside the container.
- `--rsync-path="sudo rsync"` starts rsync on the old server with root rights so it can read all files.

Watch the **trailing slashes** on both paths. With `__ROOT__/`, rsync copies the folder's content into the target folder. Without the slash, the folder itself ends up inside it once more.

If you use "central" mode and `__DATA_ROOT__` is outside `__ROOT__`, repeat the command for that folder. The same goes for other paths from your inventory:

```bash
sudo mkdir -p __DATA_ROOT__
sudo rsync -aHAX --numeric-ids --info=progress2 \
  --rsync-path="sudo rsync" \
  benutzer@192.168.1.10:__DATA_ROOT__/ __DATA_ROOT__/
```

If the transfer breaks off, simply run the same command again. rsync only transfers what's still missing. Finally, check with a dry run that both sides are the same. `-n` only simulates, and `-i` lists every difference. If the list stays empty, everything has arrived:

```bash
sudo rsync -aHAXn -i --numeric-ids --rsync-path="sudo rsync" \
  benutzer@192.168.1.10:__ROOT__/ __ROOT__/
```

Afterwards, remove the sudo exception on the **old** server again:

```bash
sudo rm /etc/sudoers.d/umzug
```
</Step>

<Step title="Start the stacks on the new server">
The proxy network belongs to Docker and isn't copied along. Create it again:

```bash
docker network create __NETWORK__
```

Start the reverse proxy first and look at the log:

```bash
cd __ROOT__/traefik
docker compose up -d
docker compose logs --tail 30
```

Then start all other stacks at once. Stacks that are already running stay unchanged:

```bash
for f in __ROOT__/*/compose.yaml; do docker compose -f "$f" up -d; done
docker ps
```

Docker downloads all images again, which takes a while the first time.

If you've switched architecture or a database doesn't start cleanly, import the dump. The principle: move the old database files aside, start only the database container with an empty folder, import the dump, start the rest. For authentik, it looks like this:

```bash
cd __ROOT__/authentik
docker compose down
sudo mv __DATA(authentik)__/postgres __DATA(authentik)__/postgres.alt
docker compose up -d postgresql
docker compose exec postgresql pg_isready -U authentik
sudo cat __DATA(authentik)__/db-dump/authentik.sql \
  | docker compose exec -T postgresql psql -U authentik -d authentik
docker compose up -d
```

Repeat `pg_isready` until `accepting connections` appears, and only then import the dump. Only delete the `.alt` folder once the service has run cleanly for a few days.

Finally, carry over the settings outside `__ROOT__` from your inventory, for example the borgmatic configuration. The backup timer only gets turned on in the last step.
</Step>

<Step title="Switch over: IP, DNS and port forwarding">
So far, the new server runs under its own IP address. Now you redirect the traffic. There are two ways:

**Way 1: the new server takes over the old IP address.** That's usually the simpler one. Shut down the old server, change the new server's static IP to the old address (as in [Static IP & hostname](/en/setup/static-ip-hostname/)) and adjust the fixed assignment in the router. Port forwarding and local DNS records are then right immediately.

**Way 2: the new server keeps its IP address.** Then switch over:

- **Port forwarding on the router** for 80 and 443, and the WireGuard port if you have one, to the new internal IP.
- **Local DNS records**, for example in the router or in Pi-hole.
- **Public DNS records** only if the public IP changes. At home, it stays the same, because your records point to your connection, not to the server. If you're moving to a new VPS, change the A and AAAA records at your DNS provider.

When moving to a new VPS, it helps to lower the TTL of the DNS records to a few minutes a day before. The TTL defines how long other computers remember a record. Then the new records take effect faster.

Afterwards, test all services, ideally from outside too, for example on your phone over the mobile network. Traefik brought its certificates along with its data folder, so it doesn't have to request anything new. Still, check in the browser that the lock appears.
</Step>

<Step title="Switch backup and monitoring over">
Now turn on the backup on the new server. If your backup target is on another computer, add the new server's root public SSH key there (see [Backups with borgmatic](/en/setup/backups-borgmatic/)). Enable the timer and start a run by hand:

```bash
sudo borgmatic config validate
sudo systemctl enable --now borgmatic.timer
sudo systemctl start borgmatic.service
sudo journalctl -u borgmatic.service -e
```

borgmatic names archives after the host name. By default, pruning rules and commands like `repo-list` only refer to archives of their own host name. So if the new server has a different name, it starts a new series, and the old server's archives stay untouched. As a fallback, that's even handy. To show or delete the old archives, you then need the `--match-archives` option; details are in the [borgmatic docs](https://torsion.org/borgmatic/reference/configuration/). If you want to avoid that, give the new server the same host name as the old one.

Also update your monitoring: install the [Beszel](/en/setup/monitoring-beszel/) agent on the new server if it ran as a system service, and check in [Uptime Kuma](/en/setup/uptime-kuma/) that all monitors are green.
</Step>

<Step title="Only switch off the old server after a few days">
After the move, leave the old server switched off but unchanged. Some problems only show up after days: a nightly job that's missing, a service you only use once a week, a file that lived outside `__ROOT__` after all. As long as the old server is still there, you catch up on it in minutes.

After one or two weeks without surprises, you can dismantle it for good. Wipe the drives securely before you sell it or give it away. All your data and secrets are on them.

Finally, update your [documentation](/en/wiki/documentation/) and the emergency sheet from the [emergency plan](/en/setup/emergency-plan/): new hardware, new IP, new SSH key at the backup target. The [docs export](/en/tools/docs-export/) generates the overview of your services with ports and paths again.
</Step>

</Steps>

<Callout type="warning" title="Switching between ARM and x86">
If you move from a Raspberry Pi (ARM) to a mini PC (x86) or the other way round, you need an image for the new architecture for every container. Most well-known images are available for both. On Docker Hub, you see this under "OS/ARCH"; on the server, you check it with `docker buildx imagetools inspect <image>`. If a `compose.yaml` has a fixed platform (`platform:`), adjust or remove it.

When switching architecture, databases **always** move as a dump. The database files themselves can't be transferred reliably between architectures. All other files, that is configuration, uploads and SQLite databases, you can copy normally.
</Callout>

## The alternative: moving from the backup

You can also do the whole move through your borgmatic backup instead of copying directly: stop the stacks, create a last backup and restore it on the new server, exactly as described in the [emergency plan](/en/setup/emergency-plan/). Depending on the backup target, that takes longer, but it's a complete restore test at the same time. Afterwards you know for sure that your backup works in an emergency.
