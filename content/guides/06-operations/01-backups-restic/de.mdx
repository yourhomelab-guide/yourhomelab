<OneWay />

Festplatten sterben, Updates gehen schief, und manchmal löschst du einfach den falschen Ordner. Ein Backup ist deshalb der wichtigste Dienst in deinem Homelab. Er muss nur drei Dinge können: regelmäßig laufen, außerhalb des Servers liegen und sich wiederherstellen lassen.

[restic](https://restic.net) erledigt das mit einem einzigen Programm. Es verschlüsselt alles, bevor es den Server verlässt, speichert nur geänderte Teile (Deduplizierung) und hält viele Versionen, sogenannte **Snapshots**, platzsparend vor. Das Ziel heißt bei restic **Repository**: ein Ordner auf einer USB-Platte, ein zweiter Rechner per SFTP oder ein S3-kompatibler Speicher in der Cloud.

Weil in diesem Guide alles unter `__ROOT__` liegt, reicht ein einziger Pfad. Hintergründe zur 3-2-1-Regel und zu Aufbewahrungszeiten findest du unter [Backup-Strategien](/de/nachschlagen/backup-strategien/).

<Steps>

<Step title="restic installieren">
restic liegt in den Paketquellen von Debian und Ubuntu.

```bash
sudo apt update
sudo apt install restic
restic version
```

Die Paketversion ist oft etwas älter als die aktuelle Version auf GitHub. Für alles in diesem Guide reicht sie.
</Step>

<Step title="Konfiguration und Passwort anlegen">
Das Backup läuft als `root`. Nur so kann restic auch Dateien lesen, die Container mit eigenen Benutzer-IDs angelegt haben, etwa Datenbankordner. Die Einstellungen kommen deshalb nach `/etc/restic`, lesbar nur für root.

Erzeuge zuerst ein zufälliges Passwort für das Repository:

```bash
sudo mkdir -p /etc/restic
sudo chmod 700 /etc/restic
openssl rand -base64 32 | sudo tee /etc/restic/password > /dev/null
sudo chmod 600 /etc/restic/password
```

<Callout type="warning" title="Passwort doppelt aufbewahren">
Ohne dieses Passwort sind alle Backups wertlos, auch für dich. Es gibt keinen Weg, es zurückzusetzen. Kopiere es sofort in deinen Passwortmanager oder drucke es aus. Es darf nicht nur auf dem Server liegen, den du sichern willst.

```bash
sudo cat /etc/restic/password
```
</Callout>

Lege dann die Datei `/etc/restic/env` an, zum Beispiel mit `sudo nano /etc/restic/env`. Sie sagt restic, wo das Repository liegt und wo das Passwort steht. Wähle **eine** der drei Varianten für `RESTIC_REPOSITORY`:

```bash
# Where the backups go. Pick ONE of these:

# a) USB disk mounted at /mnt/backup
RESTIC_REPOSITORY=/mnt/backup/restic

# b) Second computer via SFTP (root needs SSH key access to it)
# RESTIC_REPOSITORY=sftp:backup@192.168.1.20:/srv/restic

# c) S3-compatible storage
# RESTIC_REPOSITORY=s3:https://s3.example.com/my-bucket/homelab
# AWS_ACCESS_KEY_ID=...
# AWS_SECRET_ACCESS_KEY=...

RESTIC_PASSWORD_FILE=/etc/restic/password
```

```bash
sudo chmod 600 /etc/restic/env
```

Ein paar Hinweise zu den Zielen:

- **USB-Platte**: einfach und schnell. Sie schützt aber nicht vor Brand oder Diebstahl, wenn sie neben dem Server liegt. Tipp: zwei Platten im Wechsel, eine davon außer Haus.
- **SFTP**: Der zweite Rechner braucht nur SSH. Weil das Backup als root läuft, muss `root` sich per SSH-Schlüssel dort anmelden können (`sudo ssh-keygen -t ed25519`, dann den Schlüssel aus `/root/.ssh/id_ed25519.pub` auf dem Zielrechner eintragen). Teste die Verbindung einmal mit `sudo ssh backup@192.168.1.20`, damit der Host-Key bestätigt ist.
- **S3-kompatibel**: Viele Anbieter bieten S3-Speicher an, bezahlt wird meist pro Gigabyte und Monat. Die genaue URL und die Zugangsschlüssel findest du beim Anbieter. restic verschlüsselt vorher, der Anbieter sieht deine Daten nicht.

Weitere Ziele wie Backblaze B2 oder einen eigenen REST-Server beschreibt die [restic-Doku](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html).
</Step>

<Step title="Repository anlegen">
Für die Befehle von Hand wechselst du in eine root-Shell und lädst die Einstellungen. `set -a` sorgt dafür, dass alle Variablen aus der Datei an restic weitergegeben werden.

```bash
sudo -i
set -a; source /etc/restic/env; set +a
restic init
```

restic legt das Repository an und meldet `created restic repository`. Das machst du nur ein einziges Mal. Bleib für die nächsten Schritte in dieser root-Shell, mit `exit` verlässt du sie am Ende wieder.
</Step>

<Step title="Datenbanken vorher sichern">
Die meisten Dienste speichern ihre Daten als Dateien, die restic einfach kopieren kann. Bei Datenbanken wie PostgreSQL oder MariaDB ist das riskant: Sie schreiben laufend, und eine Kopie mitten im Schreiben kann unbrauchbar sein. Deshalb erzeugst du vorher einen **Dump**, also einen konsistenten Export der Datenbank als Datei. restic sichert dann diesen Dump mit.

Beispiel für den [Authentik](/de/dienste/authentik/)-Stack mit PostgreSQL. `-T` schaltet das Terminal ab, damit die Ausgabe sauber in der Datei landet:

```bash
mkdir -p __ROOT__/authentik/backup
docker compose -f __ROOT__/authentik/compose.yaml exec -T postgresql \
  pg_dump -U authentik -d authentik | gzip > __ROOT__/authentik/backup/authentik.sql.gz
```

Für MariaDB, etwa bei [Nextcloud](/de/dienste/nextcloud/), sieht es so aus. Die einfachen Anführungszeichen sorgen dafür, dass die Variable erst im Container ausgewertet wird:

```bash
mkdir -p __ROOT__/nextcloud/backup
docker compose -f __ROOT__/nextcloud/compose.yaml exec -T db \
  sh -c 'mariadb-dump --single-transaction -u root -p"$MARIADB_ROOT_PASSWORD" nextcloud' \
  | gzip > __ROOT__/nextcloud/backup/nextcloud.sql.gz
```

Container- und Datenbanknamen stehen in der `compose.yaml` des jeweiligen Dienstes. Viele Projekte beschreiben in ihrer Doku auch einen eigenen Backup-Weg. Der hat dann Vorrang.

**Die einfache Alternative:** Du stoppst den Stack kurz, sicherst und startest ihn wieder. Das ist immer konsistent, der Dienst ist dafür ein paar Minuten nicht erreichbar. Nachts stört das meist niemanden.

```bash
docker compose -f __ROOT__/nextcloud/compose.yaml stop
# ... run the backup ...
docker compose -f __ROOT__/nextcloud/compose.yaml start
```
</Step>

<Step title="Erstes Backup">
Jetzt sicherst du den kompletten Homelab-Ordner:

```bash
restic backup __ROOT__
restic snapshots
```

Das erste Backup dauert je nach Datenmenge eine Weile. Die folgenden sind viel schneller, weil restic nur Änderungen überträgt. `restic snapshots` zeigt dir den neuen Snapshot mit Datum und ID.

<Callout title="Daten liegen woanders?">
Hast du in „Mein Setup“ den Modus „zentral“ gewählt und liegen deine Daten nicht unterhalb von `__ROOT__`, gib beide Ordner an: `restic backup __ROOT__ __DATA_ROOT__`. Dasselbe gilt für Pfade außerhalb, die du in Stacks eingebunden hast, etwa eine Mediensammlung auf einer zweiten Platte.
</Callout>

Die `.env`-Dateien mit deinen Secrets sind im Backup enthalten. Das ist gewollt, denn ohne sie läuft kein Dienst wieder an. restic verschlüsselt sie, bevor sie den Server verlassen.
</Step>

<Step title="Backup-Skript schreiben">
Damit alles automatisch läuft, fasst ein kleines Skript die Schritte zusammen: Dumps erzeugen, sichern, alte Snapshots aufräumen, Repository prüfen. Lege es mit `nano /usr/local/bin/homelab-backup` an (du bist noch root):

```bash
#!/usr/bin/env bash
# Nightly homelab backup with restic
set -euo pipefail

set -a
source /etc/restic/env
set +a

# 1. Database dumps (one block per stack with a database)
mkdir -p __ROOT__/authentik/backup
docker compose -f __ROOT__/authentik/compose.yaml exec -T postgresql \
  pg_dump -U authentik -d authentik | gzip > __ROOT__/authentik/backup/authentik.sql.gz

# 2. Back up the whole homelab folder
restic backup __ROOT__

# 3. Keep 7 daily, 4 weekly and 6 monthly snapshots, delete the rest
restic forget --keep-daily 7 --keep-weekly 4 --keep-monthly 6 --prune

# 4. Check the repository structure
restic check
```

```bash
chmod 700 /usr/local/bin/homelab-backup
```

Die Dump-Zeilen passt du an deine Stacks an. Hast du keine Datenbanken, lösch den Block. `set -euo pipefail` bricht das Skript beim ersten Fehler ab. So wird nach einem fehlgeschlagenen Dump nicht stillschweigend weitergesichert.

`forget --prune` entfernt alte Snapshots nach deinen Regeln und gibt den Platz frei. Die Zahlen oben sind ein guter Start: Du kannst eine Woche lang jeden Tag zurückspringen und ein halbes Jahr lang jeden Monat. `restic check` prüft, ob die Struktur des Repositorys stimmt. Einmal im Monat lohnt es sich zusätzlich, einen Teil der Daten wirklich zu lesen:

```bash
restic check --read-data-subset=5%
```

Führe das Skript einmal von Hand aus und prüfe die Ausgabe:

```bash
/usr/local/bin/homelab-backup
```
</Step>

<Step title="Jede Nacht automatisch starten">
Ein **systemd-Timer** startet das Skript zu einer festen Uhrzeit. Er holt einen verpassten Lauf nach, wenn der Server zur geplanten Zeit aus war, und schreibt alles ins Systemlog. Lege zwei Dateien an.

`/etc/systemd/system/homelab-backup.service`:

```ini
[Unit]
Description=Homelab backup with restic
Wants=network-online.target
After=network-online.target docker.service

[Service]
Type=oneshot
ExecStart=/usr/local/bin/homelab-backup
```

`/etc/systemd/system/homelab-backup.timer`:

```ini
[Unit]
Description=Nightly homelab backup

[Timer]
OnCalendar=*-*-* 03:00:00
RandomizedDelaySec=15min
Persistent=true

[Install]
WantedBy=timers.target
```

Aktivieren und prüfen:

```bash
systemctl daemon-reload
systemctl enable --now homelab-backup.timer
systemctl list-timers homelab-backup.timer
```

Einen Lauf sofort starten und das Log ansehen:

```bash
systemctl start homelab-backup.service
journalctl -u homelab-backup.service -e
```

Lieber cron? Dann reicht eine Zeile in der Crontab von root (`crontab -e`):

```bash
0 3 * * * /usr/local/bin/homelab-backup >> /var/log/homelab-backup.log 2>&1
```

Mit `exit` verlässt du die root-Shell.
</Step>

<Step title="Über Fehler informiert werden">
Ein Backup, das seit Wochen still fehlschlägt, merkst du erst, wenn du es brauchst. Lass dich deshalb benachrichtigen. Einfach geht das mit einem **Push-Monitor** in [Uptime Kuma](/de/einrichten/uptime-kuma/): Das Skript ruft am Ende eine URL auf. Bleibt der Aufruf aus, meldet sich Uptime Kuma bei dir. Hänge dazu diese Zeile ans Ende des Skripts und setze deine Push-URL ein:

```bash
curl -fsS -m 10 "https://status.__DOMAIN__/api/push/DEIN-PUSH-TOKEN?status=up&msg=OK" > /dev/null
```

Weil das Skript bei jedem Fehler vorher abbricht, kommt der Aufruf nur nach einem erfolgreichen Lauf an.
</Step>

</Steps>
