A `compose.yaml` describes **how** a service runs. But passwords, API keys and values that differ from server to server don't belong in it. Otherwise they end up in every backup diff, in every screenshot and, in the worst case, in a public Git repository.

The solution is a file called `.env` in the same folder. Docker Compose reads it automatically and fills in its values wherever the `compose.yaml` says `${NAME}`. That keeps the `compose.yaml` free of secrets, and you can share or version it. You'll find the background in the articles [.env files](/en/wiki/env-files/) and [Managing secrets](/en/wiki/managing-secrets/).

In this guide, you keep working with the whoami stack from the [first stack](/en/setup/first-stack/).

<Steps>

<Step title="Create the .env">
Switch to the stack folder and create the `.env`:

```bash
cd __ROOT__/whoami
nano .env
```

Contents:

```bash
# Time zone for the container
TZ=__TZ__
# Name that whoami shows in its answer
WHOAMI_NAME=homelab
```

The rules are simple: one variable per line, `NAME=value`, no spaces around the `=`. Lines starting with `#` are comments.
</Step>

<Step title="Use the variables in compose.yaml">
Open the `compose.yaml` and add the `environment:` block:

```yaml
services:
  whoami:
    image: traefik/whoami:latest
    container_name: whoami
    restart: unless-stopped
    ports:
      - "8080:80"
    environment:
      - TZ=${TZ}
      - WHOAMI_NAME=${WHOAMI_NAME}
```

Important to understand: the `.env` is **not** passed to the container as a whole automatically. Compose only replaces the `${…}` spots in the `compose.yaml`. A value only reaches the container through `environment:`. This is called interpolation.
</Step>

<Step title="Check with docker compose config">
This command shows the `compose.yaml` the way Compose sees it after filling in the variables. Typos stand out right away.

```bash
docker compose config
```

Under `environment:`, you should now see your real values, such as `WHOAMI_NAME: homelab`. If a variable is missing from the `.env`, Compose warns with `variable is not set. Defaulting to a blank string.`

<Callout type="warning" title="The output contains plain text">
`docker compose config` also shows all passwords in plain text. Don't copy the output into a forum or chat without checking it.
</Callout>

The [Compose explainer](/en/tools/compose-explainer/) explains what the individual lines of a `compose.yaml` mean. But only paste the `compose.yaml` there, not the output with your secrets.
</Step>

<Step title="Restart the stack and test">
Compose detects the changed configuration and recreates the container.

```bash
docker compose up -d
curl http://localhost:8080
```

The answer now contains the line `Name: homelab`. The value came from the `.env` through the `compose.yaml` into the container.

By the way, a simple restart with `docker compose restart` isn't enough. It doesn't pick up changed variables. After changing the `.env` or `compose.yaml`, always use `docker compose up -d`. If the container then keeps restarting, a variable is often missing; see [Container in a restart loop](/en/wiki/restart-loop/).
</Step>

<Step title="Create secure secrets">
For passwords and keys you don't have to type yourself, use long random values. `openssl` comes preinstalled on Debian and Ubuntu:

```bash
openssl rand -hex 32
```

That gives you 64 characters from `0-9` and `a-f`. You can also append the value straight to the `.env` without it showing up in the terminal history:

```bash
echo "DB_PASSWORD=$(openssl rand -hex 32)" >> .env
```

`DB_PASSWORD` is just an example name here. A service's page shows in its `.env` which variables the service needs. The random values there are already filled in by your browser.

<Callout title="Why hex?">
Hex values contain no special characters. That saves trouble: otherwise Compose tries to read a `$` in the `.env` as a variable. If you do need a `$` in a value, put the value in single quotes; then Compose takes it literally.
</Callout>
</Step>

<Step title="Protect the file">
Only your user should be able to read the `.env`. `chmod 600` means: read and write for the owner only, nothing for everyone else.

```bash
chmod 600 .env
ls -l .env
```

The output now shows `-rw-------`. Do this for every new `.env`.
</Step>

<Step title="Keep the .env out of Git">
If you keep your Compose files in a Git repository, add `.env` and the data folders to the `.gitignore`. Ideally to the `.gitignore` in the repository's root folder, so it applies to all stacks:

```bash
printf '.env\ndata/\n' >> .gitignore
```

So others (or you yourself on a new server) know which variables are needed, you can check in a `.env.example` with placeholders instead of real values.

Without Git, you can skip this step. Just remember: the `.env` is part of your backup. So the backup should be encrypted. [borgmatic](/en/setup/backups-borgmatic/) does that automatically.
</Step>

</Steps>

## Good to know

- **Passwords don't change retroactively.** Many databases only read the password from the environment on the very first start and create the user with it. If you change it later in the `.env`, it no longer matches the database. So decide on secrets before the first start.
- **Enforce required variables.** With `${DB_PASSWORD:?fehlt in .env}`, Compose stops with this message instead of starting with an empty value. `${TZ:-Europe/Berlin}`, on the other hand, sets a default if the variable is missing.
- **Environment variables aren't invisible.** Anyone in the `docker` group can see them, for example with `docker inspect`. For beginners, the `.env` with `chmod 600` is perfectly enough. [Managing secrets](/en/wiki/managing-secrets/) describes stricter ways, such as Compose secrets or variables ending in `_FILE`.
