Before you start the first container, one decision pays off: where do your Compose files and the services' data live? That sounds like a detail. But it decides how easy backups, moves and troubleshooting will be later. You'll find background and more variants in the article [Directory structure](/en/wiki/directory-structure/).

## There are several common variants

Docker itself doesn't prescribe anything. In tutorials and forums, you'll mainly come across these folders:

| Location | Typical for | Note |
| --- | --- | --- |
| `/opt/stacks` or `/opt/docker` | Dockge (uses `/opt/stacks` by default), many blog posts | Works well. By Linux convention, though, `/opt` is meant more for add-on software than for data. |
| `~/docker` in the home directory | Quick tests, beginner tutorials | No `sudo` needed. But it's tied to one user account, and the home directory holds lots of other things. |
| `/srv/…` | Servers that provide data | According to the Filesystem Hierarchy Standard, `/srv` is meant exactly for "data served by this system". |
| Separate: Compose files here, data there | Bigger setups, Git workflows | Flexible, but two places you have to keep an eye on. |

All of these are legitimate. More important than the exact path is that you choose **one** place and stick with it.

## This site's recommendation

To get started, we recommend **a single root folder**: `/srv/homelab`. In the commands on this site, it's called `__ROOT__` and replaced with the value from "My setup". Inside it, every service gets its own folder, and that folder holds everything that belongs to the service:

```
/srv/homelab/            ← __ROOT__
├── traefik/
│   ├── compose.yaml     ← which containers, which settings
│   ├── .env             ← variables and secrets
│   └── data/            ← persistent data (certificates, databases …)
└── vaultwarden/
    ├── compose.yaml
    ├── .env
    └── data/
```

That has three advantages:

- **One backup target.** If you back up `/srv/homelab`, you have everything: configuration, secrets and data of all services.
- **Everything in one place.** If you want to know how a service is set up, you look in exactly one folder.
- **Easy to move.** Taking a service to another server means: stop the stack, copy the folder, start it there.

The file is called `compose.yaml`. That's Docker Compose's current default name. The old name `docker-compose.yml` still works too.

<Steps>

<Step title="Create the root folder">
`/srv` belongs to root. That's why you need `sudo` once to create the folder.

```bash
sudo mkdir -p __ROOT__
```
</Step>

<Step title="Hand the folder to your user">
So you can create and edit files without `sudo` afterwards, hand the folder over to your user. `chmod 750` makes sure other users on the server can't look inside. That's important, because passwords in `.env` files will live here later.

```bash
sudo chown "$USER":"$(id -gn)" __ROOT__
chmod 750 __ROOT__
ls -ld __ROOT__
```

The output should now show your user name and `drwxr-x---`.

<Callout title="Files that belong to root">
Some containers create files in `data/` as root or with a user ID of their own. That's normal. You can only read or delete such files with `sudo`. That's also why the backup will run with `sudo` later. If a container reports `Permission denied`, [Permission denied](/en/wiki/permission-denied/) helps.
</Callout>
</Step>

<Step title="One folder per service">
For every new service, create a subfolder named after the service. Lowercase, no spaces. The folder name is also the project name Docker Compose uses for containers and networks.

You do this each time you set up a service. For the first stack, it looks like this:

```bash
mkdir -p __ROOT__/whoami
```

Persistent data always goes into the service's `data/` subfolder. The `compose.yaml` then says, for example, `./data/db:/var/lib/postgresql/data`. The dot at the start means: relative to the folder the `compose.yaml` is in.

Do you already know which services you want to run? The [stack builder](/en/tools/stack-builder/) puts together the matching folders with `compose.yaml` and `.env` as a package.
</Step>

<Step title="Check “My setup”">
Open "My setup" at the top of the page and check under "Paths":

- **Folder for stacks:** `/srv/homelab` (or your own path)
- **Persistent data:** "Inside the stack folder"

From now on, all commands and Compose files on this site use your path.
</Step>

</Steps>

<Callout title="The proxy network comes later">
Many tutorials create a Docker network for the reverse proxy at this point. You only need it once you set up a reverse proxy. That's why it's part of the guide [Reverse proxy with Traefik](/en/setup/reverse-proxy-traefik/).
</Callout>

## Alternative: configuration and data separate

Some people split Compose files and data into two folders. That's worth it if you

- want to keep the Compose files as a Git repository without databases or uploads ending up in it,
- want to put the data on another, bigger disk,
- want to back up configuration and data at different intervals.

Under the same root folder, it looks like this:

```
/srv/homelab/
├── compose/             ← folder for stacks
│   ├── traefik/
│   │   ├── compose.yaml
│   │   └── .env
│   └── vaultwarden/
│       ├── compose.yaml
│       └── .env
└── data/                ← central data folder
    ├── traefik/
    └── vaultwarden/
```

You create it the same way as above, just with two subfolders:

```bash
sudo mkdir -p /srv/homelab/compose /srv/homelab/data
sudo chown -R "$USER":"$(id -gn)" /srv/homelab
chmod 750 /srv/homelab
```

Then set this in "My setup" under "Paths":

- **Folder for stacks:** `/srv/homelab/compose`
- **Persistent data:** "Central data folder"
- **Data folder:** `/srv/homelab/data`

The Compose files on this site then no longer point to `./data/…`, but to the matching subfolder in the data folder. The backup target stays `/srv/homelab`.

<Callout type="warning" title="The .env doesn't belong in a public repository">
Even if you manage the Compose folder with Git: the `.env` contains passwords and keys. Add it to the `.gitignore`. More in the guide [.env & secrets](/en/setup/env-secrets/).
</Callout>
