## Why an .env file?

A `compose.yaml` describes *how* a service runs. Passwords, tokens and values that differ from server to server don't
belong in it. Otherwise you can't share the file, put it in Git or simply copy it to another computer.

The solution: the `compose.yaml` only contains references like `${DB_PASSWORD}`. The real values are in a file called
`.env` in the same folder. Docker Compose reads it automatically at startup.

## Three ways, three purposes

The terms sound similar but do different things.

| Way              | Where                     | What happens                                                   |
| ---------------- | ------------------------- | -------------------------------------------------------------- |
| `.env`           | File in the stack folder  | Supplies values for `${…}` in the `compose.yaml` (interpolation) |
| `environment:`   | In the `compose.yaml`     | Sets environment variables **in the container**                |
| `env_file:`      | In the `compose.yaml`     | Loads all lines of a file into the container as environment variables |

The most important point: the `.env` does **not** end up in the container automatically. It only serves to fill in the
`compose.yaml`. Only through `environment:` (or `env_file:`) does a value arrive in the container.

That's why the templates on this site use this pattern:

```yaml
services:
  nextcloud:
    environment:
      - TZ=${TZ}
      - MYSQL_PASSWORD=${DB_PASSWORD}
```

```bash
# .env
TZ=__TZ__
DB_PASSWORD=ein-langes-zufaelliges-passwort
```

That way you see exactly in the `compose.yaml` which variables a container gets. `env_file:` is handy when a service
needs very many variables. But then it passes on everything in the file, including values the container doesn't need.
If you set the same variable in `environment:` and via `env_file:`, `environment:` wins.

## Interpolation and default values

Interpolation means Compose replaces `${VAR}` with the value from the `.env` (or from your shell) before it starts the
containers. There are a few useful variants:

| Notation           | Meaning                                                    |
| ------------------ | ---------------------------------------------------------- |
| `${VAR}`           | Value of `VAR`, empty if not set                           |
| `${VAR:-standard}` | `standard` if `VAR` is not set or empty                    |
| `${VAR-standard}`  | `standard` only if `VAR` isn't set at all                  |
| `${VAR:?Fehler}`   | Aborts with an error message if `VAR` is missing or empty  |

`${VAR:?…}` is worth it for required values like passwords. Then the stack doesn't start with an empty password but
tells you what's missing. All details are in the
[official docs on interpolation](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/).

If a variable is set both in your shell and in the `.env`, the shell wins. That sometimes surprises people who set
something with `export` for testing earlier.

## Quoting pitfalls

Most problems with `.env` files come from quotes and special characters.

- **The dollar sign.** Compose also replaces `$` in values in the `.env`. A password like `abc$def` then becomes `abc`.
  Put such values in single quotes, and they stay literal: `PASSWORD='abc$def'`. In the `compose.yaml` itself, you
  write a literal dollar sign as `$$`.
- **Quotes in `environment:`.** In the list form `- KEY="wert"`, the quotes are part of the value. So the container
  gets `"wert"` including the quotes. Simply write `- KEY=wert`.
- **Comments.** Lines starting with `#` are comments. A `#` in the middle of an unquoted value may count as a comment
  if there's a space before it. When in doubt, put the value in quotes.
- **Spaces around the `=`.** Write `KEY=wert` without spaces. That's unambiguous in all tools.

The easiest way around all this is passwords made of letters and digits, for example from `openssl rand -hex 32`.
They're still long enough.

## Checking with docker compose config

Before you guess, have Compose show you what it actually makes of it:

```bash
cd __ROOT__/nextcloud
docker compose config
```

The command prints the final configuration with all values filled in. If a variable is missing, you'll see a warning.
Careful: the output contains your passwords in plain text. Don't paste it into a forum without checking.

If you've taken a `compose.yaml` from a project's docs and don't understand every line, the
[Compose explainer](/en/tools/compose-explainer/) helps. It explains the file line by line and flags typical
problems.

## .env.example for Git

The `.env` contains secrets and never belongs in a public repository. Still, someone using your `compose.yaml` should
know which variables are needed. That's what `.env.example` is for: the same keys, but with placeholders instead of
real values.

```bash
# .env.example
TZ=Europe/Berlin
DB_PASSWORD=change-me
```

The `.env.example` goes into Git, the `.env` into the `.gitignore`. The service templates on this site are built the
same way. The [stack builder](/en/tools/stack-builder/) delivers a ready `.env` with randomly generated secrets for
each service. How to protect secrets beyond that is covered under [Managing secrets](/en/wiki/managing-secrets/).

<Callout type="warning" title="Set permissions">
  The `.env` should only be readable by you. `chmod 600 .env` makes sure of that. And remember: whoever finds the file
  in a backup has your passwords. So always encrypt backups.
</Callout>
