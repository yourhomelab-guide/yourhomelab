## Why a naming scheme?

Names appear in many places in a home lab: in folders, in `docker ps`, in logs, in monitoring, in the
Browser address bar. If the same service has a different name in every field, you'll be searching constantly. A consistent naming convention saves you
this search. And it makes commands predictable: You know the name of the container without having to look it up.

The rule on this page is simple: **Each service has a name, and that name applies everywhere.**

## Folder, Stack, and Container

A service's name is its ID, for example  `vaultwarden`or `nextcloud`. Lowercase letters, numbers, and
Hyphens, no spaces.

- **Folder:** `__ROOT__/vaultwarden`
- **Stack Name:** Docker Compose uses the folder name as the project name by default. So you don't need to do anything.
- **Container:** `container_name: vaultwarden`

Without it, Compose would`container_name` generate`vaultwarden-vaultwarden-1` names such as (project, service, number). The
It works, but it's long and hard to type. Just use a fixed name`docker logs vaultwarden`.

The [Stack Builder](/en/werkzeuge/stack-builder/) follows this pattern. The folders and `compose.yaml`files,
So the ones he generates are already appropriately named.

## Aid Containers

Many services consist of multiple containers, such as an app, a database, and a cache. The main container
is named after the folder; all others follow this pattern`<id>-<rolle>`:

```yaml
services:
  nextcloud:
    container_name: nextcloud
  db:
    container_name: nextcloud-db
  redis:
    container_name: nextcloud-redis
```

The keys are`services:` short (`db`, `redis`). The containers can be accessed using these names
within the stack, for example with `MYSQL_HOST=db`. Each one looks similar`compose.yaml`, and in `docker ps`
you can still tell right away which database belongs to which service.

Common roles are `db`, `redis`,  or`worker` `cron`. The important thing is that you always use the same ones.

<Callout type="warning" title="container_name must be unique">
  A server cannot have two containers with the same name. If you had one in each of two stacks,
  If there is a container named `db`, the second one will not start. The prefix with the ID prevents this.
</Callout>

## Subdomains

The subdomain is the name you type into the browser. It can be shorter or more descriptive than the ID, for
Example:

| Service      | Subdomain            |
| ----------- | -------------------- |
| vaultwarden | `vault.__DOMAIN__`   |
| Nextcloud   | `cloud.__DOMAIN__`   |
| forgejo     | `git.__DOMAIN__`     |
| pocket-id   | `id.__DOMAIN__`      |

The templates on this page include a suggestion. Consider whether you want to sort by function (`git`, `fotos`) or by
product (`forgejo`, `immich`). Function names have one advantage: If you change the product later,
The address remains the same. Learn more about domains under [DNS & Domains](/en/wiki/dns-domains/).

## Networks

- **Proxy network:** A shared network that hosts the reverse proxy and all web services. It is called
  `__NETWORK__` and is applied by hand just once:

  ```bash
  docker network create __NETWORK__
  ```

- **Stack Network:** Compose automatically assigns each stack its own network named `<projekt>_default`,
  For example`nextcloud_default`, databases are just sitting there, isolated from the rest.

You rarely need additional networks. If you do, give them a name that describes their purpose, such as `monitoring`.
For more information, see [Docker Networks](/en/wiki/docker-networks/).

## Host Names

Your devices need names, too. A hostname should be short and consist only of lowercase letters, numbers, and hyphens.
include them but don't reveal what's running on them. Popular schemes include `homelab`, `nas`, , or`pi` numbered sequences
`srv01`, `srv02`. Some people also use planets or characters from books. It's a matter of taste, as long as you
. The guide "[Static IP & Hostname](/en/setup/static-ip-hostname/)" explains how to set the hostname.
