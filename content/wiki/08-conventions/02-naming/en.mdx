## Why a naming scheme?

In a homelab, names show up in many places: in folders, in `docker ps`, in logs, in monitoring, in the browser's
address bar. If the same service is called something different everywhere, you're constantly searching. A fixed
scheme saves you that. And it makes commands predictable: you know what the container is called without looking.

This site's rule is simple: **a service has one name, and it applies everywhere.**

## Folder, stack and container

A service's name is its ID, for example `vaultwarden` or `nextcloud`. Lowercase letters, digits and hyphens, no
spaces.

- **Folder:** `__ROOT__/vaultwarden`
- **Stack name:** without further settings, Docker Compose uses the folder name as the project name. So you don't
  have to do anything.
- **Container:** `container_name: vaultwarden`

Without `container_name`, Compose would generate names like `vaultwarden-vaultwarden-1` (project, service, number).
That works, but it's long and hard to type. With a fixed name, `docker logs vaultwarden` is enough.

The [stack builder](/en/tools/stack-builder/) sticks to this scheme. So the folders and `compose.yaml` files it
generates are already named correctly.

## Helper containers

Many services consist of several containers, for example an app, a database and a cache. The main container is named
like the folder, all others follow the scheme `<id>-<role>`:

```yaml
services:
  nextcloud:
    container_name: nextcloud
  db:
    container_name: nextcloud-db
  redis:
    container_name: nextcloud-redis
```

The keys under `services:` stay short (`db`, `redis`). Under these names, the containers reach each other within the
stack, for example with `MYSQL_HOST=db`. That way every `compose.yaml` looks similar, and in `docker ps` you still see
at once which database belongs to which service.

Common roles are `db`, `redis`, `worker` or `cron`. All that matters is that you always use the same ones.

<Callout type="warning" title="container_name must be unique">
  There can't be two containers with the same name on one server. If you had a container called `db` in each of two
  stacks, the second wouldn't start. The prefix with the ID prevents that.
</Callout>

## Subdomains

The subdomain is the name you type in the browser. Here it may be shorter or more descriptive than the ID, for
example:

| Service     | Subdomain            |
| ----------- | -------------------- |
| vaultwarden | `vault.__DOMAIN__`   |
| nextcloud   | `cloud.__DOMAIN__`   |
| forgejo     | `git.__DOMAIN__`     |
| pocket-id   | `id.__DOMAIN__`      |

The templates on this site come with a suggestion. Think about whether you want to name by function (`git`,
`photos`) or by product (`forgejo`, `immich`). Function names have one advantage: if you switch products later, the
address stays the same. More on domains under [DNS & domains](/en/wiki/dns-domains/).

## Networks

- **Proxy network:** a shared network the reverse proxy and all web services are on. Here it's called `__NETWORK__`
  and is created once by hand:

  ```bash
  docker network create __NETWORK__
  ```

- **Stack network:** Compose automatically gives every stack its own network called `<project>_default`, for example
  `nextcloud_default`. Databases are only on that one and are therefore separated from the rest.

You'll rarely need more networks. If you do, give them a name that describes the purpose, such as `monitoring`. More
under [Docker networks](/en/wiki/docker-networks/).

## Hostnames

Your devices need names too. A hostname should be short, contain only lowercase letters, digits and hyphens, and not
give away what runs on it. Popular schemes are `homelab`, `nas`, `pi` or numbered ones like `srv01`, `srv02`. Some
people use planets or characters from books. That's a matter of taste, as long as you stick with it. How to set the
hostname is shown in the guide [Static IP & hostname](/en/setup/static-ip-hostname/).

## In short

| What                 | Scheme                    | Example                |
| -------------------- | ------------------------- | ---------------------- |
| Folder               | `__ROOT__/<id>`           | `__ROOT__/nextcloud`   |
| Stack (project)      | = folder name             | `nextcloud`            |
| Main container       | `<id>`                    | `nextcloud`            |
| Helper container     | `<id>-<rolle>`            | `nextcloud-db`         |
| Subdomain            | short, by function        | `cloud.__DOMAIN__`     |
| Proxy network        | once, shared              | `__NETWORK__`          |
| Hostname             | short, lowercase          | `homelab`              |
