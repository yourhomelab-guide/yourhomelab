## Why document?

While you're setting things up, everything is clear. A few months later, an update breaks something, or the disk
fails. Then you stand in front of your own setup as if it were a stranger's. Which port was it? Didn't the app need
one more step after the restore?

Good homelab documentation is short. It should help you in exactly these moments, not explain every setting. What's
already in the `compose.yaml` doesn't need writing down again.

## Where the notes belong

There are two common ways. Both are fine.

<Cards>
  <Card title="README per stack">
    A short `README.md` in each service's folder. The note sits exactly where you need it and moves along with the
    service when you migrate or back it up.
  </Card>
  <Card title="Central notes">
    One file, a wiki or a notes app for the whole homelab. Good for an overview of all devices and services. Careful:
    if it runs on the homelab itself, it may not be reachable in an emergency.
  </Card>
</Cards>

Many combine both: a short `README.md` per stack, plus a central overview with a network plan and a device list. What
matters is that the restore instructions are readable even when the server isn't running. Keep a copy outside the
homelab, for example in your password manager or printed out.

## What to write down?

Per service, these points are usually enough:

- **Purpose and address:** what is the service for, and which subdomain does it run on?
- **Ports:** which ports are open to the outside, and why? For example SSH for Forgejo on `2222`.
- **Dependencies:** does the service need other services, like Pocket ID for login or an SMTP server for mail?
- **Special cases:** everything you did by hand that isn't in the `compose.yaml`. Like a command after installation or
  a setting in the web interface.
- **Restore steps:** how do you get the service back from the backup? Does a database have to be restored from a dump?

A `README.md` for Nextcloud could look like this:

```markdown
# Nextcloud

Dateien und Kalender, erreichbar unter cloud.__DOMAIN__

- Abhängigkeiten: Traefik, Pocket ID (Login per OIDC)
- Datenbank: MariaDB (nextcloud-db), Dump liegt vor dem Backup in data/db-dump.sql
- Besonderheit: Hintergrundjobs laufen im Container nextcloud-cron, in den Einstellungen auf „Cron“ gestellt

## Restore
1. Ordner aus dem Backup zurückspielen
2. docker compose up -d db
3. Dump einspielen, dann docker compose up -d
```

Write your own in whatever language you like. It rarely takes more than that. Write the note right after you've set
something up. Later you'll lack the time or the memory.

The [docs export](/en/tools/docs-export/) gives you a starting point: it turns your setup and services into a Markdown
file with ports, paths and restore steps. You then add your special cases.

## The network plan

For the whole homelab, a small overview pays off: which devices are there, which IP do they have, what runs where? A
simple table is enough:

| Device    | IP             | Role                           |
| --------- | -------------- | ------------------------------ |
| Router    | `192.168.1.1`  | DHCP, port forwarding 80/443   |
| homelab   | `192.168.1.10` | Docker host, all stacks        |
| nas       | `192.168.1.20` | Backup target                  |

Add the port forwarding on the router, VPN access and where your domain is registered. These are the things you
forget fastest, because you only set them up once.

## Documentation in Git

If your Compose files and READMEs live in a Git repository, you automatically get a history: every change is recorded
with a date and a short description. Later you'll see when you changed an image tag and why. The `.env` stays out of
it. The guide [Git deployments with Forgejo](/en/setup/git-deployments-forgejo/) shows how this works with your own Git
server. For a Git-friendly folder structure, see [Directory structure](/en/wiki/directory-structure/).
