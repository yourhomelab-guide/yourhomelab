## Why the structure matters

At the start, it doesn't matter where your first `compose.yaml` lives. After ten services, it does. Then you want to
know: what has to go into the backup? Where is Vaultwarden's configuration? Which folder belongs to which container?

A fixed structure answers these questions before they come up. And it makes your backup simple: at best, you back up
**a single folder** and have everything.

## The common variants

On the web, you'll mainly find five patterns. They all work; they just set different priorities.

**(a) `/opt/stacks` or `/opt/docker`.** Very widespread, partly because some tools (such as Dockge) use `/opt/stacks`
as the default. One folder per service, usually with the data inside.

**(b) `~/docker` in the home directory.** Convenient: you don't need `sudo` to create it, and everything belongs to
your user.

**(c) Named volumes.** You only write the `compose.yaml`; Docker manages the data itself under
`/var/lib/docker/volumes/`. More under [Volumes & bind mounts](/en/wiki/volumes-bind-mounts/).

**(d) Separate: `compose/` and `data/`.** Configuration and data live in two parallel trees.

**(e) Everything per service in one folder.** `compose.yaml`, `.env` and `data/` live together. That's really a
question of internal order and can be combined with (a) or (b).

```
(c) Named Volumes                      (d) Getrennt                     (e) Pro Dienst
/opt/stacks/                           /srv/homelab/                    /srv/homelab/
└── vaultwarden/                       ├── compose/                     └── vaultwarden/
    └── compose.yaml                   │   └── vaultwarden/                 ├── compose.yaml
/var/lib/docker/volumes/               │       ├── compose.yaml             ├── .env
└── vaultwarden_data/                  │       └── .env                     └── data/
    └── _data/                         └── data/
                                           └── vaultwarden/
```

In the diagram, "Getrennt" means separate and "Pro Dienst" means per service.

## Compared

|                    | (a) `/opt/…`            | (b) `~/docker`              | (c) Named volumes              | (d) compose + data         | (e) per service       |
| ------------------ | ----------------------- | --------------------------- | ------------------------------ | -------------------------- | --------------------- |
| **Backup**         | One folder              | One folder                  | Two places, volumes only as root | Two folders (or their parent) | One folder       |
| **Permissions**    | Needs `sudo` once       | Simple, it's yours          | Everything belongs to root     | Depends on the location    | Depends on the location |
| **Overview**       | Good                    | Good                        | Data hard to find              | Good, but two places       | Very good             |
| **Git-friendly**   | Only with `.gitignore`  | Only with `.gitignore`      | Yes, Compose files only        | Very good                  | Only with `.gitignore` |
| **FHS**            | `/opt` is for software  | Home is for user data       | Docker-internal                | Depends on the location    | Depends on the location |

A few points on this:

- **FHS** is the [Filesystem Hierarchy Standard](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/index.html). It
  describes what the folders on Linux are meant for. `/opt` is for add-on software packages, `/srv` for "data served
  by this system". For a homelab, `/srv` fits best. But `/opt` isn't really bad; it's just a question of convention.
- **Home directory:** handy, but your services then depend on a user account. If you change users or a second admin
  has access, it gets confusing.
- **Named volumes** aren't wrong. Docker takes care of permissions, and for some databases that's convenient. But the
  data is hidden, names like `vaultwarden_data` are made up from the project name and the volume name, and for a
  backup you need root access to `/var/lib/docker`. For beginners, a visible folder is simpler.

## This site's recommendation

To start, we recommend **a single root folder** with **one subfolder per service**:

```
/srv/homelab/
├── traefik/
│   ├── compose.yaml
│   ├── .env
│   └── data/
└── vaultwarden/
    ├── compose.yaml
    ├── .env
    └── data/
```

That's variant (e) under `/srv`. The advantages:

- **One folder for the backup.** If you back up `/srv/homelab`, you have the configuration, secrets and data of all
  services.
- **Everything together.** If you want to move or delete a service, you take exactly one folder. That also applies to
  [moving to new hardware](/en/setup/moving-hardware/).
- **Short paths in the `compose.yaml`.** You mount persistent data as a bind mount to `./data/…`. The path is relative
  to the stack folder, so the file works anywhere.

Of course you can replace the name `homelab` with your own, such as `/srv/docker` or `/srv/home`. Enter the folder
under "My setup", and all commands and templates on this site adapt. There it's called `__ROOT__`; the default is
`/srv/homelab`. How to create the structure and set permissions is shown in the guide
[Creating the directory structure](/en/setup/creating-the-directory-structure/). If you want to set up several
services right away, the [stack builder](/en/tools/stack-builder/) generates the folders with `compose.yaml` and
`.env` in exactly this structure.

## Alternative for advanced users

If you want to manage your Compose files with Git, for example with
[Forgejo and automatic deployments](/en/setup/git-deployments-forgejo/), separating configuration and data is
more practical:

```
/srv/homelab/
├── compose/
│   ├── traefik/
│   │   ├── compose.yaml
│   │   └── .env
│   └── vaultwarden/
│       ├── compose.yaml
│       └── .env
└── data/
    ├── traefik/
    └── vaultwarden/
```

The `compose/` folder is then a clean Git repository without data. And you can put `data/` on a disk of its own or
back it up differently from the configuration. The backup still stays simple: you keep backing up `/srv/homelab`.

This is how you set it up under "My setup":

- **Folder for stacks:** `/srv/homelab/compose`
- **Persistent data:** "Central data folder"
- **Data folder:** `/srv/homelab/data`

The templates then write the full path into the `compose.yaml` instead of `./data/…`, for example
`/srv/homelab/data/vaultwarden/…`.

## Good to know

- **`compose.yaml` instead of `docker-compose.yml`.** `compose.yaml` is the current default name. Docker Compose still
  finds the old name, so you don't have to rename anything. But new files here are always called `compose.yaml`.
- **Dump databases before the backup.** If you copy the files of a running database, the backup may be inconsistent.
  Create a dump first or briefly stop the stack. More under [Backup strategies](/en/wiki/backup-strategies/).
- **The `.env` contains secrets.** Passwords and tokens are in it in plain text. Encrypt your backups (borgmatic does
  this automatically) and never put the `.env` into a public Git repository. More under
  [.env files](/en/wiki/env-files/).
