## Why Docker at all?

Imagine you want to run three services on one server. The first needs PHP 8.2, the second PHP 8.3, the third a specific version of Node.js. If you install everything directly on the system, the dependencies quickly get in each other's way. Updates become a risk, and after a year nobody knows which file belongs to which program.

Docker solves this by running each service in its own isolated **container**. The container brings its own libraries and runtime. On the server itself, you only need Docker. Removing a service means deleting the container. Nothing stays behind on the system, except the data you deliberately want to keep.

That's why almost all self-hosting projects ship their software as a Docker image. Installation often shrinks to a short configuration file and one command.

## The three basic terms

<Cards>
  <Card title="Image">
    The template. An image contains the program and everything it needs as an unchangeable package. It's built once and then only used.
  </Card>
  <Card title="Container">
    A running instance of an image. You can start as many containers from one image as you like. Each has its own process space and its own network.
  </Card>
  <Card title="Registry">
    The place where images are stored so others can download them. The best known is Docker Hub; there's also the GitHub Container Registry, for example.
  </Card>
</Cards>

## An analogy

An image is like a recipe with pre-packed ingredients in a box. The container is the dish you cook from it. You can cook from the same box several times, and every dish tastes the same, no matter which kitchen you're in. The registry is the store where the boxes sit on the shelf.

The analogy has a limit: when you delete a container, everything it wrote into itself at runtime is gone. So data that should stay is stored outside the container on the server. How that works is explained in [Volumes & bind mounts](/en/wiki/volumes-bind-mounts/).

## How a container comes about

The process is always the same:

1. Docker downloads the image from a registry (**pull**).
2. Docker starts a container from it (**run**).
3. The container runs until you stop it or it crashes. With a restart policy, Docker starts it again automatically. If it keeps restarting over and over, [Container in a restart loop](/en/wiki/restart-loop/) helps.

Once Docker is installed, you can try it with a single command:

```bash
docker run --rm hello-world
```

Docker downloads the small `hello-world` image and starts it; the container prints a greeting and exits. `--rm` removes the container again right afterwards.

In everyday use, though, you don't start containers with long `docker run` commands. You describe them in a `compose.yaml` file and start them with `docker compose up -d`. That's more readable, can be backed up and repeated at any time. More in [Docker Compose](/en/wiki/docker-compose/).

## Containers aren't virtual machines

A virtual machine (VM) simulates a complete computer with its own operating system kernel. A container, on the other hand, shares the kernel with the server and is just an isolated process. That makes containers small and fast: they start in seconds and need hardly any extra memory.

The price is weaker separation than with a VM. For most homelab services, it's entirely sufficient. When a VM is still worth it is covered in [VMs or containers?](/en/wiki/vms-or-containers/).

## Docker and Podman

Docker isn't the only container software. The best-known alternative is **Podman**, developed by Red Hat. The differences in brief:

|                   | Docker                                  | Podman                                        |
| ----------------- | --------------------------------------- | --------------------------------------------- |
| **Architecture**  | A background service (daemon) manages all containers | No central daemon; each container is a normal process |
| **Privileges**    | The daemon runs as root                 | Without root privileges by default (rootless) |
| **Commands**      | `docker …`                              | Largely the same, `podman …`                  |
| **Compose**       | `docker compose` is built in            | Possible, but with more quirks                |
| **Adoption**      | Standard in almost all guides           | Mainly on Fedora, RHEL and similar            |

Podman is technically interesting and built with security in mind. For getting started, this site still recommends Docker: almost every guide and every Compose file you find on the web assumes Docker. If something doesn't work, you'll find help faster with Docker.

<Callout title="Anyone in the docker group has root privileges">
The Docker daemon runs as root. Whoever may run Docker commands can do practically anything on the server with them. So only add users to the `docker` group whom you'd also give `sudo`.
</Callout>
