## Anatomy of an image name

Every `compose.yaml` contains a line like this:

```yaml
image: ghcr.io/example/app:1.4.2
```

The name has three parts:

| Part | Example | Meaning |
| --- | --- | --- |
| Registry | `ghcr.io` | The server the image is downloaded from |
| Repository | `example/app` | Who publishes the image and what it's called |
| Tag | `1.4.2` | Which version |

If the registry is missing, Docker automatically uses **Docker Hub** (`docker.io`). If the tag is missing, Docker uses `latest`. So `image: nginx` internally becomes `docker.io/library/nginx:latest`. The `library` namespace is reserved for Docker Hub's official images.

## Registries

A registry is a server that stores and delivers images. The most important ones for self-hosting:

- **Docker Hub** (`docker.io`): the default registry with the most images. Anonymous downloads have a limit per time period. In a homelab you rarely notice it, but it can kick in with many updates at once.
- **GitHub Container Registry** (`ghcr.io`): many open source projects publish here, right next to their source code.
- **LinuxServer.io** (`lscr.io`): a community that packages many popular programs in consistently built images.
- **Quay** (`quay.io`): mainly projects from the Red Hat ecosystem.

A project's documentation tells you which registry it uses. Use the project's official image whenever possible. Images from unknown people can be outdated or, in the worst case, contain malicious code. The [Compose explainer](/en/tools/compose-explainer/) shows you which image and tag someone else's `compose.yaml` uses.

## The problem with latest

`latest` sounds like "always the newest version". In fact, it's just a name the publisher assigns, usually to the last stable release. That has two pitfalls:

1. **You don't know which version is running.** `latest` today and `latest` in three months are different programs. If the file only says `latest`, you can't trace when what changed.
2. **Big jumps happen unnoticed.** With a `docker compose pull`, you also get versions that restructure data or change settings. That goes well for some services, often not for databases. [Database won't start after an update](/en/wiki/database-version/) describes what happens then.

By the way, `latest` doesn't update by itself. Docker only fetches a new version when you run `pull` or a tool does it for you.

## Version tags

Most projects assign tags following **semantic versioning** (semver for short): `MAJOR.MINOR.PATCH`, for example `2.1.3`.

- **PATCH** (2.1.**3**): bug fixes. Should always be unproblematic.
- **MINOR** (2.**1**.0): new features that don't break existing ones.
- **MAJOR** (**2**.0.0): bigger changes. Here a look at the release notes is worth it.

Often the same image is available under several tags. The shorter the tag, the more updates it picks up:

| Tag | Gets on the next pull |
| --- | --- |
| `2.1.3` | Nothing; this version stays fixed |
| `2.1` | New patch versions (2.1.4, 2.1.5 …) |
| `2` | New minor and patch versions (2.2, 2.3 …) |
| `latest` | Everything, including version 3 |

A good middle ground for beginners is the major tag, such as `louislam/uptime-kuma:2` or `mariadb:11`. You get bug fixes, but no jumps that require manual work. Fully fixed versions like `2.1.3` are the most predictable, but you have to enter every update yourself.

Not every project follows semver, and some only offer `latest`. How the tags are meant is stated on the image's page in the registry or in the project documentation. Some tags also carry suffixes like `-alpine` for an especially small variant or `-apache` for a particular setup.

## Digests: the exact version

A tag is just a label the publisher can move to another image at any time. The **digest**, on the other hand, is unique: a checksum over the image's content, starting with `sha256:`. You can append it to the name:

```yaml
image: nginx:1.31@sha256:0123abc…
```

Docker then downloads exactly this image, even if the tag now points elsewhere. The `…` here stands for the rest of the long checksum. To see the digests of the images on your server:

```bash
docker image ls --digests
```

Maintaining digests by hand is tedious. They make sense when a tool like Renovate updates them automatically.

## Keeping updates under control

Fixed tags have a catch: someone has to bump them. **Dockhand** helps with this most easily: it installs updates within the tag automatically if you like and shows you newer tags with their release notes. You then change the tag yourself. [Portainer or Dockhand](/en/setup/portainer-dockhand/) shows how.

If you keep your Compose files in Git, **Renovate** can optionally bump the tags. The tool finds newer tags and suggests the change as a pull request. You read the release notes, click "Merge", and the update is documented. [Updates with Renovate](/en/setup/updates-renovate/) shows how to set it up. General update strategies are covered in [Updates](/en/wiki/updates/).

Old images stay on the disk after an update. You can clean up with:

```bash
docker image prune
```

The command deletes images that no longer have a name and aren't used by any container. With `-a`, it removes all images that no container is currently using. If the disk is already full, [Disk full](/en/wiki/disk-full/) helps.
