## Why Compose instead of docker run?

You can start a container with `docker run` and a long list of options. That works, but has downsides: you have to keep the command somewhere, typos only show up at startup, and for an update you have to repeat it exactly.

Docker Compose turns this around. You write into a **`compose.yaml`** file what your containers should look like. Compose then makes sure the actual state matches. The file is readable and can be backed up and versioned. If the server fails, you restore the folder and start again with one command.

A `compose.yaml` with all its containers is called a **stack**. On this site, each stack gets its own folder under `__ROOT__`; see [Directory structure](/en/wiki/directory-structure/).

## An annotated example

This is what a stack for [Uptime Kuma](/en/services/uptime-kuma/) looks like, a tool that monitors your services. The file lives at `__ROOT__/uptime-kuma/compose.yaml`.

```yaml
services:                             # all containers of this stack
  uptime-kuma:                        # service name, also its DNS name inside the stack
    image: louislam/uptime-kuma:2     # image and tag to run
    container_name: uptime-kuma       # fixed name instead of an auto-generated one
    restart: unless-stopped           # start again after crash or reboot, unless you stopped it
    environment:                      # settings passed to the program
      - TZ=${TZ}
    volumes:                          # persistent data: host path : container path
      - ./data/data:/app/data
    ports:                            # host port : container port
      - "3001:3001"
    networks:
      - __NETWORK__                   # join the shared proxy network

networks:
  __NETWORK__:
    external: true                    # created once with "docker network create", not by this stack
```

The most important keys at a glance:

| Key | Meaning |
| --- | --- |
| `services` | List of containers. The name (here `uptime-kuma`) is up to you. |
| `image` | Which image runs in which version. Details in [Images & tags](/en/wiki/images-tags/). |
| `container_name` | A fixed name. Without it, Compose builds a name from folder and service, such as `uptime-kuma-uptime-kuma-1`. |
| `restart` | Restart rule. `unless-stopped` is almost always right for homelab services. |
| `environment` | Environment variables, which many programs are configured with. Secrets belong in the [.env file](/en/wiki/env-files/). |
| `volumes` | Connects folders on the server with folders in the container. See [Volumes & bind mounts](/en/wiki/volumes-bind-mounts/). |
| `ports` | Makes a container port reachable on the server. The server is on the left, the container on the right. |
| `networks` | Which Docker networks the container sits in. See [Docker networks](/en/wiki/docker-networks/). |

<Callout title="ports or reverse proxy?">
The example shows `ports` and `networks` together so you know both keys. In practice, you usually only need one of them: with a reverse proxy like Traefik, the service only sits in the `__NETWORK__` network and publishes no port. Without a proxy, you access it at `http://__SERVER_IP__:3001`. The templates under [Services](/en/services/) adjust this to your setup automatically.
</Callout>

Relative paths like `./data` always refer to the folder the `compose.yaml` is in. That's why all of a service's data ends up next to its configuration.

Compose reads variables like `${TZ}` from a `.env` file in the same folder. That keeps the `compose.yaml` free of passwords, and you can share it.

If you have a `compose.yaml` from a project's docs in front of you, the [Compose explainer](/en/tools/compose-explainer/) explains every line and shows what you need to adjust for your setup.

## The most important commands

You run all commands in the stack's folder:

```bash
cd __ROOT__/uptime-kuma
```

| Command | What it does |
| --- | --- |
| `docker compose up -d` | Creates the containers and starts them in the background. Simply run it again after changing the file. |
| `docker compose ps` | Shows the stack's containers and their status. |
| `docker compose logs -f` | Shows the logs live. Stop with Ctrl+C. |
| `docker compose pull` | Downloads newer versions of the images. Then run `up -d` to use them. |
| `docker compose restart` | Restarts the containers without recreating them. |
| `docker compose down` | Stops and removes the containers and the stack network. Your data in `./data` is kept. |
| `docker compose exec uptime-kuma sh` | Opens a shell in the running container, if the image includes one. |
| `docker compose config` | Checks the file and shows it with variables filled in. Good for troubleshooting. |

An update of a service then looks like this:

```bash
docker compose pull
docker compose up -d
```

Compose only recreates the containers whose image or configuration has changed.

If a stack doesn't start as expected, [Troubleshooting: first steps](/en/wiki/first-steps/) shows how to track down the cause with `ps`, `logs` and `config`.

## docker compose or docker-compose?

You'll find both spellings in tutorials. The difference:

- **`docker-compose`** with a hyphen is the old standalone version 1, written in Python. It hasn't been developed further since 2023.
- **`docker compose`** with a space is the current version 2. It's a plugin from Docker itself and is installed with the `docker-compose-plugin` package.

Always use `docker compose`. Old tutorials usually still work if you replace the hyphen with a space. The developers also simplified the file name: `compose.yaml` is the current standard, and `docker-compose.yml` is still recognized.

<Callout title="You no longer need the version: line">
Older Compose files start with `version: "3.8"` or similar. The current version of Compose ignores this line and only prints a warning. You can simply delete it.
</Callout>
