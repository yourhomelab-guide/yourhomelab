## Why separate networks?

Every container has its own network interface with its own IP address. These addresses live in virtual networks that Docker creates on the server. They aren't directly reachable from outside.

That's intended. A database should only talk to its app, not to the internet and not to other services. Docker networks separate your stacks from each other, and you decide specifically where a connection is needed.

## Every stack has its own network

When you start a stack with `docker compose up -d`, Compose automatically creates a **bridge network** for it. It's named after the folder with the suffix `_default`, for example `nextcloud_default`. All containers of this stack sit in it; containers of other stacks don't.

A bridge network is a virtual switch on the server. The containers in it can reach each other. Outward, they go through the server to the internet, for updates for example.

## Containers find each other by name

Container IP addresses change with every restart. That's why Docker comes with its own DNS service: in networks you create yourself, including Compose's stack network, you reach a container by its **service name** from the `compose.yaml`. The `container_name` works too.

Example from the [Nextcloud](/en/services/nextcloud/) template:

```yaml
services:
  nextcloud:
    image: nextcloud:35-apache
    environment:
      - MYSQL_HOST=db          # "db" is resolved by Docker's internal DNS
  db:
    image: mariadb:lts
```

Nextcloud connects to the host `db`, and Docker resolves the name to the database container's current IP. The database publishes no port. It's only reachable within the stack.

<Callout title="The bridge network is an exception">
Containers you start without Compose using `docker run` end up in the default `bridge` network. Name resolution doesn't work there. One more reason to start everything with Compose.
</Callout>

## The shared proxy network

A reverse proxy like Traefik has to reach all services it passes on to the outside. But the services live in separate stack networks. The solution is an additional network that you create once by hand:

```bash
docker network create __NETWORK__
```

Every stack that should be reachable through the proxy joins this network. Because Compose shouldn't create it itself, you mark it as `external`:

```yaml
services:
  nextcloud:
    networks:
      - default          # stack network, reaches the database
      - __NETWORK__      # proxy network, reachable by Traefik
  db:
    # no networks key: only in the stack network

networks:
  __NETWORK__:
    external: true
```

That way only the web app sits in the proxy network. The database stays in the stack network and is invisible to Traefik and other stacks. If you specify `networks` for a service, you have to list `default` too if it should keep talking to the stack's other containers. If a service is missing from the proxy network, the proxy usually answers with "Bad Gateway"; see [Bad Gateway and 404 from the proxy](/en/wiki/bad-gateway/).

The templates under [Services](/en/services/) add the proxy network automatically if you chose a reverse proxy in "My setup". [Reverse proxy explained](/en/wiki/reverse-proxy-explained/) covers how a reverse proxy works in general.

## Publish ports or not?

With `ports`, you make a container port reachable on the server:

```yaml
ports:
  - "8080:80"              # all interfaces: server port 8080 to container port 80
  - "127.0.0.1:8081:80"    # only reachable from the server itself
```

Without an address, the port listens on all of the server's network interfaces. It's then reachable from your home network, and on a VPS even from the whole internet. Each server port can only be used once. If Docker reports on startup that it's already taken, [Port already in use](/en/wiki/port-in-use/) helps.

The rule of thumb for this homelab:

- **With a reverse proxy:** only the proxy publishes ports, namely 80 and 443. All other services sit in the `__NETWORK__` network and have no `ports` entry.
- **Without a reverse proxy:** the service publishes its web port, and you reach it at `http://__SERVER_IP__:8080` on your home network.
- **Only for you on the server:** bind to `127.0.0.1`. Then you only get there through an SSH tunnel.
- **Other protocols** like SSH for Forgejo (`"2222:22"`) get published, because the HTTP proxy doesn't forward them.

<Callout type="warning" title="Docker bypasses UFW">
Docker enters published ports directly into the kernel's firewall rules (iptables), at a point that takes effect before UFW's rules. So a port from `ports` is reachable even if UFW doesn't allow it. Don't rely on UFW to protect container ports. Only publish what really has to be reachable from outside, and bind everything else to `127.0.0.1` or leave out the `ports` entry entirely. The background is in the [Docker docs on packet filtering](https://docs.docker.com/engine/network/packet-filtering-firewalls/).
</Callout>

## The host network

With `network_mode: host`, a container does without networks of its own and uses the server's network interfaces directly. Every port the program listens on is immediately open on the server. A `ports` entry is then ignored, and there's no Docker DNS by container name either.

That's rarely needed. Typical cases are programs that should find devices on the home network automatically, like [Home Assistant](/en/setup/home-assistant/) or a media server with DLNA. Their discovery works with broadcasts, which don't get through a bridge network. For everything else, the bridge network is the better choice, because it keeps services apart.

## Useful commands

```bash
docker network ls                    # list all networks
docker network inspect __NETWORK__   # show which containers are attached
```
