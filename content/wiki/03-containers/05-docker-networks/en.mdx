## Why have your own networks?

Each container has its own network interface with its own IP address. These addresses are located in virtual networks that Docker creates on the server. They are not directly accessible from the outside.

That's by design. A database should only communicate with its app—not with the internet or other services. Docker networks isolate your stacks from one another, and you decide exactly where a connection is needed.

## Each stack has its own network

When you start a stack with `docker compose up -d`, Compose automatically creates a **bridge network** for it. It is named after the folder with the suffix `_default`, for example `nextcloud_default`. All containers in this stack are connected to it; containers from other stacks are not.

A bridge network is a virtual switch on the server. The containers within it can communicate with one another. They connect to the outside world—such as the Internet—via the server, for example, to download updates.

## Containers can be found by their names

Container IP addresses change with every restart. That's why Docker comes with its own DNS service: In custom networks—including the Compose stack network—you can access a container using its **service name** from the `compose.yaml`. The  also works`container_name`.

Example from the [Nextcloud](/en/services/nextcloud/) template:

```yaml
services:
  nextcloud:
    image: nextcloud:31-apache
    environment:
      - MYSQL_HOST=db          # "db" is resolved by Docker's internal DNS
  db:
    image: mariadb:11
```

Nextcloud connects to the host`db`, and Docker resolves the name to the current IP address of the database container. The database does not expose a port; it is accessible only within the stack.

<Callout title="The bridge network is an exception">
Containers that you start`docker run` without Compose end up in the default network`bridge`. Name resolution doesn't work there. That's one more reason to start everything with Compose.
</Callout>

## The Shared Proxy Network

A reverse proxy like Traefik must be able to reach all the services it forwards to the outside world. However, those services are located in separate stack networks. The solution is an additional network that you set up manually once:

```bash
docker network create __NETWORK__
```

Every stack that is supposed to be accessible via the proxy joins this network. Since Compose isn't supposed to create it itself, you mark it as`external`:

```yaml
services:
  nextcloud:
    networks:
      - default          # stack network, reaches the database
      - __NETWORK__      # proxy network, reachable by Traefik
  db:
    # no networks key: only in the stack network

networks:
  __NETWORK__:
    external: true
```

This way, only the web app resides in the proxy network. The database remains in the stack network and is invisible to Traefik and other stacks. If you `networks`specify a service, you must include `default`it if it is to continue communicating with the other containers in the stack. If a service is missing from the proxy network, the proxy usually responds with “Bad Gateway”; see [Bad Gateway and 404 from the proxy](/en/wiki/bad-gateway/).

The templates under "[Services](/en/services/)" automatically add the proxy network if you've selected a reverse proxy in "My Setup." The [article "Reverse Proxy Explained](/en/wiki/reverse-proxy-explained/)" describes how a reverse proxy generally works.

## To publish ports or not?

Use  to make`ports` a container port accessible on the server:

```yaml
ports:
  - "8080:80"              # all interfaces: server port 8080 to container port 80
  - "127.0.0.1:8081:80"    # only reachable from the server itself
```

If no address is specified, the port listens on all of the server's network interfaces. It is then accessible from your home network, and in the case of a VPS, even from anywhere on the Internet. Each server port can only be assigned once. If Docker reports at startup that the port is already in use, see ["Port in Use](/en/wiki/port-in-use/)."

The rule of thumb for this home lab:

- **With a reverse proxy:** Only the proxy exposes ports, specifically 80 and 443. All other services remain on the network `__NETWORK__`and have no `ports`entry.
- **Without a reverse proxy:** The service exposes its web port, and you can access it via  `http://__SERVER_IP__:8080`on your home network.
- **Just for you on the server:** Listen on `127.0.0.1`. Then you'll only be able to access it via an SSH tunnel.
- You publish **other protocols**, such as SSH for Forgejo (`"2222:22"`), because the HTTP proxy does not forward them.

<Callout type="warning" title="Docker bypasses UFW">
Docker adds published ports directly to the kernel's firewall rules (iptables) at a point that takes precedence over UFW's rules. A port published by Docker is`ports` therefore accessible even if UFW does not allow it. So don’t rely on UFW to protect container ports. Only expose what really needs to go out, and bind everything else to  `127.0.0.1`or omit the `ports`entry entirely. For more background, see the [Docker documentation on packet filters](https://docs.docker.com/engine/network/packet-filtering-firewalls/).
</Callout>

## The host network

With , a container does`network_mode: host` not use its own networks and instead uses the server's network interfaces directly. Every port on which the program listens is immediately open on the server. A `ports`-entry is then ignored, and there is no Docker DNS based on container names.

You rarely need this. Typical examples include programs designed to automatically discover devices on a home network, such as [Home Assistant](/en/setup/home-assistant/) or a media server with DLNA. Their discovery process uses broadcasts that do not pass through a bridge network. For everything else, the bridge network is the better choice because it keeps the services separate from one another.

## Useful Commands

```bash
docker network ls                    # list all networks
docker network inspect __NETWORK__   # show which containers are attached
```
