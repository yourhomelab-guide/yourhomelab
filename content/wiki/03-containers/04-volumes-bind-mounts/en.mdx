## Why data doesn't belong in the container

A container is built to be deleted and recreated at any time. That's exactly what happens with every update: Compose throws away the old container and starts a new one from the new image. Everything the program wrote into the container itself is then lost.

That's why you mount the folders where a program stores its data from outside. The program seems to write into its own folder, but the files actually land on the server. Docker has two ways of doing this.

## Named volumes and bind mounts

<Cards>
  <Card title="Named volume">
    Docker manages the storage location itself. You only give it a name; the files live somewhere under /var/lib/docker/volumes.
  </Card>
  <Card title="Bind mount">
    You choose the folder on the server yourself, for example ./data/db next to the compose.yaml. You see the files directly.
  </Card>
</Cards>

In the `compose.yaml`, both look almost the same:

```yaml
services:
  app:
    image: example/app:1
    volumes:
      - app-data:/var/lib/app       # named volume: name on the left
      - ./data/config:/config       # bind mount: path on the left

volumes:
  app-data:                         # named volumes must be declared here
```

The rule: if the left part starts with `/` or `./`, it's a bind mount. Otherwise it's a named volume. For a `compose.yaml` from someone else, the [Compose explainer](/en/tools/compose-explainer/) shows you which entries mount what.

| | Named volume | Bind mount |
| --- | --- | --- |
| **Location** | Managed by Docker | Chosen by you |
| **Viewing files** | Only in roundabout ways | Directly with `ls`, `cat` or an editor |
| **Backup** | Per volume, usually through a helper container | Copy the folder, done |
| **Permissions** | Docker takes care of them | You have to set them correctly yourself |
| **Deleting** | `docker compose down -v` removes it | Stays until you delete the folder |

## Why this site uses bind mounts

Named volumes are technically clean and cause less trouble with permissions. For a homelab, though, one advantage of bind mounts outweighs that: **everything is in one place.**

Each service gets a folder under `__ROOT__`, and its data lives in the `data/` subfolder:

```
__ROOT__/
└── vaultwarden/
    ├── compose.yaml
    ├── .env
    └── data/
        └── data/        ← mounted into the container as /data
```

For a backup, you then only have to back up one folder: `__ROOT__`. It holds the configuration, secrets and data of all services. If you move to a new server, you copy the folder and start the stacks again, see [Moving to new hardware](/en/setup/moving-hardware/). More in [Directory structure](/en/wiki/directory-structure/) and [Backup strategies](/en/wiki/backup-strategies/).

All templates under [Services](/en/services/) follow this pattern. If you choose a central data folder in "My setup", `./data/…` automatically becomes `__DATA_ROOT__/<service>/…`.

<Callout type="warning" title="Don't copy databases while they're running">
A database writes to its files constantly. If you copy the folder while it's running, the copy may be unusable. Create a dump with the database's own tool first, or briefly stop the stack with `docker compose stop`.
</Callout>

## Permissions: who owns the files?

With bind mounts, the same permission system applies on the server and in the container. Linux doesn't know user names here, only numbers: the **UID** (user ID) and the **GID** (group ID). If a program in the container runs as UID 1000, the files it creates also belong to UID 1000 on the server.

This leads to two typical problems:

- **The folder is missing.** If the path on the left doesn't exist yet, Docker creates it at startup, as root. A program that doesn't run as root in the container then may not write into it. So create the folders yourself beforehand.
- **The numbers don't match.** The program runs as a different UID than the owner of the folder. The log then usually says "Permission denied". How to fix that step by step is shown in [Permission denied](/en/wiki/permission-denied/).

The `id` command shows your own UID and GID. For the first user created, that's usually 1000.

```bash
id
```

## PUID and PGID

Many images, above all those from [LinuxServer.io](https://www.linuxserver.io/), solve the problem with two environment variables. You tell the container which UID and GID to work as:

```yaml
environment:
  - PUID=__PUID__
  - PGID=__PGID__
```

If you put in your own values here, all files in `./data` belong to your user. You can edit and back them up without `sudo`.

`PUID` and `PGID` are a convention, though, not a Docker standard. Images that don't know them simply ignore them. Some images instead always run as a fixed UID that's stated in their documentation. Then you adjust the folder's owner:

```bash
sudo chown -R 1000:1000 __ROOT__/<dienst>/data
```

Replace `1000:1000` with the UID and GID from the image's docs, and `<dienst>` with the service's folder. Other images support the Compose key `user:`, with which you set the UID directly. Which of these applies is always in the documentation of the image in question.

## Read-only

If you append `:ro` to a mount, the container can read the files but not change them:

```yaml
volumes:
  - ./config.yml:/app/config.yml:ro
```

That makes sense for configuration files only you change. One exception is the Docker socket `/var/run/docker.sock`, which Traefik mounts, for example: there, `:ro` only prevents the file itself from being changed. The container can still send commands to Docker through the socket. So only give it to containers you trust.
