## Why Data Doesn't Belong in the Container

A container is designed to be deleted and recreated at any time. That is exactly what happens with every update: Compose discards the old container and starts a new one from the new image. Anything the program has written inside the container itself is then lost.

That's why you mount the folders where a program stores its data from the outside. The program appears to be writing to its own folder, but in reality, the files end up on the server. Docker offers two ways to do this.

## Named Volumes and Bind Mounts

<Cards>
  <Card title="Named Volume">
    Docker manages the storage location itself. You just assign a name; the files are stored somewhere under /var/lib/docker/volumes.
  </Card>
  <Card title="Bind Mount">
    You choose the folder on the server yourself—for example, ./data/db next to the compose.yaml file. You'll see the files right away.
  </Card>
</Cards>

In the [...], they both `compose.yaml`look almost the same:

```yaml
services:
  app:
    image: example/app:1
    volumes:
      - app-data:/var/lib/app       # named volume: name on the left
      - ./data/config:/config       # bind mount: path on the left

volumes:
  app-data:                         # named volumes must be declared here
```

The rule: If the left part begins with  or`/` `./`, it is a bind mount. Otherwise, it is a named volume.

| | Named Volume | Bind Mount |
| --- | --- | --- |
| **Location** | Managed by Docker | Chosen by you |
| **View Files** | Only by taking a detour | Directly using `ls`,  or`cat` an editor |
| **Backup** | Per volume, usually via a auxiliary container | Copy the folder—done |
| **Rights** | Docker takes care of it | You have to set the appropriate value yourself |
| **Delete** | `docker compose down -v` it removes it | It will remain until you delete the folder |

## Why This Site Uses Bind Mounts

Named volumes are technically sound and cause fewer issues with permissions. For a home lab, however, bind mounts have one major advantage: **everything is in one place.**

Each service is assigned a folder under `__ROOT__`, and its data is stored in the subfolder `data/`:

```
__ROOT__/
└── vaultwarden/
    ├── compose.yaml
    ├── .env
    └── data/
        └── data/        ← mounted into the container as /data
```

To back up your system, all you need to do is back up one folder: `__ROOT__`. This folder contains the configuration, secrets, and data for all services. When you move to a new server, simply copy the folder and restart the Stacks. For more information, see "[Directory Structure](/en/wiki/directory-structure/) and [Backup Strategies](/en/wiki/backup-strategies/)."

All templates under "[Services](/en/services/)" follow this pattern. If you select a central data folder in "My Setup," it automatically`./data/…` becomes `__DATA_ROOT__/<dienst>/…`.

<Callout type="warning" title="Do not copy databases while the system is running">
A database is constantly writing to its files. If you copy the folder while it's running, the copy may be unusable. Create a dump beforehand using the database tool, or briefly stop the stack with `docker compose stop`.
</Callout>

## Rights: Who owns the files?

With bind mounts, the same permission settings apply on the server and inside the container. Linux does not use usernames; instead, it uses numbers: the **UID** (User ID) and the **GID** (Group ID). If a program runs in the container with UID 1000, the files it creates also belong to UID 1000 on the server.

This leads to two common problems:

- **The folder is missing.** If the path on the left does not yet exist, Docker will create it at startup—as root. A program that does not run as root inside the container will not be able to write to it. Therefore, create the folders yourself beforehand.
- **The permissions don't match.** The program is running under a different UID than the folder's owner. The log usually shows "Permission denied."

The command displays your own UID and GID`id`. For the first user created, this is usually 1000.

```bash
id
```

## PUID and PGID

Many images, most notably those from [LinuxServer.io](https://www.linuxserver.io/), solve this problem using two environment variables. You tell the container which UID and GID it should use:

```yaml
environment:
  - PUID=__PUID__
  - PGID=__PGID__
```

If you enter your own values here, all files will be stored in your`./data` user account. You can edit`sudo` and save them without any issues.

`PUID` However, they are`PGID` a convention, not a Docker standard. They simply ignore images that don't use them. Some images, on the other hand, always run as a fixed UID, which is listed in their documentation. In that case, you adjust the folder owner:

```bash
sudo chown -R 1000:1000 __ROOT__/<dienst>/data
```

Replace  `1000:1000`with the UID and GID from the image's documentation. Other images support the `compose` key`user:`, which allows you to specify the UID directly. The documentation for each image will always indicate which of these options applies.

## Read-only

If you `:ro`mount it, the container can read the files but not modify them:

```yaml
volumes:
  - ./config.yml:/app/config.yml:ro
```

This makes sense for configuration files that only you modify. One exception is the Docker socket`/var/run/docker.sock`, which Traefik, for example, mounts: In that case, it only`:ro` prevents the file itself from being modified. The container can still send commands to Docker via the socket. Therefore, only assign it to containers you trust.
