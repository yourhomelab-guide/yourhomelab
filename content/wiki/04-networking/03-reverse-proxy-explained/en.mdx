## The problem

Imagine Vaultwarden, Immich and Uptime Kuma run on your server. Each service brings its own web server and listens on a port of its own. Without a proxy, you'd have to open each of them to the outside individually and remember addresses like `__DOMAIN__:8081` or `__DOMAIN__:2283`. On top of that, each service would need its own certificate for HTTPS, and every open port is extra attack surface.

A **reverse proxy** solves this. It sits in front of all services and is the only thing reachable from outside.

## What a reverse proxy does

**One entrance.** The proxy takes ports 80 (HTTP) and 443 (HTTPS). Those are the only two ports you open. All other containers don't publish any ports but share a [Docker network](/en/wiki/docker-networks/) with the proxy, on this site `__NETWORK__`.

**Routing by hostname.** With every request, the browser sends along which name it called. The proxy looks at this name and decides where the request goes:

| Request to | is forwarded to |
| --- | --- |
| `vault.__DOMAIN__` | Container `vaultwarden`, port 80 |
| `fotos.__DOMAIN__` | Container `immich`, port 2283 |
| `status.__DOMAIN__` | Container `uptime-kuma`, port 3001 |

In DNS, all names point to the same IP, most easily with a wildcard record (see [DNS & domains](/en/wiki/dns-domains/)). A proxy can also route by path, such as `__DOMAIN__/api`.

**TLS termination.** The proxy handles HTTPS. It gets the certificates from Let's Encrypt, renews them in time and decrypts the requests. The request then goes to the container unencrypted over the internal Docker network. So your services don't have to deal with certificates. More in [TLS & certificates](/en/wiki/tls-certificates/).

**Headers.** Because the proxy sits in between, the service at first only sees the proxy's address. So the proxy adds headers like `X-Forwarded-For` (the visitor's real IP), `X-Forwarded-Proto` (was it HTTPS?) and `X-Forwarded-Host`. Many services need this information, for example for correct links or to attribute login attempts to the right IP. Some services have to be explicitly configured to trust the proxy. Their docs then mention it under keywords like "trusted proxies".

**Middlewares.** Between the entrance and the service, the proxy can insert further steps: redirecting HTTP to HTTPS, security headers, limiting requests per minute or a login in front. With a login service like [Tinyauth](/en/services/tinyauth/) or [Pocket ID](/en/services/pocket-id/), you can protect even services that don't have a good login of their own (see [Single sign-on](/en/wiki/single-sign-on/)).

## Three proxies this site supports

<Cards>
  <Card title="Traefik">
    A bit more complicated at first, but with the most possibilities. The configuration sits as labels directly in each service's compose.yaml. Traefik detects new containers by itself. This site's default.
  </Card>
  <Card title="Nginx Proxy Manager">
    The beginner's route. You create proxy hosts in a web interface with a few clicks, and the certificate comes with a checkbox.
  </Card>
  <Card title="Caddy">
    The middle ground. A short, readable text file, the Caddyfile. HTTPS is on automatically.
  </Card>
</Cards>

|                        | Traefik                                   | Nginx Proxy Manager                    | Caddy                                 |
| ---------------------- | ----------------------------------------- | -------------------------------------- | ------------------------------------- |
| **Configuration**      | Labels in each service's `compose.yaml`   | Web interface, stored in a database    | One text file (`Caddyfile`)           |
| **New service**        | Add labels, start the container           | Create a proxy host in the interface   | Add a block to the Caddyfile, reload  |
| **Certificates**       | Automatic                                 | With a checkbox per proxy host         | Automatic                             |
| **Getting started**    | Somewhat steeper                          | Easiest                                | Easy                                  |
| **Middlewares, login protection** | Very flexible, well documented | Basic features, the rest via custom Nginx configuration | Possible, directly in the Caddyfile |
| **Automation, Git**    | Very good, everything is in files         | Difficult, clicks can't be versioned   | Good, one file                        |

A quick impression of how a service is connected in each case. With Traefik, a few labels go into the service's `compose.yaml`:

```yaml
labels:
  - traefik.enable=true
  - traefik.http.routers.vaultwarden.rule=Host(`vault.__DOMAIN__`)
  - traefik.http.routers.vaultwarden.tls.certresolver=le
```

With Caddy, it's a block in the Caddyfile:

```
vault.__DOMAIN__ {
  reverse_proxy vaultwarden:80
}
```

In Nginx Proxy Manager, you enter the same details in a form: domain, target container, port.

For a service that's not in the [service catalog](/en/services/), the [proxy configuration](/en/tools/proxy-config/) tool generates these details for your proxy. If the proxy then only answers with "Bad Gateway" or 404, [Bad Gateway and 404 from the proxy](/en/wiki/bad-gateway/) helps.

## Which one should I take?

- **You want to learn and automate later?** Take **Traefik**. The first labels feel unfamiliar, but after that the proxy configuration belongs to each service, lives in files and can be versioned with Git. Login protection with Tinyauth or Pocket ID and CrowdSec plug in cleanly. All guides on this site build on Traefik: [Reverse proxy with Traefik](/en/setup/reverse-proxy-traefik/).
- **You want a quick result?** Take **Nginx Proxy Manager**. After a few minutes, your first service runs with HTTPS without you writing a single line of configuration: [Reverse proxy with Nginx Proxy Manager](/en/setup/reverse-proxy-npm/).
- **You like text files but not labels?** Then **Caddy** is a good middle ground.

The choice isn't final. Your services hardly notice which proxy sits in front of them. Switching later mainly means entering the routes again. Many people start with Nginx Proxy Manager and switch to Traefik once they have more services.

More about the individual proxies is on the service pages: [Traefik](/en/services/traefik/), [Nginx Proxy Manager](/en/services/nginx-proxy-manager/) and [Caddy](/en/services/caddy/).

<Callout type="warning" title="Only one proxy per server">
Ports 80 and 443 can only be taken by one program at a time. So don't run two proxies at once on the same server. When you switch, stop the old proxy first. If Docker still reports a port in use, see [Port already in use](/en/wiki/port-in-use/).
</Callout>

## In short

- A reverse proxy is the only entrance, on ports 80 and 443.
- It forwards requests to the right container based on the hostname.
- It handles HTTPS, sets headers for the services and can put middlewares like a login in front.
- Traefik for automation and possibilities, Nginx Proxy Manager for a quick start, Caddy as the middle ground.
