## Why you should know this

Almost every self-hosting problem of the "I can't get to my service" kind has one of three causes: the wrong address, the wrong port or a translation (NAT) somewhere in between. The basics are manageable, and they'll save you a lot of guesswork later. How to approach such a problem systematically is shown in [Troubleshooting: first steps](/en/wiki/first-steps/).

## IP addresses

An **IP address** is a device's house number on the network. There are two versions:

- **IPv4**: four numbers from 0 to 255, such as `192.168.1.20`. There are only about 4.3 billion of them, and they've long been scarce.
- **IPv6**: much longer, such as `2001:db8::20`. The address space is so large that every device can get its own globally valid address.

With IPv4, there are **private** and **public** addresses. Private addresses only apply within your home network and aren't routed on the internet. Three ranges are reserved for them:

| Range | Typical use |
| --- | --- |
| `10.0.0.0/8` | Company networks, VPNs, some routers |
| `172.16.0.0/12` | Docker networks often use addresses from here |
| `192.168.0.0/16` | Most home routers, e.g. `192.168.1.x` or `192.168.178.x` |

The notation `/8`, `/12` or `/16` is called **CIDR**. It states how many bits at the front define the network. The smaller the number, the larger the range.

Your router gets the public IPv4 address from your internet provider. All devices in your household share this one address towards the outside. On many lines it changes regularly, and some providers don't give you one of your own at all anymore (see [CGNAT & DS-Lite](/en/wiki/cgnat-ds-lite/)).

On your server, you see its addresses like this:

```bash
ip -brief address
```

So your server doesn't suddenly have a different address after a restart, give it a static IP on your home network. How that works is shown in [Static IP & hostname](/en/setup/static-ip-hostname/).

## Ports

An IP address leads to the device. The **port** says which program on that device is meant. Ports are numbers from 0 to 65535. A port can only be used by one program per address and protocol (TCP or UDP). What to do if a port is already taken is in [Port already in use](/en/wiki/port-in-use/).

Some ports are permanently assigned and come up all the time:

| Port | Service |
| --- | --- |
| 22 | SSH |
| 53 | DNS |
| 80 | HTTP |
| 443 | HTTPS |
| 51820 (UDP) | WireGuard (default) |

This command shows which ports on your server are currently open and listening. With `sudo`, you also see which process is behind them:

```bash
sudo ss -tulpn
```

An address like `0.0.0.0:443` means the service listens on all network interfaces. `127.0.0.1:8080` means only locally on the server itself, not reachable from outside.

## NAT

**NAT** (network address translation) translates addresses. Your router does this constantly: when your laptop with the private address `192.168.1.30` opens a website, the router replaces the sender address with its public IP. The reply arrives at the router, and it still knows which device it belongs to.

That works well for connections **from inside to outside**. For connections **from outside to inside**, though, the router doesn't know which device is meant. That's exactly what you need [port forwarding](/en/wiki/port-forwarding/) for: you tell the router that, for example, everything on port 443 should go to `192.168.1.20`.

A side effect: NAT acts like a simple layer of protection. Whatever isn't forwarded doesn't get through from outside in the first place.

<Callout title="IPv6 and NAT">
With IPv6, there's usually no NAT. Every device has a public address. Instead, the router's firewall provides the protection by blocking incoming connections by default. For a service, you then don't forward a port but allow access to the port and device.
</Callout>

## NAT in Docker

Docker uses the same principle. Containers have their own private addresses in a [Docker network](/en/wiki/docker-networks/). With `ports:` in the `compose.yaml`, you publish a container port on the host:

```yaml
ports:
  - "8080:80"   # host port 8080 -> container port 80
```

The left number is the port on the server, the right one the port in the container. That way, two containers can both use port 80 internally without getting in each other's way.

<Callout type="warning" title="Docker bypasses UFW">
Docker writes published ports directly into the kernel's firewall rules. UFW rules don't apply to them. So a `ports: "8080:80"` is reachable on the whole network, even if UFW blocks port 8080. Therefore only publish the reverse proxy's ports. If you only need a port locally, bind it to `127.0.0.1`, e.g. `"127.0.0.1:8080:80"`.
</Callout>

With a [reverse proxy](/en/wiki/reverse-proxy-explained/), you usually only need two published ports: 80 and 443. The proxy reaches all other services through the shared Docker network.

## In short

- The **IP address** finds the device, the **port** the program on it.
- On your home network, you use private addresses; towards the outside, all devices share one public address.
- **NAT** simply lets outgoing connections through; incoming ones need port forwarding.
- Docker does the same internally: `ports:` connects a port on the host to a port in the container.
