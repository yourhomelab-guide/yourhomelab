## Two kinds of updates

There are two layers on your server that you have to keep up to date:

<Cards>
  <Card title="Operating system">
    Kernel, system libraries, SSH, Docker itself. Comes through Debian's or Ubuntu's package manager (`apt`).
  </Card>
  <Card title="Container images">
    The services that run in Docker, such as Vaultwarden or Immich. They come as new image versions from a registry.
  </Card>
</Cards>

The two are independent of each other. `apt upgrade` doesn't update a single container, and a new image changes
nothing about the operating system.

## Operating system updates

Security updates for Debian and Ubuntu are usually small and well tested. So they can safely be installed
automatically, with the `unattended-upgrades` package. The guide [Automatic updates](/en/setup/automatic-updates/)
shows how.

To check for and install updates by hand:

```bash
sudo apt update
sudo apt upgrade
```

Kernel updates require a reboot. If the file `/var/run/reboot-required` exists, the system is waiting for one.

An upgrade to a new **major release** (for example from Debian 12 to 13, or from Ubuntu 24.04 to 26.04), on the other
hand, is a bigger step. Read the release notes first, make a backup and plan some time.

## Container updates

A container isn't updated, it's **replaced**: Docker downloads the new image, deletes the old container and starts a
new one. Your data survives this because it lives in `data/` outside the container (see
[Volumes & bind mounts](/en/wiki/volumes-bind-mounts/)).

Which version you get is defined by the **tag** in the `compose.yaml`. More under [Images & tags](/en/wiki/images-tags/).
The update itself is two commands in the stack folder:

```bash
cd __ROOT__/vaultwarden
docker compose pull
docker compose up -d
```

`pull` downloads new images, and `up -d` only recreates the containers whose image has changed. Afterwards, clean up
old, unused images with `docker image prune`.

### Read first, then update

Before you update a service, take a look at the **changelogs** or release notes, usually on the project's releases
page on GitHub or Codeberg. Watch especially for words like "breaking changes", "migration" or "deprecated". Some
updates require you to change environment variables or do an intermediate step.

### Major versions

Many projects number their releases as `major.minor.patch` (for example `2.4.1`). Patch and minor updates shouldn't
break anything. A jump in the first number (major), on the other hand, may. **Databases** are especially delicate:
moving a PostgreSQL container from version 17 to 18 doesn't simply work with a new tag, because the data format
changes. For that you need a dump and a restore; see [Database won't start after an update](/en/wiki/database-version/).
So always pin database images to a major version, such as `postgres:18`.

<Callout type="warning" title="Before bigger updates: back up">
  Before major updates, make a fresh backup of the stack folder, including a database dump. If something goes wrong,
  put the old tag back and restore the data. See [Backup strategies](/en/wiki/backup-strategies/).
</Callout>

## Automatic container updates?

There are tools that update containers without you doing anything. The best known was **Watchtower**. However, the
original project (`containrrr/watchtower`) is no longer maintained and was archived in December 2025. There are forks
whose maintenance you should check yourself before using them.

Whatever the tool, the trade-off is the same:

| | Automatic updates | Updates by hand |
| --- | --- | --- |
| **Pro** | Security holes closed quickly, no effort | You read changelogs and react to breaking changes |
| **Con** | A faulty update takes a service down at night without you noticing | You have to remember; updates pile up |

A good middle ground: **notify automatically, install small updates automatically, big ones deliberately.** Tools
like [Diun](https://crazymax.dev/diun/) only report new image versions to you without installing them.

## Dockhand: updates with checks (recommended)

If you use [Dockhand](/en/setup/portainer-dockhand/) as your interface, it already comes with this middle ground:

- On a schedule, it checks whether there are new images for your containers' tags, and notifies you if you like.
- You turn on automatic updates per container or for all of them. Updates always stay within the tag from the
  `compose.yaml`: with `:2`, you get all 2.x versions, but not version 3.
- With a vulnerability scanner active, the new image is checked first. If it fails, the old container keeps running.
- Dockhand shows newer tags (a new major version, for example) as suggestions with their release notes. You change
  the tag yourself.

Exclude databases (label `dockhand.update=false`) and only update them with a fresh backup. For most homelabs, that's
the best balance between security and effort. The guide [Portainer or Dockhand](/en/setup/portainer-dockhand/) shows
how to set it up.

## Renovate: updates as pull requests (optional)

Renovate is optional and mainly worth it if you work with Git anyway. If you keep your Compose files in a Git
repository, in Forgejo for example, [Renovate](https://docs.renovatebot.com/) can do the work. Renovate searches the
repository for image tags and opens a **pull request** for every new version, with a link to the release notes. You
review, merge, and your deployment rolls out the change.

That gives you both: you don't miss any update, but you still decide. And the Git history shows when which version
arrived, which helps with troubleshooting. The guide [Updates with Renovate](/en/setup/updates-renovate/) shows how to
set it up.

## A simple routine

- Operating system: security updates automatically, reboot when needed.
- Containers: Dockhand checks daily and installs updates within the tag. Without Dockhand: read the changelogs once a
  week or every two weeks, then `pull` and `up -d`.
- New major versions: read the release notes, change the tag in the `compose.yaml`, `up -d`.
- After the update, quickly check that everything runs, for example in [Uptime Kuma](/en/services/uptime-kuma/).
- Databases and major versions: only with a fresh backup and some time.
