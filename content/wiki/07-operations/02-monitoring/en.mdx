## Why monitoring at all?

Without monitoring, you only notice problems when something stops working: the photos don't load, the password
manager doesn't sync. Often there are warning signs beforehand. The disk slowly fills up, a container keeps
restarting, memory is permanently at its limit. Monitoring makes such developments visible and raises the alarm when
something goes down.

## Three angles

Monitoring in a homelab answers three different questions. Each needs a different tool.

| Question | What's measured | Example tool |
| --- | --- | --- |
| **How is the server doing?** | CPU, RAM, disk space, temperature, network, usage per container | Beszel |
| **Is the service reachable?** | Does the website answer? Is the status code right? Is the certificate about to expire? | Uptime Kuma |
| **What happened?** | Error messages and events from the services | Logs, see [Logs](/en/wiki/logs/) |

Resource monitoring shows you trends and causes. Availability monitoring shows you what users see. A server can look
perfectly healthy while the reverse proxy is misconfigured and nobody can reach your services. Conversely, a website
can still answer although the disk will be full in two days. That's why both are worth it.

## Resources: Beszel

[Beszel](/en/services/beszel/) consists of two parts: the **hub** with a web interface and a small **agent** that runs
on every monitored server and delivers metrics to the hub. You see history for CPU, RAM, disks, network and for each
Docker container individually. That way you can tell, for example, which container suddenly needs a lot of memory.

Beszel is deliberately lean. Big solutions like Prometheus with Grafana can do more, but are considerably more work
to start with. You can always switch later.

## Availability: Uptime Kuma

[Uptime Kuma](/en/services/uptime-kuma/) checks at fixed intervals whether your services answer. Among other things, it
can open HTTP(S) pages, test ports, ping hosts and query Docker containers. It also warns you when a TLS certificate
is about to expire. If you like, you build a status page from it to share with family or roommates.

<Callout title="Check from outside">
  Uptime Kuma on the same server can't see what happens from outside. If the server or your internet line goes down,
  monitoring goes down with it and can no longer warn you. So ideally run Uptime Kuma on another device, for example a
  small VPS, or add an external check service that calls your public addresses from outside.
</Callout>

## Notifications

Monitoring doesn't help much if you have to look at the dashboard every day. So set up notifications. Beszel and
Uptime Kuma can notify you by email, Telegram, Discord, Matrix or [ntfy](https://ntfy.sh) (push messages to your
phone), among others. How to set that up is shown in the guide [Notifications](/en/setup/notifications/).

A few tips so the warnings stay useful:

- **Few, important alarms.** Service unreachable, disk more than about 85 percent full, certificate expiring. If you
  get warnings all the time, you'll eventually ignore them.
- **Patient thresholds.** Short CPU spikes are normal. Only warn when a value stays high for a few minutes.
- **Test the notification.** Both tools have a test button. Use it before you rely on it.

## Monitor backups too

A backup job that has been failing silently for weeks is a classic problem. Uptime Kuma has the **push** monitor type
for this: your backup script calls a URL at the end. If that call doesn't come, you get a warning. That way you also
notice failures that produce no error message.

## How to start?

1. Install Beszel and set up the agent on your server:
   [Monitoring with Beszel](/en/setup/monitoring-beszel/).
2. Set up Uptime Kuma and create an HTTP monitor for each service:
   [Uptime Kuma](/en/setup/uptime-kuma/).
3. Set up and test notifications.

Then you know how your server is doing and are the first to hear about outages.
