## What are logs?

Logs are the records programs write while they work: startup messages, warnings, errors, access. When troubleshooting,
they're usually the first and best clue. If a container doesn't start or keeps restarting, the reason is almost always
in the last lines of its log.

On a homelab server, there are two sources:

- **Container logs**: everything a service in a container writes to standard output. Docker collects it.
- **System logs**: messages from the operating system and its services, such as SSH, Docker itself or updates. On
  Debian and Ubuntu, systemd's **journald** collects them.

## Reading container logs

In the stack folder, `docker compose logs` shows the logs of all containers in the stack:

```bash
cd __ROOT__/vaultwarden
docker compose logs
```

For longer logs, a few options help:

```bash
# Follow live (exit with Ctrl+C)
docker compose logs -f

# Only the last 100 lines
docker compose logs --tail 100

# Only the last hour, with timestamps
docker compose logs --since 1h -t

# Only one specific service of the stack
docker compose logs -f vaultwarden
```

The options can be combined, for example `docker compose logs -f --tail 50`. That's the typical command when you've
just restarted a service and want to watch what happens. With `grep`, you filter by keywords:

```bash
docker compose logs --since 24h | grep -i error
```

## System logs with journalctl

You read the system's logs with `journalctl`. If it shows few or no entries, your user lacks read access. Then put
`sudo` in front.

```bash
# Logs of the Docker service, live
journalctl -u docker -f

# SSH logins since yesterday
journalctl -u ssh --since yesterday

# Only errors since the last boot
journalctl -b -p err
```

The journal limits its own size, so you normally don't have to worry about it.

## Log rotation: the underestimated trap

By default, Docker stores container logs with the `json-file` logging driver as files under
`/var/lib/docker/containers/`. These files keep growing **without a size limit**. A chatty container can pile up many
gigabytes over months until the disk is full and nothing works anymore.

The solution is **log rotation**: once a log file reaches a certain size, Docker starts a new one and deletes the
oldest. You set this up once, centrally, in `/etc/docker/daemon.json`:

```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}
```

With this, Docker keeps at most three files of 10 MB each per container. The values have to be text in quotes.
Alternatively, use the `local` driver, which rotates on its own and compresses to save space:

```json
{
  "log-driver": "local"
}
```

If the file already exists, add the entries instead of overwriting it. Then restart Docker:

```bash
sudo nano /etc/docker/daemon.json
sudo systemctl restart docker
```

<Callout type="warning" title="Only applies to new containers">
  The setting only applies to containers that are **recreated** afterwards. A simple restart isn't enough. Recreate
  existing stacks with `docker compose up -d --force-recreate` in the respective stack folder.
</Callout>

If you want different values for a single service, you can set them in its `compose.yaml` with the `logging:` key.
Details are in the [Docker documentation on logging drivers](https://docs.docker.com/engine/logging/configure/).

This shows how much space container logs currently take up:

```bash
sudo du -sh /var/lib/docker/containers/
```

## Logs in the browser: Dozzle

If you'd rather read logs in the browser, try [Dozzle](https://dozzle.dev). Dozzle is a small container that shows
the logs of all containers live in a web interface, with search and filters. It doesn't store anything itself but
reads directly from Docker. For that, it needs access to the Docker socket. So don't put Dozzle on the internet
unprotected, only on your home network, via VPN or behind login protection like [Tinyauth](/en/setup/tinyauth/).

If you already use [Dockhand or Portainer](/en/setup/portainer-dockhand/), you usually don't need Dozzle: both
show every container's logs in the browser as well.

## Troubleshooting tips

- **Container keeps restarting?** `docker compose ps` shows the status, `docker compose logs --tail 50` the reason.
  Typical causes and solutions are under [Container in a restart loop](/en/wiki/restart-loop/).
- **Something doesn't work after an update?** Look for the first error message in the logs, not the last. Follow-up
  errors often hide the actual cause.
- **Service unreachable, but the container is running?** Then the reverse proxy's logs are worth a look.
- **Error message makes no sense?** Paste it into a search engine or the project's issues. You're rarely the first.

A step-by-step guide to troubleshooting is under [Troubleshooting: first steps](/en/wiki/first-steps/).
