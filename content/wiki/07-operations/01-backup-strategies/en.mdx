## Why Backups Are Essential

As long as you're just trying out services, data loss is annoying. But as soon as you have photos, passwords, or documents
If it's on your server, it's a problem. The most common causes are nothing out of the ordinary: a hard drive fails,
An update wrecks a database; you accidentally delete the wrong folder. Less common, but worse:
Ransomware (malware that encrypts your data), theft, fire, or water damage.

A backup is a **copy of your data stored in a different location** that you can restore in case of an emergency. It's important to
Part Two: A backup you've never restored is just a hope.

## The 3-2-1 Rule

The best-known rule of thumb for backups is:

- **3** copies of your data (the original plus two backups),
- on 2 different media or devices,
- including **1** copy stored offsite.

For a home lab, for example, this means: The data is stored on the server, and a backup is made to a USB drive or
A NAS on the home network, with a second encrypted backup stored in cloud storage or on a friend's computer.
The local copy can be quickly restored, while the external copy protects against fire and theft.

## RAID is not a backup

RAID distributes data across multiple hard drives in such a way that the failure of a single drive doesn't cause any problems. That's handy,
because the server just keeps running. But RAID mirrors **every** change immediately: If you delete a file or
If ransomware encrypts your photos, it happens on all drives at the same time. RAID therefore protects data availability,
not your data. The same applies to sync services like Nextcloud or Syncthing: They, too, reliably spread errors.

## Versioning

A good backup system keeps several snapshots from the past. If you don't realize until two weeks later that
If a file is corrupted, yesterday's backup won't help you. Common retention rules include, for example: the most recent
Keep 7 daily, 4 weekly, and 6 monthly records; delete older ones.

Modern backup tools store only the changes (deduplication). As a result, many snapshots take hardly any
First place.

## Encryption

Your backups contain everything: databases, configuration, and the `.env`files containing passwords and API keys.
If a backup is stored off-site, it should therefore **always** be **encrypted**—before it leaves your server.
In that case, the storage provider won't be able to do anything with it either.

<Callout type="warning" title="The password doesn't just belong on the server">
  Without the password or key for your backup repository, the backup is worthless. Be sure to store it in a separate
  somewhere else, such as in your password manager or printed out. If the server goes down, that's when you'll need it most.
</Callout>

## What You Should Back Up

This is where the directory structure of this site comes in handy: Everything related to your home lab is located under a
a single folder, by default`__ROOT__`. Within it, each service has its own folder with `compose.yaml`, `.env`
and the data in `data/`. A backup of  therefore contains`__ROOT__` everything you need to restore your data.
For more information, see "[Directory Structure](/en/wiki/directory-structure/)."

You don't need to back up:

- **Docker images**: It downloads them again `docker compose pull`at any time.
- **The operating system**: A fresh install is faster than restoring from a system backup. But make a note of this:
  what changes you made to the system (see [the documentation](/en/wiki/documentation/)).

### Databases require extra attention

A database is constantly writing to its files. If you copy these files while the system is running, the backup may
contain an incomplete state that the database will later be unable to read. Two simple solutions:

1. **Create a dump:** Before backing up, export the database to a file and include it in the backup.
   For PostgreSQL, something like this:

   ```bash
   cd __ROOT__/immich
   docker compose exec -T database pg_dumpall -U postgres > data/db-dump.sql
   ```

   The name of the database container (`database`) and the user depend on the specific stack.

2. **Briefly pause the stack:** `docker compose stop`, Backup, `docker compose start`. This is the easiest way; it means
   But a few minutes of downtime—usually at night—isn't a problem.

SQLite databases (a single file, such as those used by Vaultwarden or Uptime Kuma) are also affected.
Many services describe in their documentation how to back them up properly. It's worth taking a look.

There are three tried-and-true tools for Linux servers. All three encrypt, deduplicate, and manage snapshots.

    There are also specialized providers for this. The guides on this site use Borgmatic.
