## Why backups are a must

As long as you're only trying out services, losing data is annoying. But as soon as photos, passwords or documents
live on your server, it's a real problem. The most common causes are unspectacular: a disk dies, an update wrecks a
database, you accidentally delete the wrong folder. Rarer, but worse: ransomware (malware that encrypts your data),
theft, fire or water damage.

A backup is a **copy of your data in another place** that you can restore in an emergency. The second part is what
matters: a backup you've never restored is just a hope.

## The 3-2-1 rule

The best-known rule of thumb for backups is:

- **3** copies of your data (the original plus two backups),
- on **2** different media or devices,
- **1** of them off-site.

For a homelab, that means for example: the data lives on the server, one backup goes to a USB disk or a NAS on your
home network, and a second backup goes encrypted to cloud storage or to a computer at a friend's place. The local copy
is restored quickly; the external one protects against fire and theft.

## RAID is not a backup

RAID spreads data across several disks so that the failure of one disk doesn't break anything. That's handy, because
the server simply keeps running. But RAID mirrors **every** change immediately: if you delete a file or ransomware
encrypts your photos, it happens on all disks at once. So RAID protects availability, not your data. The same goes
for sync services like Nextcloud or Syncthing: they reliably distribute mistakes too.

## Versioning

A good backup keeps several **states** (snapshots) from the past. If you only notice after two weeks that a file is
damaged, yesterday's backup won't help you. Common retention rules are, for example: keep the last 7 daily,
4 weekly and 6 monthly states, delete older ones.

Modern backup tools only store the changes (deduplication). So many snapshots take up hardly more space than one.

## Encryption

Your backups contain everything: databases, configuration and the `.env` files with passwords and API keys. So if a
backup is stored off-site, it should **always be encrypted**, before it leaves your server. Then even the storage
provider can't do anything with it.

<Callout type="warning" title="The password doesn't belong only on the server">
  Without the password or key of your backup repository, the backup is worthless. Keep it in another place as well,
  for example in your password manager or printed out. If the server is gone, that's when you need it most.
</Callout>

## What you should back up

This is where this site's directory structure pays off: everything that belongs to your homelab lives under a single
folder, `__ROOT__` by default. In it, each service has its own folder with `compose.yaml`, `.env` and the data in
`data/`. So a backup of `__ROOT__` contains everything you need to restore. More under
[Directory structure](/en/wiki/directory-structure/).

You don't need to back up:

- **Docker images**: `docker compose pull` downloads them again at any time.
- **The operating system**: reinstalling is faster than restoring a system backup. But note what you've changed on
  the system (see [Documentation](/en/wiki/documentation/)).

### Databases need extra attention

A database writes to its files constantly. If you copy these files while it's running, the backup may contain a
half-finished state the database can't read later. Two simple solutions:

1. **Create a dump:** before the backup, export the database to a file and back that up too. For PostgreSQL, for
   example:

   ```bash
   cd __ROOT__/immich
   docker compose exec -T database pg_dumpall -U postgres > data/db-dump.sql
   ```

   The name of the database container (`database`) and the user depend on the stack.

2. **Briefly stop the stack:** `docker compose stop`, backup, `docker compose start`. That's the simplest, but means a
   few minutes of downtime, usually no problem at night.

SQLite databases (a single file, for example with Vaultwarden or Uptime Kuma) are affected too. Many services
describe in their docs how to back them up correctly. It's worth a look.

## Tools

There are three proven tools for Linux servers. All three encrypt, deduplicate and manage snapshots.

<Cards>
  <Card title="BorgBackup + borgmatic">
    Borg is very mature and efficient. borgmatic adds a single configuration file for sources, retention, checks and
    hooks. The target is a local disk or a computer with SSH and Borg; there are also specialized providers for it.
    The guides on this site use borgmatic.
  </Card>
  <Card title="restic">
    A single program, encryption always on. Stores locally, via SFTP or directly in S3-compatible cloud storage,
    without anything having to be installed on the target.
  </Card>
  <Card title="Kopia">
    Similar to restic, but also comes with a web interface and a desktop app.
  </Card>
</Cards>

All of them are a good choice. More important than the tool is that the backup runs **automatically**, for example
with a cron job or systemd timer, and that you check regularly whether it works.

The [borgmatic configuration](/en/tools/borgmatic-config/) tool generates a suitable `config.yaml` for
borgmatic from your setup, including database dumps and retention rules.

## Testing restores

Rehearse the emergency regularly: restore a service from the backup on another computer or in another folder and
check whether it starts and your data is there. Only then do you know your backup is any good. How that works is
shown in the guide [Testing restores](/en/setup/testing-restores/). What to do if the whole server fails is best
decided beforehand in an [emergency plan](/en/setup/emergency-plan/).
