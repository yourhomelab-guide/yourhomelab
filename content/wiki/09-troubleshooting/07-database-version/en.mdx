## Symptom

After `docker compose pull` and `docker compose up -d`, the database container is stuck in a
[restart loop](/en/wiki/restart-loop/), and the app reports that it can't reach a database. Postgres's log says:

```text
FATAL:  database files are incompatible with server
DETAIL:  The data directory was initialized by PostgreSQL version 17, which is not compatible with this version 18.3.
```

## Why this happens

Postgres stores its data in a format that belongs to the **major version** (16, 17, 18 …). A new major version can't
simply open the old one's files. Within a major version, from 18.2 to 18.3 for example, an update is no problem.

Usually a tag that's too open is behind it: `postgres:latest` or no tag at all silently jumps to the next major version
on the next `pull`. Background in [Images & tags](/en/wiki/images-tags/).

## Causes

1. **Tag `latest` or no tag** on the database image.
2. **Tag raised deliberately** without migrating the data.
3. **An update tool** raised the major version: Renovate through a merged pull request, or Watchtower or Dockhand with
   a tag like `latest`.

## Checking

Which image is running, and which version does the data have?

```bash
cd __ROOT__/myapp
grep -n "image:" compose.yaml
docker compose logs --tail 20 db
sudo cat __DATA(myapp)__/db/PG_VERSION
```

`myapp` stands for your stack, `db` for the database's service name. The bind mount in your `compose.yaml` shows where
the data lives; in the example it's `__DATA(myapp)__/db`. `PG_VERSION` contains the data's major version. The
[Compose explainer](/en/tools/compose-explainer/) marks which images in your `compose.yaml` run with `latest` or
without a tag at all.

## Quick fix: back to the old version

The data isn't broken. Postgres just refused to open it. Put the major version from `PG_VERSION` back into the
`compose.yaml` and **pin** it so this doesn't happen again:

```yaml
  db:
    image: postgres:17
```

```bash
docker compose up -d
```

The service runs again. If the new version did already change something in the data and the start still fails,
restore your last backup; see [Testing restores](/en/setup/testing-restores/).

## Upgrading properly: dump and restore for Postgres

The safe way: export the data with the old version (dump), create it fresh with the new version and import it again
(restore).

<Callout type="warning" title="Back up first">
  Make a backup of the whole stack folder first; see [Backups with borgmatic](/en/setup/backups-borgmatic/). In the
  following process, the old data folder also stays around as a copy.
</Callout>

1. **Keep the old version running and stop the app.** Only the database may run, so nothing changes during the dump:

   ```bash
   cd __ROOT__/myapp
   docker compose stop
   docker compose up -d db
   ```

2. **Create the dump.** `pg_dumpall` backs up all databases including users. The variable is evaluated in the
   container:

   ```bash
   docker compose exec -T db sh -c 'pg_dumpall -U "$POSTGRES_USER"' > dump.sql
   ls -lh dump.sql
   ```

   The file must not be empty.

3. **Stop the stack and set the old data folder aside:**

   ```bash
   docker compose down
   sudo mv __DATA(myapp)__/db __DATA(myapp)__/db-old
   ```

4. **Enter the new major version** and start only the database. It creates an empty data folder with the user and
   password from the `.env`. From Postgres 18 on, you mount `/var/lib/postgresql` instead of
   `/var/lib/postgresql/data` as before. The image creates a subfolder per major version inside it by itself:

   ```yaml
     db:
       image: postgres:18
       volumes:
         - __DATA(myapp)__/db:/var/lib/postgresql
   ```

   ```bash
   docker compose up -d db
   docker compose logs --tail 20 db
   ```

   Wait until `database system is ready to accept connections` appears.

5. **Import the dump:**

   ```bash
   docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d postgres' < dump.sql
   ```

   Messages like `role "..." already exists` are harmless, because the user was already created on startup.

6. **Start everything and test:**

   ```bash
   docker compose up -d
   ```

   Log in to the app and check that your data is there. Once everything has run stably for a few days, delete
   `dump.sql` and `__DATA(myapp)__/db-old`. The dump contains password hashes, so don't leave it lying around.

<Callout title="Follow the app's requirements">
  Some apps require a specific Postgres version or bring their own image, like Immich. Read the app's docs before the
  upgrade. The [Postgres page on Docker Hub](https://hub.docker.com/_/postgres) describes the changed storage location
  from Postgres 18 on.
</Callout>

## MariaDB

MariaDB can usually take over data files from older versions directly, but then has to adjust its system tables. The
official image does that on startup if you set this variable:

```yaml
  db:
    image: mariadb:lts
    environment:
      - MARIADB_AUTO_UPGRADE=1
```

A **downgrade** to an older version, however, doesn't work. For that you need the backup from before. Instead of
`mariadb:latest`, use a fixed major version like `mariadb:11` or the `lts` tag, which only gets long-term support
versions. The [Nextcloud template](/en/services/nextcloud/) uses `lts` together with `MARIADB_AUTO_UPGRADE`. For MySQL:
only make big version jumps step by step and with a backup; see the
[MySQL docs on upgrading](https://dev.mysql.com/doc/refman/8.4/en/upgrading.html).

## Prevention

- Always pin database images to the major version: `postgres:18`, `mariadb:11` or `mariadb:lts`.
- Never take database updates automatically. In Dockhand, exclude them with the label `dockhand.update=false` (the
  templates on this site already set it). [Renovate](/en/setup/updates-renovate/) only suggests new major versions as
  pull requests, which you merge deliberately and with a backup.
- Make a fresh backup before every bigger update; see [Updates](/en/wiki/updates/).
