## Stay calm

Almost every error in a homelab has a cause that's written down somewhere: in the log, in the container's status or
in the configuration. Frantic trial and error usually makes it worse, because afterwards you no longer know which
change did what. Three rules help:

- **Read first, then change.** Look at the status and logs before you touch anything.
- **One change at a time.** Change one value, restart, check. If it doesn't help, undo it.
- **Backup before experiments.** Before you touch data or databases, back up the data folder. A quick copy is enough
  for the moment:

```bash
cd __ROOT__/myapp
docker compose stop
sudo cp -a __DATA(myapp)__ __DATA(myapp)__.bak-$(date +%F)
docker compose start
```

Replace `myapp` with the name of your stack, for example `vaultwarden`.

## 1. Is the container running at all?

Change into the stack folder and show the status of all containers, including stopped ones:

```bash
cd __ROOT__/myapp
docker compose ps -a
```

Watch the `STATUS` column:

| Status | Meaning |
| --- | --- |
| `Up 3 hours` | Running. The problem is more likely the network or the proxy. |
| `Up 2 minutes (unhealthy)` | Running, but the health check fails. |
| `Restarting (1) 5 seconds ago` | Crashes and gets restarted. See [restart loop](/en/wiki/restart-loop/). |
| `Exited (1) 10 minutes ago` | Exited with an error code. The logs tell you why. |
| `Exited (137)` | Killed, often because of a lack of memory. |

## 2. Read the logs

The last lines of the log almost always name the reason:

```bash
docker compose logs --tail 50
docker compose logs --tail 50 -f <service>
```

`-f` follows the log live; exit with `Ctrl+C`. Look for the **first** error message, not the last. Follow-up errors
often hide the actual cause. More in the article [Logs](/en/wiki/logs/).

## 3. Check the configuration

Typos in the `compose.yaml` or missing variables in the `.env` are very common. `docker compose config` reads both and
shows the final configuration as Docker sees it:

```bash
docker compose config
```

If a variable is missing, you'll see a warning like this:

```text
WARN[0000] The "DB_PASSWORD" variable is not set. Defaulting to a blank string.
```

<Callout type="warning" title="Contains secrets">
  The output of `docker compose config` contains your passwords in plain text. Don't post it in forums without checking.
</Callout>

Don't understand a section of your `compose.yaml`? The [Compose explainer](/en/tools/compose-explainer/) explains
every line.

## 4. Details with docker inspect

`docker inspect` shows everything Docker knows about a container. The full output is long, so you filter
specifically:

```bash
# Status, exit code and whether memory ran out
docker inspect --format '{{.State.Status}} exit={{.State.ExitCode}} oom={{.State.OOMKilled}}' <container>

# Which networks is the container on?
docker inspect --format '{{range $name, $net := .NetworkSettings.Networks}}{{$name}} {{end}}' <container>

# Which folders are mounted?
docker inspect --format '{{range .Mounts}}{{.Source}} -> {{.Destination}}{{println}}{{end}}' <container>
```

`docker compose ps` shows the container name in the first column.

## 5. Ports and resources

`ss` shows which ports are taken and by which program:

```bash
sudo ss -tulpn
```

Plus a quick look at disk space and load:

```bash
df -h
docker stats --no-stream
```

## If you're stuck

- Paste the error message into a search engine or the project's issues on GitHub. You're rarely the first.
- Read the release notes if the error appeared after an update. Breaking changes are listed there.
- If you ask in a forum, include: the image with its tag, the relevant parts of the `compose.yaml` (without secrets)
  and the log lines around the first error.
