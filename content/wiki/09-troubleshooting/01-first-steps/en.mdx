## Stay calm

Almost every error in the Homelab has a cause that can be found somewhere: in the log, in the container's status, or in the
Configuration. Frantically trying things out usually makes it worse, because afterward you won't remember which change
which has had an effect. Three rules can help:

- **Read first, then make changes.** Check the status and logs before you do anything.
- **One change at a time.** Change a value, restart, and check. If it doesn't help, undo it.
- **Back up before experimenting.** Before you start working with data or databases, back up the data folder.
  A quick copy will do for now:

```bash
cd __ROOT__/myapp
docker compose stop
sudo cp -a __DATA(myapp)__ __DATA(myapp)__.bak-$(date +%F)
docker compose start
```

Replace  with`myapp` the name of your stack, for example `vaultwarden`.

## 1. Is the container even running?

Navigate to the stack folder and view the status of all containers, including the stopped ones:

```bash
cd __ROOT__/myapp
docker compose ps -a
```

Pay attention to the column`STATUS`:

| Status | Meaning |
| --- | --- |
| `Up 3 hours` | It's working. The problem is more likely with the network or proxy. |
| `Up 2 minutes (unhealthy)` | It's running, but the health check fails. |
| `Restarting (1) 5 seconds ago` | Crashes and restarts. See "[Restart Loop](/en/wiki/restart-loop/)." |
| `Exited (1) 10 minutes ago` | Terminated with an error code. The logs reveal why. |
| `Exited (137)` | Crashes, often due to insufficient memory. |

## 2. Read logs

The last few lines of the log almost always state the reason:

```bash
docker compose logs --tail 50
docker compose logs --tail 50 -f <service>
```

`-f` Follow the log in real time; exit with `Strg+C`. Look for the **first** error message, not the last one.
Consequential errors often mask the actual cause. Read more about this in the article "[Logs](/en/wiki/logs/)."

## 3. Check Configuration

Typos in the  `compose.yaml`or missing variables in the  `.env`are very common. `docker compose config`
reads both and displays the final configuration as Docker sees it:

```bash
docker compose config
```

If a variable is missing, you'll see a warning like this:

```text
WARN[0000] The "DB_PASSWORD" variable is not set. Defaulting to a blank string.
```

<Callout type="warning" title="Contains Secrets">
  The output of  contains`docker compose config` your passwords in plain text. Do not post them in forums without checking them first.
</Callout>

Don't`compose.yaml` understand a section of your text? The [Compose Guide](/en/werkzeuge/compose-erklaerer/)
explains each line.

## 4. Details with `docker inspect`

`docker inspect` shows everything Docker knows about a container. The full output is long, so you can filter it
specifically:

```bash
# Status, Exit-Code und ob der Speicher ausging
docker inspect --format '{{.State.Status}} exit={{.State.ExitCode}} oom={{.State.OOMKilled}}' <container>

# In welchen Netzwerken hängt der Container?
docker inspect --format '{{range $name, $net := .NetworkSettings.Networks}}{{$name}} {{end}}' <container>

# Welche Ordner sind eingebunden?
docker inspect --format '{{range .Mounts}}{{.Source}} -> {{.Destination}}{{println}}{{end}}' <container>
```

The container name is displayed in`docker compose ps` the first column.

## 5. Ports and Resources

To see which ports are in use and by which program, run`ss`:

```bash
sudo ss -tulpn
```

Here's a quick look at storage space and utilization:

```bash
df -h
docker stats --no-stream
```

## If you're stuck

- Copy the error message into a search engine or into the project's issues on GitHub. You're rarely the first one.
- Read the release notes if the error occurred after an update. Breaking changes are listed there.
- If you ask a question in a forum, include: an image with a tag, relevant parts of the text (`compose.yaml`without any secrets), and the
  Log entries surrounding the first error.
