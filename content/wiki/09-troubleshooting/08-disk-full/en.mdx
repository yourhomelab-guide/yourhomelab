## Symptom

Suddenly many things stop working at once. A `docker compose pull` aborts, containers don't start, and the logs say:

```text
write /var/lib/docker/tmp/GetImageBlob123456: no space left on device
```

```text
PANIC:  could not write to file "pg_wal/xlogtemp.42": No space left on device
```

## Causes

1. **Old images.** Every update downloads a new image. The old ones stay behind, often several gigabytes.
2. **Container logs without rotation.** By default, Docker writes logs without a size limit.
3. **Old backups or dumps** on the same disk that never get cleaned up.
4. **Build cache**, if you build images yourself.
5. **The services' own data**, such as photos, downloads or media.

## Check

How full is which disk?

```bash
df -h
```

What matters is `/` and the disk `__ROOT__` lives on. If `Use%` says 100%, it's full.

How much does Docker use, and how much of it could be freed (`RECLAIMABLE`)?

```bash
docker system df
```

Which container logs are big?

```bash
sudo du -sh /var/lib/docker/containers/*/*-json.log | sort -h | tail -5
```

Which stack uses the most?

```bash
sudo du -h -d1 __ROOT__ | sort -h
```

And the system journal:

```bash
journalctl --disk-usage
```

## Solution

### Remove old images

```bash
docker image prune -a
```

This deletes all images no container is currently using. If a stack isn't running right now, `docker compose up -d`
simply downloads its image again later. Data isn't affected.

Remove the build cache if you build images yourself:

```bash
docker builder prune
```

<Callout type="warning" title="Careful with --volumes">
  `docker system prune` cleans up stopped containers, unused networks and untagged images. With `--volumes`, it also
  deletes volumes no container is currently using, and with them possibly the data of a stopped stack. Leave the
  option out. Docker never touches bind mounts under `__ROOT__`.
</Callout>

### Empty large logs and turn on rotation

You empty a huge log while it's running, without deleting the file. You found the path above with `du`:

```bash
sudo truncate -s 0 /var/lib/docker/containers/<id>/<id>-json.log
```

So this doesn't happen again, set up log rotation. How is explained in the article [Logs](/en/wiki/logs/), in
the section on log rotation.

You shrink the journal to 500 MB like this:

```bash
sudo journalctl --vacuum-size=500M
```

### Old backups and packages

If backups live on the same disk, delete old states. With borgmatic, `keep_daily` & co. and `compact` do this
automatically, see [Backups with borgmatic](/en/setup/backups-borgmatic/). Also don't forget old dumps and `.bak`
copies from earlier experiments.

You delete packages downloaded by `apt` with:

```bash
sudo apt clean
sudo apt autoremove
```

### When the data itself gets too big

If a service simply outgrows the disk, cleaning up won't help for long. Then its data belongs on a bigger or
additional disk. With the "central" mode from [Directory structure](/en/wiki/directory-structure/), you can
store the data separately from the configuration.

## After cleaning up

Databases that were interrupted mid-write usually recover on their own when restarted. Restart the affected stacks and
check their logs:

```bash
cd __ROOT__/myapp
docker compose up -d
docker compose logs --tail 30
```

`myapp` stands for your stack.

## Prevention

Get warned before the disk is full. [Beszel](/en/setup/monitoring-beszel/) can send you a message from 85% usage,
for example. How the message gets to your phone is shown in the guide [Notifications](/en/setup/notifications/).
Background in [Monitoring](/en/wiki/monitoring/).
