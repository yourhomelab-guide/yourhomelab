## Symptom

Suddenly, a lot of things stop working at the same time. One  `docker compose pull`crashes, containers fail to start, and in the
The logs say:

```text
write /var/lib/docker/tmp/GetImageBlob123456: no space left on device
```

```text
PANIC:  could not write to file "pg_wal/xlogtemp.42": No space left on device
```

## Causes

1. **Old images.** Every update downloads a new image. The old ones remain on the system, often totaling several gigabytes.
2. **Container logs without rotation.** By default, Docker writes logs without a size limit.
3. **Old backups or dumps** on the same disk that are never cleaned up.
4. **Build cache** if you build images yourself.
5. **Data from the services themselves**, such as photos, downloads, or media.

## Check

How full is each drive?

```bash
df -h
```

Also of interest are  `/`and the disk on which  `__ROOT__`is located. If it reads  `Use%`100%, it is full.

How much space does Docker take up, and how much of that could be freed up (`RECLAIMABLE`)?

```bash
docker system df
```

Which container logs are large?

```bash
sudo du -sh /var/lib/docker/containers/*/*-json.log | sort -h | tail -5
```

Which stack takes up the most space?

```bash
sudo du -h -d1 __ROOT__ | sort -h
```

And the system log:

```bash
journalctl --disk-usage
```

## Solution

### Remove Old Images

```bash
docker image prune -a
```

This deletes all images that are not currently being used by a container. If a stack is not currently running, its`docker compose up -d`
Just re-image it later. The data won't be affected.

Remove the build cache if you build images yourself:

```bash
docker builder prune
```

<Callout type="warning" title="Be careful with --volumes">
  `docker system prune` cleans up stopped containers, unused networks, and untagged images. It also `--volumes`deletes
  Volumes that are not currently being used by any container, and thus may contain data from a stopped stack. Leave the option
  Docker never touches`__ROOT__` bind mounts.
</Callout>

### Empty large logs and enable rotation

You can clear a huge log file while the system is running, without deleting the file. You found`du` the path above using:

```bash
sudo truncate -s 0 /var/lib/docker/containers/<id>/<id>-json.log
```

To prevent this from happening again, configure log rotation. You can find instructions on how to do this in the article "[Logs](/en/wiki/logs/)."
in the section on log rotation.

Here's how to reduce the size of the log file to 500 MB:

```bash
sudo journalctl --vacuum-size=500M
```

### Old Backups and Packages

If backups are stored on the same disk, delete the old versions. With borgmatic,  `keep_daily`& Co. and  take care of `compact`that
Automatically; see "[Backups with Borgmatic](/en/setup/backups-borgmatic/)." Also, forget about old dumps and `.bak`copies.
not from earlier experiments.

To delete`apt` downloaded packages from , use:

```bash
sudo apt clean
sudo apt autoremove
```

### When the data itself becomes too large

If a service simply outgrows its disk space, cleaning it up won't be a permanent solution. In that case, its data belongs on a
a larger or additional disk. Using the "central" mode from [the directory structure](/en/wiki/directory-structure/)
you can store the data separately from the configuration.

## After Cleaning Up

Databases that were interrupted while writing are usually restored automatically when the system restarts. Start the
Restart the affected stacks and check their logs:

```bash
cd __ROOT__/myapp
docker compose up -d
docker compose logs --tail 30
```

`myapp` stands for your stack.
