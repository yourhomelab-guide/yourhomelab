## Symptom

The container exits shortly after starting or ends up in a [restart loop](/en/wiki/restart-loop/).
The log shows a message like:

```text
mkdir: cannot create directory '/data/config': Permission denied
chown: changing ownership of '/var/lib/postgresql/data': Operation not permitted
Error: EACCES: permission denied, open '/app/data/db.sqlite'
```

## Why this happens

Processes in a container run under a user ID (UID) and group ID (GID), just like on the host. Linux only knows
numbers here, not names. If a container with UID 1000 writes to a bind mount owned by root (UID 0), Linux refuses.
The user's name inside the container doesn't matter.

## Causes

1. **Docker created the folder itself.** If a bind mount's path doesn't exist yet at startup, Docker creates it, as
   `root:root`. If the service doesn't run as root, it may not write there.
2. **The image deliberately runs without root privileges.** Many modern images (rootless) use a fixed UID, often
   `1000`, sometimes `65532` or one of their own. The data folder has to belong to this UID.
3. **PUID/PGID are missing or wrong.** Images from linuxserver.io, for example, read the `PUID` and `PGID` variables
   and then run under that UID/GID.
4. **Files were copied as root.** For example when restoring a backup with `sudo cp` or `sudo tar`.
5. **The permissions are too strict**, for example `700` for a different owner.

## Check

In the commands, `myapp` stands for your stack and `<service>` for the service name from the `compose.yaml`.

Who owns the data folder? `-n` shows numbers instead of names:

```bash
ls -ln __DATA(myapp)__
```

Which UID does the process in the container run as?

```bash
cd __ROOT__/myapp
docker compose exec <service> id
```

If the container doesn't run long enough for `exec`, check whether the image specifies a user. Empty means root:

```bash
docker image inspect --format '{{.Config.User}}' <image>
```

`id` on the host shows your own UID and GID. On Debian and Ubuntu, the first user created usually has `1000`.

## Solution

**Give the folder to the right user.** Use the UID and GID from the check:

```bash
cd __ROOT__/myapp
docker compose down
sudo chown -R 1000:1000 __DATA(myapp)__
docker compose up -d
```

**For images with PUID/PGID**, enter your own UID/GID in the `compose.yaml`, and the folder belongs to you:

```yaml
environment:
  - PUID=__PUID__
  - PGID=__PGID__
```

```bash
sudo chown -R __PUID__:__PGID__ __DATA(myapp)__
```

**Create the folder before the first start.** That keeps Docker from creating it as root:

```bash
mkdir -p __DATA(myapp)__
```

The image's docs usually state which UID it expects. Often there's a ready-made `chown` command there too. The
[Compose explainer](/en/tools/compose-explainer/) shows you line by line which bind mounts and variables your
`compose.yaml` sets.

<Callout type="warning" title="No chmod 777">
  `chmod -R 777` seems to make the error go away, but allows every process on the server to read and change the data.
  Some programs, such as databases or SSH, even refuse to start with permissions that are too open. Set the right owner
  instead.
</Callout>

**Don't bend databases.** Official images of Postgres or MariaDB set the permissions of their data folder themselves
at the first start. If the folder then has an unexpected UID (such as `999`), that's normal. Don't change it.

## SELinux

On Fedora, RHEL or Rocky Linux, SELinux can block access even though the permissions are right. Then the `:Z` suffix
on the bind mount helps, for example `- __DATA(myapp)__:/data:Z`. On Debian and Ubuntu, SELinux normally isn't active,
so you don't need it there.

More background on bind mounts is under [Volumes & bind mounts](/en/wiki/volumes-bind-mounts/).
