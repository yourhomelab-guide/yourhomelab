## What attack surface means

The **attack surface** is everything an attacker can reach from outside: open ports, login pages, programs with
security holes. The smaller it is, the less can go wrong.

You don't have to be a security expert for this. Most attacks on homelabs are automated. Bots scan the internet for
open ports, known vulnerabilities and default passwords. If you avoid these easy targets, you're already very well
protected.

## Only open the ports you need

Every port reachable from the internet has to be secured. The simplest protection: don't open the port in the first
place.

- **In the router:** with a reverse proxy, you only need to forward ports 80 and 443. All services run through these
  two ports. More in [Port forwarding](/en/wiki/port-forwarding/).
- **Without open ports:** with a [VPN](/en/wiki/vpn/) or a [tunnel](/en/wiki/tunnels/), you don't have
  to open anything. For services only you use, that's often the best choice.
- **SSH:** don't forward port 22 in the router unless you have to. On the go, you reach the server through the VPN.

You see which ports are listening on your server with:

```bash
sudo ss -tlnp
```

Anything listed with `0.0.0.0` or `[::]` is reachable on all network interfaces. `127.0.0.1` means only from the
server itself.

## Docker bypasses UFW

This is one of the most common surprises. You set up [UFW](/en/setup/firewall-ufw/), allow only SSH, 80 and 443,
and still a container is reachable on port 8080.

The reason: when a container publishes a port (`ports:` in the `compose.yaml`), Docker writes its own firewall rules.
They apply before UFW's rules are even checked. UFW doesn't show the port, but it's open.

The solution is not to publish ports in the first place:

- **Services behind the reverse proxy** don't need `ports:`. The proxy reaches them through the shared network
  `__NETWORK__`. Only the proxy itself publishes 80 and 443.
- **If a port only needs local access,** bind it to `127.0.0.1`:

```yaml
    ports:
      - "127.0.0.1:8080:8080"
```

Then you can only reach the service from the server itself, for example through an SSH tunnel. Background is in the
[Docker documentation on packet filtering](https://docs.docker.com/engine/network/packet-filtering-firewalls/).

<Callout type="warning" title="A router isn't the same as a firewall">
  If your server sits at home behind a router without port forwarding, published ports are only reachable on your home
  network. A VPS, on the other hand, is connected directly to the internet. There, every published port is open to the
  whole world immediately.
</Callout>

## Don't make admin interfaces public

The Traefik dashboard, [Dockhand](/en/services/dockhand/) or [Portainer](/en/services/portainer/), the interface of
[Nginx Proxy Manager](/en/services/nginx-proxy-manager/) or your router's admin page are powerful. Whoever gets in there
often controls the whole server.

- Only make such interfaces reachable on your home network or through the VPN.
- If you have to publish them through the reverse proxy, put a login in front, for example with
  [Tinyauth](/en/setup/tinyauth/) or [Pocket ID](/en/setup/pocket-id/). See also
  [Single sign-on](/en/wiki/single-sign-on/).
- Change default passwords right after installation.

## Protecting the Docker socket

Some containers get the Docker socket `/var/run/docker.sock` mounted, for example Traefik, Dockhand, Portainer or
monitoring tools. Through the socket, they control Docker.

Important to know: **access to the socket is as good as root access to the server.** Whoever can use it starts any
container with any privileges. The `:ro` suffix when mounting changes little about that. It only prevents the file
itself from being changed, not the commands that go through the socket.

So:

- Only give the socket to containers that really need it, and only from trustworthy sources.
- For more security, there are **socket proxies**. They sit between the container and the socket and only let certain
  requests through, for example read-only access.
- The same applies to the `docker` group on the server: whoever is in it effectively has root privileges.

## Installing updates

Many attacks exploit holes that were patched long ago. So keep two levels up to date:

- **The operating system:** with [automatic updates](/en/setup/automatic-updates/) for security patches.
- **The containers:** update images regularly, most conveniently with Dockhand's update schedules, see
  [Updates](/en/wiki/updates/).

Services reachable from the internet take priority.

## Protecting logins

Public login pages attract password guessers. These help:

- **Strong, unique passwords** and, where possible, passkeys or a second factor.
- **Keys instead of passwords for SSH**, see [SSH basics](/en/wiki/ssh-basics/).
- **CrowdSec:** reads the logs of your reverse proxy and other services, detects suspicious behavior like many failed
  logins and blocks the IP. In addition, all users share their findings, so known attackers are often blocked in
  advance. With Traefik, CrowdSec can be added as a middleware, see [CrowdSec](/en/setup/crowdsec/).

## Least privilege: as few rights as possible

The **principle of least privilege** means every user, every service and every container only gets the rights it
really needs. If it's compromised, the damage stays limited.

In a homelab, that means for example:

- You work as a normal user with `sudo`, not as root. See [Users & sudo](/en/setup/users-sudo/).
- Containers don't run as root where possible. Many images support `user:` in the `compose.yaml` or variables like
  `PUID` and `PGID` for this.
- Containers only share the networks they need. A database doesn't have to be on the proxy network.
- Bind mounts only as far as needed, and with `:ro` if the container only has to read.

## Short checklist

- Only 80 and 443 forwarded in the router, or nothing at all thanks to a VPN or tunnel.
- No unnecessary `ports:` in the `compose.yaml` files.
- Admin interfaces only internal or behind a login.
- SSH with a key only.
- Operating system and images up to date.
- Docker socket only where it's needed.

The [security check](/en/tools/security-check/) offers a more detailed checklist to click through. At the end,
you see where you're well set up and what's still missing.
