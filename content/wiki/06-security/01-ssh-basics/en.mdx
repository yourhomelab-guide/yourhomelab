## What SSH does

SSH (Secure Shell) opens an encrypted connection to another computer. You type commands on your laptop, and they run
on the server. Everything that goes over the line is encrypted: passwords, commands, output.

In a homelab, SSH is the normal way to work. The server sits somewhere on a shelf, and you manage it from your desk.

## Client and server

Every connection has two sides:

- The **server** is a service (`sshd`) that runs on the homelab computer and listens on port 22 by default. On Debian
  and Ubuntu Server, you install it with the `openssh-server` package, usually right during installation.
- The **client** is the `ssh` program on your laptop. Linux, macOS and Windows 10/11 already come with it.

A connection looks like this:

```bash
ssh __USER__@__SERVER_IP__
```

Before the `@` is the user name on the server, after it the address. You end the session with `exit`.

## Key pairs instead of passwords

A password can be guessed or intercepted. As soon as SSH is reachable from the internet, bots try common combinations
around the clock. Keys solve this problem.

A **key pair** consists of two files:

| File | Where it lives | Who may see it |
| --- | --- | --- |
| Private key, e.g. `~/.ssh/id_ed25519` | only on your laptop | nobody but you |
| Public key, e.g. `~/.ssh/id_ed25519.pub` | on every server you want to log in to | anyone |

On the server, the public key goes into the file `~/.ssh/authorized_keys`. At login, the server sets a challenge that
can only be solved with the matching private key. The private key itself never leaves your laptop.

You create a new pair like this:

```bash
ssh-keygen -t ed25519 -C "laptop"
```

`ed25519` is a modern, short and secure key type. The comment after `-C` helps you tell keys apart later. Set a
**passphrase**: then the private key is useless even if someone copies the file. So you don't have to type the
passphrase all the time, `ssh-agent` remembers it for the session.

You transfer the public key with:

```bash
ssh-copy-id __USER__@__SERVER_IP__
```

How that works step by step and how to turn off password login afterwards is shown in the guides
[Setting up SSH keys](/en/setup/ssh-keys/) and [Hardening SSH](/en/setup/hardening-ssh/).

<Callout type="warning" title="Never share your private key">
  Don't copy the private key to servers, into chats or into Git repos. If you need access from a second device, create
  a separate key pair there. That way you can lock out a lost device specifically.
</Callout>

## known_hosts and fingerprint

There are keys on the other side too. Every SSH server has its own **host key**. With it, the server proves that
you're really talking to your server and not to a device that has slipped in between.

The first time you connect, you see a message like this:

```text
The authenticity of host '__SERVER_IP__ (__SERVER_IP__)' can't be established.
ED25519 key fingerprint is SHA256:...
Are you sure you want to continue connecting (yes/no/[fingerprint])?
```

The **fingerprint** is a short checksum of the host key. If you want to be thorough, compare it with the value the
server itself shows (directly on the device or in your VPS provider's console):

```bash
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

If you confirm with `yes`, the client saves the host key in `~/.ssh/known_hosts`. From then on, it checks with every
connection whether the key is still the same.

If the host key changes, SSH aborts with a big warning (`REMOTE HOST IDENTIFICATION HAS CHANGED`). That happens quite
harmlessly when you've reinstalled the server or an IP has been assigned to another device. Only then do you remove
the old entry:

```bash
ssh-keygen -R __SERVER_IP__
```

If you haven't changed anything, take the warning seriously and don't just connect anyway.

## The ~/.ssh/config file

Over time, you type the same user names, IPs and key paths again and again. The file `~/.ssh/config` on your laptop
bundles them:

```text
Host homelab
    HostName __SERVER_IP__
    User __USER__
    IdentityFile ~/.ssh/id_ed25519

Host vps
    HostName vps.__DOMAIN__
    User __USER__
    Port 22
```

After that, `ssh homelab` is enough. The shortcut also works for `scp` and `rsync` and in editors like VS Code with
Remote-SSH. The `man ssh_config` man page describes all options.

## File permissions

SSH is strict about file permissions. If the folder or the private key is readable by others, the client refuses the
key. You set the right permissions like this:

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519 ~/.ssh/config
```

On the server, the same applies to `~/.ssh` and `~/.ssh/authorized_keys`.
