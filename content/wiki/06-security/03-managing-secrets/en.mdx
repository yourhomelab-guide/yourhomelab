## What a Secret Is

A "**secret"** is any piece of information that can be used to gain access: database passwords, API tokens,
the client secret for [single sign-on](/en/wiki/single-sign-on/), keys for encrypted backups.

The danger rarely lies in a sophisticated attack. Most of the time, a secret simply ends up in the wrong place: in a
a public Git repository, in a screenshot on the forum, or in an unencrypted backup. That's why we're focusing on this here
Above all, order and a few set routines.

## The basic rule: Put secrets in the .env file

The  describes`compose.yaml` **how** a service works. The  `.env`next to it contains information that's just for you. So
You can safely`compose.yaml` split or version them.

```text
__ROOT__/nextcloud/
├── compose.yaml    ← teilbar
├── .env            ← Secrets, bleibt privat
└── data/
```

In the  you simply reference`compose.yaml` the variable:

```yaml
services:
  db:
    image: postgres:17
    environment:
      POSTGRES_PASSWORD: ${DB_PASSWORD}
```

"How .env `.env`Files Work" explains exactly [how .env files](/en/wiki/env-files/) work.

### Not in Git

If you manage your stacks as a Git repository, exclude `.env`files right from the start. One in`.gitignore` the root folder is enough:

```text
.env
*.env
!.env.example
```

It contains`.env.example` all variables with empty or sample values. That way, when you start over, you'll know what you
you have to fill out. Once a secret is committed, it remains in the Git history, even if you delete the file later.
The only solution is to change the secret (see below).

## Generate Secrets Randomly

Don't come up with passwords for services. You don't have to remember them, so they can be long and random:

```bash
openssl rand -hex 32
```

This generates 64 characters from  and`0-9` `a-f`. The variant  `openssl rand -base64 32`is shorter, but contains characters such as
`/`,  and`+` `=`. These can cause problems in link URLs or with some images. Hex is the safer choice.

Use a separate secret for each service and each database. If one becomes known, only one service is affected.

Some services, such as Tinyauth or Traefik's Basic Auth, expect a **bcrypt hash** instead of a password. You can generate one
using the [Password Hash](/en/werkzeuge/passwort-hash/) tool, right in your browser.

The  on`.env` the server is where the service reads the secret. However, it is not a good place to

## Docker Secrets: Secrets as Files

Environment variables are convenient, but they're visible to anyone who is allowed to run`docker inspect` the command. Docker Compose supports
That's why there are additional **secrets**: The secret is stored in a separate file and is located in the container under `/run/secrets/`
integrated.

```yaml
services:
  db:
    image: postgres:17
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets:
      - db_password

secrets:
  db_password:
    file: ./secrets/db_password.txt
```

This only works if the image can read the secret from a file. Many official images support this
Variables ending in `_FILE`, such as Postgres here. Whether an image supports this is specified in its documentation. For the
It's a perfectly`.env` fine starting point. You can find details in the
[Docker documentation on secrets in Compose](https://docs.docker.com/compose/how-tos/use-secrets/).

## For Advanced Users: SOPS and age

Do you want to manage your entire Homelab in Git, including secrets? If so, you can store the secrets in encrypted form
check in. A commonly used tool for this is [SOPS,](https://github.com/getsops/sops) along with
[age](https://github.com/FiloSottile/age) for the keys. SOPS encrypts only the values; the variable names remain
readable. Before deployment, decrypt the file on the server.

This is especially worthwhile if you use [Git deployments](/en/setup/git-deployments-forgejo/) or have multiple servers
run. You'll need to keep your private age key especially secure, because without it, you won't be able to access any of your
More secrets.

## Share secrets

Sooner or later, you'll have to change a secret—perhaps because it ended up in a repo or because someone doesn't have access
is supposed to have more. This is called **rotation**.

1. Create a new secret.
2. Modify it in the service, if the service has saved it.
3. Enter`.env` it in the  and `docker compose up -d`restart the stack with .
4. Update the entry in the password manager.

Note regarding databases: Databases such as Postgres or MariaDB only retrieve the password from the environment variable when
The very first time you start it, when the database is created. If you change only the afterward`.env`, the password will no longer work.
You have to change it in the database first, and only then in the `.env`.
