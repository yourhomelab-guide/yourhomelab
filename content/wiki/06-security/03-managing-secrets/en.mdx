## What a secret is

A **secret** is any piece of information that can be used to gain access: database passwords, API tokens, the client
secret for [single sign-on](/en/wiki/single-sign-on/), keys for encrypted backups.

The danger rarely lies in a sophisticated attack. Usually a secret simply ends up in the wrong place: in a public Git
repo, in a screenshot on a forum or in an unencrypted backup. So this is mostly about order and a few firm habits.

## The basic rule: secrets go into the .env

The `compose.yaml` describes **how** a service runs. The `.env` next to it contains what's nobody else's business. That
way you can share or version the `compose.yaml` without risk.

```text
__ROOT__/nextcloud/
├── compose.yaml    ← shareable
├── .env            ← secrets, stays private
└── data/
```

In the `compose.yaml`, you only refer to the variable:

```yaml
services:
  db:
    image: postgres:18
    environment:
      POSTGRES_PASSWORD: ${DB_PASSWORD}
```

[.env files](/en/wiki/env-files/) explains exactly how `.env` files work.

### Restrict permissions

Only your user should be able to read the `.env`:

```bash
chmod 600 __ROOT__/nextcloud/.env
```

`600` means: the owner may read and write, everyone else nothing at all. Docker Compose reads the file with your
rights, so that keeps working.

### Not in Git

If you keep your stacks in a Git repo, exclude `.env` files from the start. A `.gitignore` in the root folder is enough:

```text
.env
*.env
!.env.example
```

The `.env.example` contains all variables with empty or example values. That way you know what to fill in when you
set things up again. Once a secret has been committed, it stays in the Git history, even if you delete the file later.
Then the only thing that helps is replacing the secret (see below).

## Create secrets randomly

Don't make up passwords for services. You don't have to remember them, so they can be long and random:

```bash
openssl rand -hex 32
```

This creates 64 characters from `0-9` and `a-f`. The variant `openssl rand -base64 32` is shorter but contains
characters like `/`, `+` and `=`. They can cause problems in connection URLs or with some images. Hex is the safe
choice.

Use a separate secret for every service and every database. If one leaks, only one service is affected.

Some services like Tinyauth or Traefik's basic auth expect a **bcrypt hash** instead of the password. You create it
with the [password hash](/en/tools/password-hash/) tool, right in the browser.

## Keeping track

The `.env` on the server is where the service reads the secret. But it's not a good place to keep track of everything
there is. Two additions have proven themselves:

- **Password manager:** also store important secrets in your password manager, for example in
  [Vaultwarden](/en/services/vaultwarden/) or KeePassXC. This is especially important for everything you can't
  restore a backup without, like the passphrase of your Borg repository.
- **Encrypted backups:** your backup of `__ROOT__` contains all `.env` files. So it has to be encrypted. borgmatic does
  this automatically; see [Backup strategies](/en/wiki/backup-strategies/).

<Callout type="warning" title="Careful when sharing output">
  `docker compose config` shows the final configuration with all values filled in, including your passwords. The same
  goes for `docker inspect`. Check such output before you post it in a forum or chat.
</Callout>

## Docker secrets: secrets as files

Environment variables are convenient, but visible to anyone who may run `docker inspect`. That's why Docker Compose
also knows **secrets**: the secret lives in a file of its own and is mounted in the container under `/run/secrets/`.

```yaml
services:
  db:
    image: postgres:18
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets:
      - db_password

secrets:
  db_password:
    file: ./secrets/db_password.txt
```

This only works if the image can read the secret from a file. Many official images support variables ending in
`_FILE` for this, like Postgres here. The image's documentation tells you whether it can. To get started, the `.env` is
perfectly fine. Details are in the [Docker documentation on secrets in Compose](https://docs.docker.com/compose/how-tos/use-secrets/).

## For advanced users: SOPS and age

Want to manage your homelab completely in Git, secrets included? Then you can check the secrets in encrypted. A common
tool for this is [SOPS](https://github.com/getsops/sops) together with [age](https://github.com/FiloSottile/age) for
the keys. SOPS only encrypts the values; the variable names stay readable. Before deploying, you decrypt the file on
the server.

That's mainly worth it if you use [Git deployments](/en/setup/git-deployments-forgejo/) or run several servers. You
then have to back up the private age key especially well, because without it you can't get to any of your secrets.

## Replacing secrets

Sooner or later you'll have to change a secret, for example because it ended up in a repo or someone should no longer
have access. This is called **rotation**.

1. Create a new secret.
2. Change it in the service, if the service stored it.
3. Enter it in the `.env` and restart the stack with `docker compose up -d`.
4. Update the entry in your password manager.

Careful with databases: images like Postgres or MariaDB only take the password from the environment variable on the
very first start, when the database is created. If you only change the `.env` afterwards, the password no longer
matches. You have to change it in the database itself first, and only then in the `.env`.
