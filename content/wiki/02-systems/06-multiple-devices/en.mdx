## Many people start with more than one device

A Raspberry Pi is still lying in a drawer, a retired Dell OptiPlex or Lenovo ThinkCentre joins it, and later you may
rent a small VPS. That's completely normal. What matters is that each device gets a clear task. Otherwise, after a
few months, you won't know what runs where anymore.

The basic rule: **one device is your main server, the others take on clearly defined side roles.** Start with the
main server and work through the guides there once, completely. Another device comes in when there's a concrete
reason for it.

## Each device stays independent

You're not building a cluster. Each device is a server of its own with its own Linux, its own Docker and its own
Compose stacks. That has two advantages: if one device fails, the others keep running. And you can set up every
device with the same guides you already know.

So on each device, you repeat the basics:

- [SSH keys](/en/setup/ssh-keys/), [Users & sudo](/en/setup/users-sudo/) and [Hardening SSH](/en/setup/hardening-ssh/)
- [Firewall with UFW](/en/setup/firewall-ufw/) and [automatic updates](/en/setup/automatic-updates/)
- [Installing Docker](/en/setup/installing-docker/) and the same [directory structure](/en/setup/creating-the-directory-structure/) under `__ROOT__`

The same paths on all devices save a lot of thinking later, especially for backups and when moving services.

Joining several servers into a cluster (Docker Swarm, Kubernetes) rarely pays off in a homelab. Why is explained in
[Operating models at a glance](/en/wiki/operating-models/).

## Which device does what?

| Device | Role | Typical services |
| --- | --- | --- |
| **Mini PC** (OptiPlex, ThinkCentre, NUC) | Main server: x86 CPU, SSD, enough RAM | Vaultwarden, Immich, Paperless-ngx, Jellyfin, databases, reverse proxy |
| **Raspberry Pi** | Small services that should keep running when the main server is off | AdGuard Home, Uptime Kuma, Home Assistant |
| **VPS** | Public entry point and off-site location | Entry via VPN to the home network, monitoring from outside, target for off-site backups |

Three questions help with every service:

1. **Does it need lots of storage or computing power?** Then it belongs on the main server. Photos, documents and
   media live where the big disks are.
2. **Should it work when the main server fails?** DNS and monitoring belong on another device. If AdGuard Home runs
   on the main server and that restarts, suddenly the whole home network has no internet. And monitoring that runs
   on the server it watches can't report that server going down.
3. **Does it have to be reachable from the internet?** Then a VPS can be the entry point, while the data still stays
   at home. More in [Cloud, hybrid or local?](/en/wiki/cloud-hybrid-local/).

<Callout title="Start small">
You don't have to set up all three devices at once. One main server with backups is worth more than three
half-configured devices. The Pi as a DNS server is usually the most sensible second step.
</Callout>

## What's different on a Raspberry Pi

- **ARM instead of x86:** most well-known images exist for both architectures, but not all. On Docker Hub, "OS/ARCH"
  shows whether `linux/arm64` is included.
- **SSD instead of SD card:** SD cards tend to break in continuous operation. An SSD via USB or an NVMe HAT lasts
  much longer.
- **Little RAM:** 4 to 8 GB is enough for a few small services, not for Immich or Nextcloud.
- **Operating system:** Raspberry Pi OS Lite is based on Debian. Choose Debian for it under "My setup". Ubuntu Server
  is available for the Pi as well.

## What's different on a VPS

A VPS has a public IP and gets probed by bots from the first minute. The guides on
[hardening SSH](/en/setup/hardening-ssh/) and the [firewall](/en/setup/firewall-ufw/) are mandatory here, not
optional. Only run what really has to be public there, and don't store sensitive data with the provider that you
wouldn't also back up encrypted.

## Connecting the devices

On the home network, all devices get a [static IP](/en/setup/static-ip-hostname/). If a VPS joins, connect it to
the home network via [VPN](/en/wiki/vpn/), for example with WireGuard or Tailscale. Then all devices talk to
each other over private addresses, without you having to open ports at home.

So you don't have to juggle IPs, give each device a name in `~/.ssh/config` on your laptop:

```text
Host homelab
    HostName __SERVER_IP__
    User __USER__

Host pi
    HostName 192.168.1.20
    User __USER__

Host vps
    HostName vps.__DOMAIN__
    User __USER__
```

After that, `ssh pi` or `ssh vps` is enough. More in [SSH basics](/en/wiki/ssh-basics/). Also record in
your [documentation](/en/wiki/documentation/) which device has which IP and which stacks run on it.

## Reverse proxy across devices

This is the biggest pitfall. Traefik only reads its labels from containers on the **same** Docker host. So a service
on the Pi doesn't show up in Traefik on the main server by itself. You have two options:

- **Each device gets a reverse proxy of its own.** That's simplest when services with their own domain run on every
  device. Each proxy gets its own certificates.
- **One central proxy also forwards to other devices.** The service on the Pi publishes its port on the home network,
  and the proxy on the main server gets a fixed entry with IP and port. In
  [Nginx Proxy Manager](/en/setup/reverse-proxy-npm/), that's a normal proxy host; with Traefik, it's an entry in
  a configuration file instead of labels.

To start with, the first option is clearer. Very small services like AdGuard Home or Uptime Kuma on the Pi often
don't need a domain at all. On the home network, the IP with the port is enough.

## Backups and monitoring crosswise

Several devices are a gift for your [backup strategy](/en/wiki/backup-strategies/): the Pi backs up to the
main server, and the main server backs up to an external target or the VPS. The only important thing is that a backup
never sits on the same device as the data. How that works with borgmatic is shown in the guide
[Backups with borgmatic](/en/setup/backups-borgmatic/).

For monitoring, install a [Beszel](/en/setup/monitoring-beszel/) agent on every device.
[Uptime Kuma](/en/setup/uptime-kuma/) is best run on a different device than the services it checks, for example
on the Pi or the VPS.

## "My setup" with several devices

"My setup" always describes one device. When you set up another device, first enter its IP, its operating system
and, if needed, the stack folder. Then all commands in the guides fit. Domain and email stay the same.

## Checklist for a new device

1. Install the operating system, assign a static IP, enter it in "My setup" and `~/.ssh/config`
2. SSH key, user, hardening SSH, firewall, automatic updates
3. Install Docker and create the directory structure
4. Decide on the role and note it in your documentation
5. Start the Beszel agent and add the device to Uptime Kuma
6. Set up backups, to another device
