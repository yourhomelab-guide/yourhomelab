## Zwei Fragen, zwei Schichten

Wer sich Homelabs anderer Leute ansieht, findet scheinbar hundert verschiedene Setups. Fast alle lassen sich aber
mit zwei Fragen beschreiben:

1. **Unterbau:** Was läuft direkt auf der Hardware? Ein normales Linux, ein Hypervisor oder ein NAS-System?
2. **Container:** Wie startest und verwaltest du deine Dienste? Per Einzelbefehl, per Datei, per Weboberfläche oder
   mit einem Orchestrierer?

Beide Fragen kannst du getrennt beantworten. Die Antwort auf die zweite ist fast immer „Docker Compose“, egal
worauf es läuft.

## Schicht 1: der Unterbau

<Cards>
  <Card title="Bare Metal">
    Debian oder Ubuntu direkt auf der Hardware, darauf Docker. Wenig bewegliche Teile, volle Leistung. Der Weg der Anleitungen dieser Seite.
  </Card>
  <Card title="Hypervisor">
    Ein System, das virtuelle Maschinen (VMs) ausführt, im Homelab meist Proxmox VE. Mehrere Systeme auf einem Rechner, mit Snapshots und Backups eingebaut.
  </Card>
  <Card title="NAS-System">
    TrueNAS oder Unraid kümmern sich vor allem um Festplatten und Freigaben. Apps laufen über eine eigene Oberfläche, intern ebenfalls mit Docker.
  </Card>
</Cards>

**[Bare-Metal Linux](/de/nachschlagen/bare-metal-linux/)** ist der einfachste Start. Ein System, ein Ort für
Logs, und fast jede Anleitung im Netz passt. Was fehlt, sind Snapshots des ganzen Systems und die Möglichkeit,
nebenher ein anderes Betriebssystem zu betreiben.

Ein **Hypervisor** ist ein Betriebssystem, dessen Aufgabe es ist, andere Systeme laufen zu lassen. Im Homelab ist
**[Proxmox VE](/de/nachschlagen/proxmox-ve/)** der Standard: kostenlos, Open Source, auf Debian aufgebaut. Daneben
gibt es XCP-ng (Open Source, auf Basis von Xen) und Hyper-V, das in Windows Pro und Windows Server steckt. VMware
ESXi war lange verbreitet. Seit der Übernahme durch Broadcom ist die kostenlose Version aber nur noch eingeschränkt
verfügbar, für ein neues Homelab ist ESXi deshalb selten die erste Wahl.

**[TrueNAS und Unraid](/de/nachschlagen/truenas-unraid/)** lohnen sich, wenn der Rechner vor allem ein Datenspeicher
mit mehreren Platten ist. Sie bringen App-Kataloge mit, verwalten Docker aber auf ihre eigene Weise. Pfade und
Abläufe weichen deshalb von den Anleitungen dieser Seite ab.

### Docker unter Proxmox: VM oder LXC?

Proxmox kennt zwei Arten von Gästen: VMs mit eigenem Kernel und LXC-Container, die sich den Kernel mit dem Host
teilen. Docker läuft technisch auch in einem LXC-Container, und viele betreiben es erfolgreich so. Wir empfehlen
trotzdem, wie auch die Proxmox-Dokumentation, eine **VM**: Sie trennt stärker, braucht keine gelockerten
Sicherheitsoptionen, und ein Update des Proxmox-Hosts ändert nichts an deinem Docker. Die Gründe stehen ausführlich im
Artikel [Proxmox VE](/de/nachschlagen/proxmox-ve/). Den Unterschied zwischen VMs und Containern erklärt
[VMs oder Container?](/de/nachschlagen/vms-oder-container/).

In der VM installierst du Debian oder Ubuntu und folgst den Anleitungen, als wäre sie ein eigener Server.

## Schicht 2: Wie Container gestartet werden

Was ein Container ist, erklärt [Was ist Docker?](/de/nachschlagen/was-ist-docker/). Hier geht es darum, wie du ihn
startest. Nimm als Beispiel [Uptime Kuma](/de/dienste/uptime-kuma/), ein Tool, das deine Dienste überwacht.

### docker run: ein Befehl

```bash
docker run -d \
  --name uptime-kuma \
  --restart unless-stopped \
  -e TZ=__TZ__ \
  -p 3001:3001 \
  -v __DATA(uptime-kuma)__/data:/app/data \
  louislam/uptime-kuma:2
```

Das ist ideal, um schnell etwas auszuprobieren. Der Haken: Der Befehl steht danach nirgends. Für ein Update musst
du den Container löschen und den Befehl exakt wiederholen. Nach ein paar Monaten weiß niemand mehr, mit welchen
Optionen ein Container gestartet wurde.

### Docker Compose: eine Datei

Dasselbe als `__ROOT__/uptime-kuma/compose.yaml`:

```yaml
services:
  uptime-kuma:
    image: louislam/uptime-kuma:2
    container_name: uptime-kuma
    restart: unless-stopped
    environment:
      - TZ=__TZ__
    ports:
      - "3001:3001"
    volumes:
      - __DATA(uptime-kuma)__/data:/app/data
```

Gestartet wird mit `docker compose up -d` im Ordner des Stacks. Der Inhalt ist derselbe, aber jetzt steht er in
einer Datei. Die kannst du lesen, sichern, mit Git versionieren und nach einer Änderung einfach erneut anwenden.
Genau deshalb ist [Docker Compose](/de/nachschlagen/docker-compose/) der Standard dieser Seite.

### Compose mit Weboberfläche

Werkzeuge wie Portainer, Dockhand, Dockge oder Komodo zeigen deine Stacks im Browser: Status, Logs, Neustart per
Klick. Das ist bequem, vor allem vom Handy aus. Eine Regel macht dir das Leben leichter:

<Callout title="Dateien bleiben führend">
Behalte deine Stacks als `compose.yaml` unter `__ROOT__` und nutze die Oberfläche zum Ansehen und Steuern. Stacks, die
du nur in der Oberfläche anlegst, liegen im Datenordner des Werkzeugs und hängen an ihm. Mehr dazu im Guide
[Portainer oder Dockhand](/de/einrichten/portainer-dockhand/).
</Callout>

### Orchestrierung: Kubernetes, k3s, Docker Swarm

Ein Orchestrierer verteilt Container auf mehrere Server, startet sie bei einem Ausfall anderswo neu und rollt
Updates schrittweise aus. Kubernetes ist der Standard in Rechenzentren, **k3s** eine schlanke Variante davon, die
gut auf kleiner Hardware läuft. **Docker Swarm** ist in Docker schon eingebaut und einfacher, wird aber seltener
genutzt.

Das ist spannende Technik, und wer beruflich mit Cloud oder DevOps zu tun hat, lernt im Homelab viel damit. Für
einen oder wenige Server zuhause bringt sie aber vor allem zusätzliche Konzepte, die du verstehen und pflegen
musst. Compose ist dort übersichtlicher, leichter zu sichern und reicht für fast alle Dienste. Die Anleitungen dieser
Seite behandeln Kubernetes deshalb nicht.

## Welche Kombination passt?

| Situation | Unterbau | Container | Einstieg |
| --- | --- | --- | --- |
| **Ein Rechner, Einstieg** | Debian oder Ubuntu direkt auf der Hardware | Docker Compose | Der Weg dieser Seite, ab [Betriebssystem installieren](/de/einrichten/betriebssystem-installieren/) |
| **Mehrere Systeme, ausprobieren, Snapshots** | Proxmox VE, darin eine Debian-VM | Docker Compose in der VM | [Proxmox VE](/de/nachschlagen/proxmox-ve/), dann die Guides in der VM |
| **Viel Speicher, NAS zuerst** | TrueNAS oder Unraid | Compose-Stacks trotzdem als Dateien, oder eine Linux-VM | [TrueNAS & Unraid](/de/nachschlagen/truenas-unraid/) |
| **Lernen für den Beruf** | Proxmox mit mehreren VMs | k3s zusätzlich, wichtige Dienste weiter mit Compose | Erst Compose sicher beherrschen |

Wenn du unsicher bist: Nimm die erste Zeile. Ein Umzug ist später leicht, weil jeder Dienst als `compose.yaml`
mit seinen Daten unter `__ROOT__` liegt. Den Ordner kopierst du auf das neue System, etwa in eine VM unter Proxmox,
und startest die Stacks dort neu. Die Schritte dafür stehen in [Umzug auf neue Hardware](/de/einrichten/umzug-neue-hardware/).
