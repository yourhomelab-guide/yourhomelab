## Two questions, two shifts

If you look at other people's home labs, you'll apparently find a hundred different setups. But almost all of them can be
Describe it using two questions:

1. **Underlying infrastructure:** What runs directly on the hardware? A standard Linux system, a hypervisor, or a NAS system?
2. **Containers:** How do you start and manage your services? Using a single command, a file, a web interface, or
   with an orchestrator?

You can answer both questions separately. The answer to the second one is almost always “Docker Compose,” no matter what
what it all comes down to.

## Layer 1: the subbase

<Cards>
  <Card title="Bare Metal">
    Debian or Ubuntu running directly on the hardware, with Docker on top. Few moving parts, full performance. That's the approach outlined in the guides on this page.
  </Card>
  <Card title="Hypervisor">
    A system that runs virtual machines (VMs)—usually Proxmox VE in a home lab. Multiple systems on a single computer, with built-in snapshots and backups.
  </Card>
  <Card title="NAS system">
    TrueNAS and Unraid primarily handle hard drives and file shares. Apps run through their own interface, using Docker internally as well.
  </Card>
</Cards>

**[Bare-Metal Linux](/en/wiki/bare-metal-linux/)** is the easiest way to get started. One system, one place for
Logs, and almost every tutorial online works. What's missing are snapshots of the entire system and the ability to,
to run another operating system alongside it.

A **hypervisor** is an operating system whose purpose is to run other systems. In a home lab,
**[Proxmox VE](/en/wiki/proxmox-ve/)** is the standard: free, open source, and based on Debian. In addition,
There is XCP-ng (open source, based on Xen) and Hyper-V, which is included in Windows Pro and Windows Server. VMware
ESXi has been widely used for a long time. However, since Broadcom acquired it, the free version has been limited.
It's available, so ESXi is rarely the first choice for a new home lab.

**[TrueNAS and Unraid](/en/wiki/truenas-unraid/)** are worth it if the computer is primarily used for data storage
with multiple volumes. They come with app catalogs but manage Docker in their own way. Paths and
The procedures therefore differ from the instructions on this page.

### Docker on Proxmox: VM or LXC?

Proxmox supports two types of guests: VMs with their own kernel and LXC containers that share the host's kernel
Share. Technically, Docker also runs in an LXC container, and many people use it successfully this way. We recommend
Still, just like the Proxmox documentation says, it's a **VM**: It provides greater isolation and doesn't require relaxed
Security options, and updating the Proxmox host won't affect your Docker. The reasons are explained in detail in the
Article: [Proxmox VE](/en/wiki/proxmox-ve/). Explaining the Difference Between VMs and Containers
[VMs or containers?](/en/wiki/vms-or-containers/)

In the VM, install Debian or Ubuntu and follow the instructions as if it were a standalone server.

## Layer 2: How Containers Are Started

["What Is Docker?](/en/wiki/what-is-docker/)" explains what a container is. This article focuses on how to use it.
Let's get started. Take [Uptime Kuma](/en/services/uptime-kuma/), for example—a tool that monitors your services.

### docker run: a command

```bash
docker run -d \
  --name uptime-kuma \
  --restart unless-stopped \
  -e TZ=__TZ__ \
  -p 3001:3001 \
  -v __DATA(uptime-kuma)__/data:/app/data \
  louislam/uptime-kuma:2
```

This is ideal for quickly trying something out. The catch: The command isn't saved anywhere afterward. To update it, you must
You should delete the container and repeat the command exactly as before. After a few months, no one will remember which
Options with which a container was started.

### Docker Compose: a file

The same as`__ROOT__/uptime-kuma/compose.yaml`:

```yaml
services:
  uptime-kuma:
    image: louislam/uptime-kuma:2
    container_name: uptime-kuma
    restart: unless-stopped
    environment:
      - TZ=__TZ__
    ports:
      - "3001:3001"
    volumes:
      - __DATA(uptime-kuma)__/data:/app/data
```

We'll start with  `docker compose up -d`in the stack's folder. The content is the same, but now it's located in
a file. You can read it, save it, version it with Git, and simply reapply it after making a change.
That is exactly why [Docker Compose](/en/wiki/docker-compose/) is the standard on this site.

### Compose with a Web Interface

Tools like Portainer, Dockhand, Dockge, and Komodo display your stacks in the browser: status, logs, and restart via

### Orchestration: Kubernetes, k3s, Docker Swarm

An orchestrator distributes containers across multiple servers, restarts them on another server in the event of a failure, and rolls out
Roll out updates gradually. Kubernetes is the standard in data centers; **k3s is** a lightweight version of it that
runs well on low-end hardware. **Docker Swarm** is already built into Docker and is easier to use, but it's used less often
used.

This is exciting technology, and anyone who works with the cloud or DevOps can learn a lot from it in a home lab. For
Having one or a few servers at home, however, provides you above all with additional concepts that you need to understand and maintain
you have to. Compose is more organized, easier to back up, and works for almost all services. The instructions in this
That is why Kubernetes does not handle this.

## Which combination works best?

| Situation | Substructure | Container | Getting Started |
| --- | --- | --- | --- |
| **A Computer: Getting Started** | Debian or Ubuntu directly on the hardware | Docker Compose | The path to this page, starting from "[Install operating system"](/en/setup/installing-the-os/) |
| **Multiple systems, testing, snapshots** | Proxmox VE, with a Debian VM inside it | Docker Compose in the VM | [Proxmox VE](/en/wiki/proxmox-ve/), then the guides in the VM |
| **Plenty of storage, NAS first** | TrueNAS or Unraid | Compose stacks as files anyway, or a Linux VM | [TrueNAS & Unraid](/en/wiki/truenas-unraid/) |
| **Learning for a Career** | Proxmox with Multiple VMs | k3s in addition; continue using Compose for important services | First, master Compose thoroughly |

If you're unsure, go with the first line. Moving later is easy because every service acts as `compose.yaml`
which contains`__ROOT__` its data. Copy the folder to the new system, for example, to a VM running on Proxmox,
and restart the stacks there.
