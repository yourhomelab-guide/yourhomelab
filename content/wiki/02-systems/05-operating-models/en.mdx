## Two questions, two layers

If you look at other people's homelabs, you'll find what seem like a hundred different setups. But almost all of
them can be described with two questions:

1. **Foundation:** what runs directly on the hardware? A normal Linux, a hypervisor or a NAS system?
2. **Containers:** how do you start and manage your services? With a single command, with a file, through a web
   interface or with an orchestrator?

You can answer both questions separately. The answer to the second is almost always "Docker Compose", no matter
what it runs on.

## Layer 1: the foundation

<Cards>
  <Card title="Bare metal">
    Debian or Ubuntu directly on the hardware, Docker on top. Few moving parts, full performance. The path of the guides on this site.
  </Card>
  <Card title="Hypervisor">
    A system that runs virtual machines (VMs), in a homelab usually Proxmox VE. Several systems on one computer, with snapshots and backups built in.
  </Card>
  <Card title="NAS system">
    TrueNAS or Unraid mainly take care of disks and shares. Apps run through an interface of their own, internally with Docker as well.
  </Card>
</Cards>

**[Bare-metal Linux](/en/wiki/bare-metal-linux/)** is the simplest start. One system, one place for logs,
and almost every guide on the web fits. What's missing are snapshots of the whole system and the option to run
another operating system on the side.

A **hypervisor** is an operating system whose job is to run other systems. In homelabs,
**[Proxmox VE](/en/wiki/proxmox-ve/)** is the standard: free, open source, built on Debian. There's also
XCP-ng (open source, based on Xen) and Hyper-V, which comes with Windows Pro and Windows Server. VMware ESXi was
widespread for a long time. Since the takeover by Broadcom, though, the free version is only available with
restrictions, so ESXi is rarely the first choice for a new homelab.

**[TrueNAS and Unraid](/en/wiki/truenas-unraid/)** are worth it if the computer is mainly data storage with
several disks. They come with app catalogs but manage Docker in their own way. Paths and workflows therefore differ
from the guides on this site.

### Docker under Proxmox: VM or LXC?

Proxmox knows two kinds of guests: VMs with their own kernel and LXC containers that share the kernel with the host.
Technically, Docker also runs in an LXC container, and many people run it that way successfully. Still, like the
Proxmox documentation, we recommend a **VM**: it separates more strongly, needs no relaxed security options, and an
update of the Proxmox host doesn't change anything about your Docker. The reasons are explained in detail in the
article [Proxmox VE](/en/wiki/proxmox-ve/). The difference between VMs and containers is explained in
[VMs or containers?](/en/wiki/vms-or-containers/).

In the VM, you install Debian or Ubuntu and follow the guides as if it were a server of its own.

## Layer 2: how containers are started

What a container is is explained in [What is Docker?](/en/wiki/what-is-docker/). Here it's about how you
start it. Take [Uptime Kuma](/en/services/uptime-kuma/) as an example, a tool that monitors your services.

### docker run: one command

```bash
docker run -d \
  --name uptime-kuma \
  --restart unless-stopped \
  -e TZ=__TZ__ \
  -p 3001:3001 \
  -v __DATA(uptime-kuma)__/data:/app/data \
  louislam/uptime-kuma:2
```

That's ideal for trying something quickly. The catch: afterwards, the command isn't written down anywhere. For an
update, you have to delete the container and repeat the command exactly. After a few months, nobody knows which
options a container was started with.

### Docker Compose: one file

The same as `__ROOT__/uptime-kuma/compose.yaml`:

```yaml
services:
  uptime-kuma:
    image: louislam/uptime-kuma:2
    container_name: uptime-kuma
    restart: unless-stopped
    environment:
      - TZ=__TZ__
    ports:
      - "3001:3001"
    volumes:
      - __DATA(uptime-kuma)__/data:/app/data
```

You start it with `docker compose up -d` in the stack's folder. The content is the same, but now it's in a file. You
can read it, back it up, version it with Git and simply apply it again after a change. That's exactly why
[Docker Compose](/en/wiki/docker-compose/) is the standard on this site.

### Compose with a web interface

Tools like Portainer, Dockhand, Dockge or Komodo show your stacks in the browser: status, logs, restart with a
click. That's convenient, especially from your phone. One rule makes your life easier:

<Callout title="Files stay in charge">
Keep your stacks as `compose.yaml` under `__ROOT__` and use the interface for viewing and controlling. Stacks you
only create in the interface live in the tool's data folder and depend on it. More in the guide
[Portainer or Dockhand](/en/setup/portainer-dockhand/).
</Callout>

### Orchestration: Kubernetes, k3s, Docker Swarm

An orchestrator distributes containers across several servers, restarts them elsewhere when one fails and rolls out
updates step by step. Kubernetes is the standard in data centers; **k3s** is a lean variant of it that runs well on
small hardware. **Docker Swarm** is already built into Docker and simpler, but used less often.

That's exciting technology, and if you work with cloud or DevOps, you'll learn a lot with it in a homelab. For one or
a few servers at home, though, it mainly brings extra concepts you have to understand and maintain. Compose is
clearer there, easier to back up and enough for almost all services. So the guides on this site don't cover
Kubernetes.

## Which combination fits?

| Situation | Foundation | Containers | Where to start |
| --- | --- | --- | --- |
| **One computer, getting started** | Debian or Ubuntu directly on the hardware | Docker Compose | The path of this site, starting with [Installing the operating system](/en/setup/installing-the-os/) |
| **Several systems, experimenting, snapshots** | Proxmox VE with a Debian VM in it | Docker Compose in the VM | [Proxmox VE](/en/wiki/proxmox-ve/), then the guides in the VM |
| **Lots of storage, NAS first** | TrueNAS or Unraid | Compose stacks still as files, or a Linux VM | [TrueNAS & Unraid](/en/wiki/truenas-unraid/) |
| **Learning for work** | Proxmox with several VMs | k3s in addition, important services still with Compose | Master Compose first |

If you're unsure: take the first row. Moving later is easy, because every service lives as a `compose.yaml` with its
data under `__ROOT__`. You copy the folder to the new system, for example into a VM under Proxmox, and start the
stacks there again. The steps are in [Moving to new hardware](/en/setup/moving-hardware/).
