## What's this about?

Many services run side by side on a server. To keep them out of each other's way, you separate them. There are two
techniques for this: **virtual machines** (VMs) and **containers**. Both look similar from the outside but work in
fundamentally different ways.

The key term is the **kernel**. It's the core of the operating system that talks directly to the hardware and
manages memory, processes and devices.

## Virtual machines

A VM is a **simulated computer**. A hypervisor (such as KVM in Proxmox) presents it with CPU, RAM, disk and network
card. Inside the VM runs a complete operating system **with its own kernel**. Often it doesn't even know it's
virtualized.

- **Strong isolation.** Between the VM and the host sits the hypervisor, backed by the CPU (Intel VT-x, AMD-V).
- **Any operating system.** Linux, Windows, Home Assistant OS, BSD.
- **Fixed resource needs.** Each VM boots a system of its own and reserves RAM. A lean Linux VM needs roughly a few
  hundred MB of RAM before a single service runs.

## Containers

A container is **not a computer of its own** but a group of processes on the host that's walled off. All containers
**share the host's kernel**. Features of the Linux kernel take care of the separation:

- **Namespaces** make sure a container only sees its own processes, its own file system and its own network.
- **cgroups** limit how much CPU and RAM a container may use.

That makes containers light: they start in seconds and need hardly more resources than the program itself. The
price: because the kernel is shared, only Linux programs run, and a hole in the kernel affects all containers at
once.

There are two kinds:

- **Application containers** like [Docker](/en/wiki/what-is-docker/): one container per service, built from
  a ready-made image. That's the standard for self-hosting.
- **System containers** like LXC in Proxmox: a whole Linux system with package management and several services,
  almost like a small VM, but without a kernel of its own.

## Compared

| | VM | Container (Docker) |
| --- | --- | --- |
| **Kernel** | Its own | Shared with the host |
| **Isolation** | Strong | Good, but weaker |
| **Startup** | Seconds to minutes | Usually under a second |
| **Overhead** | A full operating system per VM | Hardly more than the program |
| **Operating systems** | Any | Linux only (on a Linux host) |
| **Typical use** | Separate systems, a different OS | Individual services |

## When do you use which?

For a homelab, the question is rarely "either or". The usual combination is: **Docker containers for the services**
and, if needed, **a VM as a shell around them**.

- **Docker only:** you have one computer and want to run a few services. Linux directly on the hardware, Docker on
  top. That's how the [guides on this site](/en/setup/installing-docker/) work.
- **VM with Docker inside:** you use Proxmox or a NAS system and want to keep Docker cleanly separated from the host.
- **A VM of its own:** for anything that needs its own operating system (Home Assistant OS, Windows, a firewall like
  OPNsense), or for services you want to isolate especially strictly. For Home Assistant, the guide
  [Home Assistant](/en/setup/home-assistant/) weighs VM against container.
- **LXC:** for small, single Linux services under Proxmox when RAM is tight.

<Callout title="Containers are still secure enough">
Weaker isolation doesn't mean containers are insecure. How you use them matters more than the technology: current
images, no unnecessary privileges like `privileged: true`, as few open ports as possible. More under
[Keeping the attack surface small](/en/wiki/attack-surface/).
</Callout>
